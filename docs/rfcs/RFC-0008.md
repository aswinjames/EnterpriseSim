# RFC-0008 — Planner API

| Field | Value |
|---|---|
| RFC | `RFC-0008` |
| Title | Planner API |
| Status | Accepted |

| Created | 2026-03-24 |
| Related | `ARCH-06`; `RFC-0007` (DI Control Loop), `RFC-0002` (Context Assembly), `RFC-0014` (Evaluation Framework), `RFC-0017` (Learning Event Propagation); `ADR-0008` (DI Sole Orchestrator) |

## 1. Summary

This RFC specifies the **Planner API** — the contract by which Decision Intelligence turns a
`TaskIntent` and assembled context into an explicit, testable `PLAN-###`, and by which that
plan is validated against `CANON-001` before any execution. It normatively owns
`sdk.planner.Planner`, `sdk.planner.PlanValidator`, and the `planning_object.schema.json`
contract. It defines `plan(intent, context)`, lineage-preserving `replan(previous, reason,
context)`, and `PlanValidator.validate`/`required_approvals`, including the concrete
violations a plan can carry (missing rollback, reverse dependency, insufficient test coverage)
and the risk-tier approval rules of `CANON-001` §7. The Planner produces the commitment;
Decision Intelligence (`RFC-0007`) owns the agency to act on it, and Evaluation (`RFC-0014`)
scores execution against it.

## 2. Motivation

`CANON-001` §9 (Stage 3) makes planning a first-class artifact: "A plan is a commitment the
Worker can be evaluated against. It answers *what will I do, in what order, and how will I know
it worked?*" `ARCH-06` Best Practice 2 sharpens this — "plan explicitly, then evaluate against
the plan." Without a durable, structured plan there is nothing for Evaluation to measure
adherence to, nothing for Reflection to diagnose against, and no artifact in which to record
the rollback strategy, risk tier, and applied experience that `CANON-001` §4/§7 require.

A plan is also the natural place to enforce standards *before* work is done rather than after.
Catching a missing rollback plan, a forbidden reverse dependency, or thin test coverage at
plan-validation time is far cheaper than catching it as a failed evaluation on an opened PR.
The `PlanValidator` exists so that the loop fails fast on a bad commitment.

## 3. Guide-level explanation

### 3.1 From intent to plan

When Decision Intelligence has a `TaskIntent` and a `ContextObject` (e.g. `CTX-0118` for
`CHK-1421`), it calls `Planner.plan(intent, context)`. The Planner produces a `PLAN-###`
containing:

- **success_criteria** — the observable conditions that mean "done," written so Evaluation can
  test each one.
- **steps** — an ordered list of `{ n, action, tool, expect? }` directives.
- **rollback** — how to revert safely, ideally with no schema down-migration (`CANON-001` §7.4).
- **risk_tier** — the `CANON-001` criticality tier (0–3) of the affected application, which
  drives approvals and routing.
- **applied_experience** — the `EXP-###` lessons the plan incorporates, closing the learning
  loop from `ARCH-03`.
- **routing** — the model class the plan warrants (a hint the Model Router in `RFC-0010`
  consumes), with a reason.

The plan is a structured object (`planning_object.schema.json`), not prose — the same
model-agnostic discipline the Context Layer uses (`ARCH-01`).

### 3.2 Replanning preserves lineage

Plans are revised mid-task — a contract test fails, context is re-retrieved, a step proves
unworkable. `Planner.replan(previous, reason, context)` produces a *new* `PLAN-###` that
records the `reason` and links back to the plan it supersedes (`supersedes` in the schema). A
replan is never an in-place edit; the original plan and the trail of revisions are retained so
Reflection (`ARCH-05`) can ask *why* the plan changed and the replan rate (`ARCH-06` signals)
can be measured.

### 3.3 Validation is a gate, not advice

Before execution, `PlanValidator.validate(plan)` returns a `PlanCheck` — `ok` plus a list of
`violations`. A plan that omits a rollback, encodes a dependency against the canon dependency
graph, or fails to include the tests its risk tier requires is **not** executed; Decision
Intelligence replans or escalates. Separately, `PlanValidator.required_approvals(plan)` reports
how many human approvals the plan's risk tier demands under `CANON-001` §7, which the
`PolicyGuard` (`RFC-0030`) enforces before any `Act`.

## 4. Reference-level explanation

### 4.1 `sdk.planner.Planner`

This RFC owns the `Planner` abstract base class in `sdk/planner/interfaces.py`:

- `plan(intent: TaskIntent, context: ContextObject) -> PlanningObject` — "produce an ordered
  plan with success criteria, tests, rollback and risk tier." `TaskIntent` is owned by
  `sdk.context` (`RFC-0002`); the returned `PlanningObject` conforms to
  `planning_object.schema.json`.
- `replan(previous: PlanningObject, reason: str, context: ContextObject) -> PlanningObject` —
  "revise a plan invalidated mid-task, preserving lineage to the previous plan." The
  implementation sets `supersedes = previous.id` and records `reason` in `metadata`.

The Planner has no agency: it is *called by* Decision Intelligence (`RFC-0007`), which decides
whether and when to plan, replan, or act (`ADR-0008`). The Planner never invokes tools or the
Gateway.

### 4.2 The `PlanningObject` contract

Per `sdk.objects.PlanningObject` and `planning_object.schema.json`, a `PLAN-###` requires
`id`, `task`, `intent`, `success_criteria` (≥1), `steps` (≥1), `rollback`, and `risk_tier`
(integer 0–3). Optional fields include `app`, `applied_experience` (`EXP-###` references),
`supersedes` (a `PLAN-###`, set by `replan`), and `routing` (`{ model_class, reason }`). Each
step is `{ n, action, tool, expect? }` with a monotonic `n ≥ 1`. The schema closes with
`unevaluatedProperties: false`, so extension data lives only under `metadata` (`RFC-0021`).

### 4.3 `PlanValidator` and `PlanCheck`

This RFC owns `PlanValidator`. `validate(plan) -> PlanCheck` checks the plan against
`CANON-001` §4/§7/§8. `PlanCheck` is `{ ok: bool, violations: Sequence[str] }`. The canonical
violation classes:

| Violation | Rule source | Example |
|---|---|---|
| `missing rollback plan` | `CANON-001` §7.4; PR template §4.2 | `rollback` empty or absent |
| `reverse dependency` | `CANON-001` §3 dependency graph | a step makes `APP-012` depend on `APP-003` |
| `insufficient test coverage` | `CANON-001` §4.4 test pyramid | no unit/contract step for a Tier 0/1 change; coverage plan below the ≥80% bar |
| `missing required approvals` | `CANON-001` §7.5 | fewer approvers planned than the tier demands |
| `undeclared risk tier` | `CANON-001` §3/§7 | `risk_tier` inconsistent with the affected `APP-` |

`validate` is deterministic and evidence-linkable: each violation names the offending step or
field and the canon clause, so a failed check is as auditable as a failed evaluation
(`ARCH-04`, "no score without evidence").

### 4.4 Required approvals by risk tier

`required_approvals(plan) -> int` implements `CANON-001` §7.5 directly:

| Change class (by tier / scope) | Required approvals | Additional gates |
|---|---|---|
| Standard (Tier 2/3) | 1 | CI green |
| Tier 0/1 service | 2 (incl. CODEOWNERS) | CI green; perf gate for Tier 0 |
| PCI / auth code | 2, **including Security Engineering (`TEAM-040`)** | threat-model check, SAST/DAST |
| Cross-service contract change | owning + dependent team | contract tests; RFC if breaking |

For `PLAN-0072` (`risk_tier: 0`, `APP-003` Checkout), `required_approvals` returns **2**. A
plan that also touched Payments (`APP-012`, PCI) would still return 2 but with the constraint
that one approver be Security Engineering — the count and the *composition* both matter, and
the `PolicyGuard` (`RFC-0030`) enforces both before execution.

### 4.5 The plan as a testable commitment

A plan is written to be evaluated. Every entry in `success_criteria` must be phrased as
something the Evaluation Layer (`RFC-0014`) can turn into an objective gate or a rubric item —
"guest can place an order end to end," "no `APP-015` account created for guests (negative
test)." This is what lets `EVAL-0061` score `PR-0312` *against* `PLAN-0072` and report plan
adherence as a first-class signal (`ARCH-04`). A plan whose criteria are untestable is itself a
validation defect.

### 4.6 Applied experience and the learning loop

`applied_experience` links a plan to the `EXP-###` lessons it incorporates. `PLAN-0072` applies
`EXP-090` ("guest carts must not create Loyalty (`APP-015`) accounts"), which is precisely why
step 3 adds a negative-assertion test. This is the closed loop of `CANON-001` §9: a past
failure became a reflection (`REF-0019`), then an experience (`EXP-090`), retrieved into context
(`CTX-0118`), and now planned against. `RFC-0017` governs how experiences update planning policy
over time; this RFC only requires that applied experiences be recorded on the plan.

### 4.7 Worked example — `PLAN-0072` (mirrors `ARCH-06` Example A)

```yaml
plan:
  id: PLAN-0072
  task: CHK-1421
  app: APP-003
  intent: "Add guest checkout without creating a Loyalty (APP-015) account."
  success_criteria:
    - "Guest can place an order end to end."
    - "No APP-015 account created for guests (negative test)."
    - "Idempotency preserved (KN-052)."
  steps:
    - { n: 1, action: "read PlaceOrder.java + guest-flow tests", tool: repo }
    - { n: 2, action: "implement guest path; guard APP-015 provisioning", tool: repo }
    - { n: 3, action: "add GuestNoLoyaltyTest (negative assertion)", tool: repo }
    - { n: 4, action: "run unit + contract tests", tool: ci, expect: "TR-#### pass" }
    - { n: 5, action: "open PR with rollback plan", tool: github }
  rollback: "Feature-flag guest checkout; disable flag to revert with no schema change."
  risk_tier: 0                       # Tier 0 service -> 2 approvals (CANON-001 §7)
  applied_experience: [EXP-090]
  routing: { model_class: "high-reasoning", reason: "Tier 0 change with subtle side-effect risk" }
```

Running `validate(PLAN-0072)` returns `ok = true`: rollback is present and schema-safe, no
reverse dependency (Checkout `APP-003` may depend on Payments `APP-012`, not vice-versa), and
steps 3–4 satisfy the Tier 0 test-coverage bar. `required_approvals(PLAN-0072)` returns **2**.
The plan then executes as `PR-0312` and is scored by `EVAL-0061` (0.91).

## 5. Drawbacks

- **Upfront rigidity.** Committing to an ordered plan can be wasteful for exploratory tasks
  where the right steps are unknown until work begins; `replan` mitigates but adds churn.
- **Validation false positives.** A conservative `PlanValidator` may flag a legitimately novel
  step as a violation (e.g., an intentional, canon-approved dependency exception), forcing an
  escalation; the `metadata` escape hatch and human review absorb these.
- **Plan/execution divergence.** A plan is only a commitment; execution can still deviate. This
  is detected downstream by Evaluation's plan-adherence check (`ARCH-04`), not prevented here.

## 6. Rationale & alternatives

- **Implicit planning inside the reasoning call** — rejected: produces no inspectable
  `PLAN-###`, so nothing can be validated pre-execution or scored for adherence (`CANON-001`
  §9, `ARCH-06`).
- **Free-text plans** — rejected: not machine-checkable against the dependency graph or the
  approval matrix; the structured `planning_object.schema.json` is required for `validate`.
- **Mutable plans (edit in place on replan)** — rejected: destroys lineage and the replan-rate
  signal, and breaks replay (`RFC-0024`); `supersedes` preserves history instead.
- **Validation as post-hoc advice** — rejected: the point is to fail fast before execution
  (`ADR-0041` neighbourhood); an advisory validator would let bad plans reach tools.

## 7. Prior art

Generic inspirations: classical **AI planning** (goal → ordered actions with pre/post
conditions) and **hierarchical task networks**; the software-engineering practice of a
**design/implementation plan reviewed before coding**; and change-management **rollback
planning** as a release-gate artifact. The "plan as testable commitment" framing echoes
acceptance-criteria-driven development. No proprietary planner or workflow engine is referenced.

## 8. Unresolved questions

- Should `success_criteria` be a structured, per-criterion object (with an expected gate type)
  rather than free strings, to tighten the Evaluation coupling (`RFC-0014`)?
- How should `PlanValidator` express *approved exceptions* to the dependency graph so a
  legitimate cross-context call is not a permanent false positive?
- Should routing hints live on the plan at all, or move entirely to `RFC-0010`? (Leaning: keep
  the hint on the plan; the Router remains authoritative.)

## 9. Future possibilities

- **Learned planners** — planning heuristics continuously improved by the Learning Engine and
  specialized per task type (`ARCH-06` future evolution), narrowing `replan` rates.
- **Playbook instantiation** — generating a plan by instantiating a validated experience-cluster
  playbook (`ARCH-03`) rather than planning from scratch.
- **Cost-aware planning** — planning the *reasoning budget* itself (how many calls a task
  merits) as an explicit plan field, feeding `RFC-0029`.
- **Machine-checked criteria** — a linter that verifies every `success_criteria` entry maps to
  at least one Evaluation gate or rubric item before the plan is accepted.

---

*RFC-0008 is consistent with `CANON-001`: plans are explicit, testable commitments (§9 Stage 3)
owned and acted upon solely by Decision Intelligence (`ADR-0008`); the `PlanValidator` enforces
the dependency graph (§3), rollback and test standards (§4), and the risk-tier approval matrix
including the Tier 0/PCI two-approval rule with Security Engineering (§7) before any execution.*
