## 1. Summary

This RFC specifies the **Execution Runtime** — the component of the Enterprise Cognitive Layer
(ECL) through which an Enterprise AI Worker *acts on Meridian Commerce Group (MCG)*. Where
Decision Intelligence (`ARCH-06`) decides and plans, the Execution Runtime **carries out** a
plan's directives against real MCG systems — GitHub, CI, TestRail, Jira — recording the result
as canonical, provenanced artifacts. It normatively owns `sdk.execution.ExecutionRuntime`,
`execution_object.schema.json`, and `worker_artifact.schema.json`.

The contract is deliberately narrow: `execute_step(plan, step)` runs exactly one directive of a
`PLAN-###`, invoking tools that leave the same trail a human engineer would (`CANON-001` §9.1) —
`PR-####`, `TR-####`, Jira comments, incident actions. Every step is **idempotent** (`ADR-0045`)
so retries are safe even on Tier 0; every tool call runs under least-privilege scope
(`ADR-0042`); every artifact is a `WorkerArtifact` addressable by canonical `ref` and `uri`. The
runtime never *decides* — Decision Intelligence remains the sole orchestrator (`ADR-0008`).

## 2. Motivation

`CANON-001` §9 makes **Execution** Stage 4 of the Enterprise Worker lifecycle, and `ARCH-07`
marks it *cross-cutting*: the Worker acting through real tools rather than a layer of the ECL.
That framing creates three obligations this RFC discharges.

- **A real trail, not a simulation.** `CANON-001` §9.1 requires Workers to use the same
  artifacts as engineers. Execution must produce genuine `PR-0312` / `TR-0442` / Jira records —
  canonical and diffable — or nothing is benchmarkable.
- **Safety under retry.** Distributed tool calls fail and are re-driven; on a Tier 0 service
  like Checkout (`APP-003`, `mcg-checkout-service`) a double-applied side effect is an incident.
  Execution needs a first-class idempotency contract (`ADR-0045`).
- **A clean seam to Evaluation, Learning, and Replay.** Evaluation (`RFC-0014`) scores what
  Execution produced, the Replay Engine (`RFC-0024`) reconstructs a run, and audit (`RFC-0023`)
  traces it — all depending on a stable, provenanced object.

Without one owned contract, each Worker type reinvents tool wiring and the "same tools as
engineers" invariant erodes into per-Worker glue.

## 3. Guide-level explanation

### 3.1 What the Execution Runtime is

The Execution Runtime is the thin, auditable executor between a plan and the enterprise: DI
hands it directives, it invokes tools, it returns a record. It holds **no agency and no
memory** — choosing the next step, replanning, and judging the work belong to DI (`ADR-0008`)
and Evaluation (`ARCH-04`). Concentrating action but not judgment keeps behavior legible.

### 3.2 The running example

Consider `PLAN-0072`, DI's plan for the guest-checkout story `CHK-1421` on `APP-003`
(`ARCH-06`, Example A; `ARCH-07`, Example A), executed one step at a time: step 2 implements the
guest path and guards `APP-015` provisioning (`repo`); step 3 adds `GuestNoLoyaltyTest`
(`repo`); step 4 runs unit + contract tests (`ci` → `testrail`, yielding `TR-0442`/`TR-0443`);
step 5 opens `PR-0312` and comments on `CHK-1421` (`github` / `jira`). On a failed gate or SLO
breach, `rollback(PLAN-0072)` disables the guest-checkout feature flag (§4.7).

### 3.3 The one-step contract

Each `execute_step(plan, step)` does four things only: (1) reads the step's directives from the
`PLAN-###`; (2) resolves and invokes the step's tool (resolution governed by `RFC-0013`); (3)
collects the resulting `WorkerArtifact`s; (4) returns an `ExecutionObject` with status
`succeeded`, `partial`, or `failed`. DI drives the loop by issuing steps in order and reading
each status; the runtime never advances itself.

## 4. Reference-level explanation

### 4.1 Owned contracts

RFC-0012 normatively owns, per the `RFC-0001` §4.6 map: `sdk.execution.ExecutionRuntime`
(`execute_step`, `rollback`, `artifacts`); `execution_object.schema.json` (the `ExecutionObject`
record); and `worker_artifact.schema.json` (the `WorkerArtifact` record).
`sdk.execution.Tool`, `ToolRegistry`, and `ToolSpec` are cited here but **owned by `RFC-0013`**;
this RFC treats a resolved `Tool` as a given.

### 4.2 Directives drive `execute_step`

`sdk.execution.ExecutionRuntime.execute_step(plan, step)` accepts a `PlanningObject`
(`planning_object.schema.json`, owned by `RFC-0008`) and a zero-based `step` index. It reads
`plan.steps[step]` — carrying the `action`, `tool` name, and any `expect` clause (`ARCH-06`,
Example A) — maps it to a tool invocation, and returns an `ExecutionObject` whose `plan`,
`step`, and `tool` echo the directive, whose `directives` capture the resolved arguments, and
whose `artifacts`/`status` capture the outcome. Because DI is the sole orchestrator
(`ADR-0008`), the runtime rejects any step whose `tool` is not granted under `RFC-0013`.

### 4.3 The tool invocation protocol

A resolved tool implements `sdk.execution.Tool`: it exposes a `ToolSpec` and a single
`invoke(args) -> ToolResult`. The runtime builds `args` from the step's directives; `args`
**must** validate against `ToolSpec.input_schema` (a JSON Schema) *before* invocation, and a
validation failure yields an `ExecutionObject` with `status = failed` and a populated `error`
without the side-effecting call ever being made. `Tool.invoke(args)` returns a `ToolResult`
(`ok`, `output`, `artifacts`, `error`); the runtime lifts `ToolResult.artifacts` into
`ExecutionObject.artifacts` and sets `status` from `ok` and the step's `expect` clause —
`succeeded` when the tool succeeds and expectations hold, `partial` when the action landed but
an expectation did not (e.g. `TR-0443` red), `failed` when `ok` is false. The runtime does no
provider-specific work: reasoning goes through the Model Gateway (`RFC-0011`), tool selection
through the registry (`RFC-0013`).

### 4.4 Idempotency (`ADR-0045`)

Every `execute_step` runs under an **idempotency key** derived from run identity and step
(`run_id:step`), passed to the tool so a re-driven step is a no-op-with-same-result rather than
a duplicate side effect — the discipline `KN-052` mandates for the checkout path. Re-running
step 5 does not open a second PR, it reconciles to `PR-0312`; re-running step 4 re-attaches
`TR-0442`/`TR-0443` rather than spawning new runs. This makes retry safe on Tier 0, where
`execute_step` must be replayable without a human. Tools whose `ToolSpec.side_effects` is
`irreversible` cannot be made idempotent by key alone and fall under the stricter gating in
`RFC-0013`.

### 4.5 Artifacts as canonical `WorkerArtifact`s

Each `WorkerArtifact` (`worker_artifact.schema.json`) carries an `artifact_type`
(`pull_request | test_run | comment | file | incident_action | commit`), a canonical `ref`
(`PR-0312`, `TR-0442`), a resolvable `uri`, and the ECL object base. `ref` follows `CANON-001`
§6 so a `PR-####` or `TR-####` resolves identically wherever cited — `EVAL-0061` scoring
`PR-0312`, `REF-0019` reflecting on it. This is the referential-integrity backbone (`ADR-0023`,
`RFC-0022`): Execution *produces* the IDs the rest of the loop consumes.

### 4.6 Status feeds Evaluation

`ExecutionObject.status` is the seam to Evaluation (`RFC-0014`): `EvaluationObject.execution`
points at the execution, and objective gates re-check the real `TR-0442`/`TR-0443` outcomes and
the `APP-003 → APP-015` dependency rule. A `partial` status is not a verdict but Evaluation's
*input*; DI acts on Evaluation's verdict, not Execution's status.

### 4.7 Rollback

`rollback(plan)` invokes the plan's declared `PlanningObject.rollback` strategy and returns an
`ExecutionObject` recording the reverting action. For `PLAN-0072` the strategy is *disable the
guest-checkout feature flag* — a reversible `write` action, not a code revert, so recovery needs
no schema down-migration (`CANON-001` §7.4). Rollback is itself idempotent. DI (not the runtime)
decides to call it on a failed gate or SLO breach; the runtime executes it and records the
`incident_action` artifact.

### 4.8 Identity and provenance for replay

`sdk.execution.ExecutionRuntime.artifacts(run_id)` returns every `WorkerArtifact` produced
during a run. When execution is scoped to a concrete Worker run, the record is a
`WorkerExecution` (`worker_execution.schema.json`), adding `worker` and `run_id` to the
`ExecutionObject` base. Together these give each action a stable identity — *which Worker, run,
step, tool, and artifacts* — exactly what the Replay Engine (`RFC-0024`) needs to reconstruct a
run and what the decision trace (`RFC-0023`) needs to bind Execution into the audit record.

## 5. Drawbacks

- **One-step granularity is chatty.** Step-by-step execution is more round trips than a
  whole-plan call and pushes loop control onto DI — deliberate, but it costs overhead.
- **Idempotency is only as good as the tool.** The runtime supplies a key, but a tool that
  ignores it (or an `irreversible` action) can still double-apply; risk shifts to
  `ToolSpec.side_effects` honesty (`RFC-0013`).
- **Rollback is plan-declared, not automatic.** A weak `PlanningObject.rollback` strategy (e.g.
  "manual revert") cannot be improved by the runtime; it executes only what the plan declared.

## 6. Rationale & alternatives

Making the runtime a *pure executor* — action without agency — follows from `ADR-0008`: if
Execution could decide, there would be two orchestrators and the audit story would fracture.
Idempotency by key (`ADR-0045`) beats "detect and compensate" because compensation on a Tier 0
revenue path is itself risky. Alternatives considered:

- **Whole-plan execution (`execute(plan)`).** Rejected: it hides per-step status and prevents DI
  from interleaving re-retrieval or replanning between steps (`ARCH-06`).
- **Runtime-owned retries.** Rejected: retry-vs-escalate is a *decision* belonging to DI's
  confidence-gated control, not the executor.
- **Free-form artifact blobs.** Rejected: without canonical `ref`/`uri`
  (`worker_artifact.schema.json`) the integrity Evaluation, Replay, and audit rely on collapses
  (`ADR-0023`).

## 7. Prior art

Generic, non-proprietary prior art only: the **idempotency-key** pattern of payment and REST
APIs (a client key that dedupes retried mutations); **saga / compensating-action** patterns for
reversible workflows; the **tool-calling / function-calling** convention in agent frameworks (a
declared schema, validated arguments, a structured result); and infrastructure-as-code
**plan/apply** separation. No proprietary internal tool or runtime is referenced.

## 8. Unresolved questions

- Should `partial` be a single status or graded (which expectation failed) to give Evaluation
  richer input? Leaning single, with detail in `metadata`.
- For multi-tool steps (open PR *and* comment on `CHK-1421`), is the atomic unit the step or the
  tool call? Current reading: the step succeeds only if all its tool calls do; partial-failure
  semantics deferred to `RFC-0024`.
- What is the retention floor for `artifacts(run_id)` on Tier 0 runs to serve Replay
  (`RFC-0024`)? Deferred to `RFC-0028`.

## 9. Future possibilities

- **Dry-run execution.** A `plan`-only mode validating every step's `args` against each
  `ToolSpec.input_schema` and reporting side-effect classes without invoking, feeding a
  pre-flight confidence signal to DI.
- **Transactional multi-step groups** with group-level compensation, for changes that must land
  or revert together across `mcg-*` repos.
