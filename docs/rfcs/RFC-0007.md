## 1. Summary

This RFC specifies the **Decision Intelligence (DI) control loop** — the single orchestration
cycle that every Enterprise AI Worker runs to turn a task trigger into completed, evaluated
work. It normatively owns `sdk.decision.Orchestrator` and the `worker_decision.schema.json`
contract. It defines how a trigger is interpreted into a `TaskIntent`; how DI sequences the
loop **Interpret → Plan → Route → Reason → Act → Evaluate → Decide**; how each turn of the
loop emits an immutable `DecisionObject` carrying a fused confidence, a rationale, and the
per-layer confidences it fused; and how those decisions accumulate into the mandatory decision
trace (`ADR-0021`). DI is the *only* layer with agency (`ADR-0008`); this RFC draws the
boundaries where DI delegates — planning to `RFC-0008`, confidence math to `RFC-0009`, model
selection to `RFC-0010`, execution to `RFC-0012`, evaluation to `RFC-0014`, and policy
enforcement to `RFC-0030`.

## 2. Motivation

`ARCH-06` establishes DI as the executive function of the ECL: "the Context Layer assembles,
the Knowledge Layer knows, the Evaluation Layer judges, the Learning Engine improves — but DI
**chooses**." `ADR-0008` makes that concentration of agency an invariant. The reason is
benchmarkability: if agency were diffuse — Context deciding to re-retrieve on its own, or
Execution deciding to escalate — Worker behavior would be neither auditable nor reproducible,
and EnterpriseSim a demo rather than a benchmark.

A single orchestrator is worth little without a *disciplined* loop. Three failure modes from
`ARCH-06` motivate the precision here: **overconfident autonomy** (acting on a bad plan),
**analysis paralysis** (endless re-retrieval that never acts), and **opaque decisions**
(behavior no one can explain). This RFC closes all three by making every control decision a
typed `Control` value produced from an explicit fused confidence, bounded by iteration and
reasoning budgets, and recorded on an immutable trace.

## 3. Guide-level explanation

### 3.1 Interpreting the trigger

A run begins when DI receives a task trigger — a canonical ID such as the Jira story
`CHK-1421` (guest checkout, `APP-003`, Tier 0) — plus a small `context_hint`.
`Orchestrator.interpret(trigger, context_hint)` produces a `TaskIntent`: the structured goal,
constraints, and success criteria that drive everything downstream. The intent is what the
Context Layer (`RFC-0002`) retrieves against and what the Planner (`RFC-0008`) plans toward.
Interpretation is where a raw enterprise artifact becomes a machine-actionable objective; it
performs no work and commits to nothing.

### 3.2 The loop

Every task traverses one cycle, mirroring the `ARCH-06` lifecycle:

- **Interpret** — trigger → `TaskIntent` (§3.1).
- **Plan** — the Planner produces a `PLAN-###` (`RFC-0008`); for `CHK-1421`, `PLAN-0072`
  (risk_tier 0, `applied_experience: [EXP-090]`, routing `high-reasoning`).
- **Route** — DI asks the Model Router (`RFC-0010`) for a model class matching plan difficulty;
  the Router speaks only to the Gateway (`RFC-0011`), so no vendor detail enters DI.
- **Reason** — the routed model reasons over the assembled `CTX-0118` to produce directives.
- **Act** — the Execution Runtime (`RFC-0012`) carries out one plan step through least-privilege
  tools (`ADR-0042`), producing artifacts (`PR-0312`, test runs).
- **Evaluate** — the Evaluation Layer (`RFC-0014`) scores the execution, returning an
  `EvaluationObject` (`EVAL-0061`, 0.91) with a verdict and a judgment confidence.
- **Decide** — `Orchestrator.decide(plan, context, evaluation)` fuses the layer confidences and
  emits a `DecisionObject` whose `choice` is a `Control` value (`proceed`, `re-retrieve`,
  `replan`, `retry`, `escalate`, `abort`). `proceed` advances a step or (if criteria are met)
  concludes; `re-retrieve`/`replan`/`retry` loop back; `escalate`/`abort` end the run.

### 3.3 Policy is a hard gate, not a vote

Before any `Act`, DI consults the `PolicyGuard` (`RFC-0030`). A `PolicyVerdict` with
`allowed = false` stops execution *regardless of confidence* — a high-confidence plan lacking
the two approvals a Tier 0 or PCI change requires (`CANON-001` §7) does not proceed. This is
`ADR-0041`: policy is enforced before execution and can only ever subtract autonomy.

## 4. Reference-level explanation

### 4.1 `sdk.decision.Orchestrator`

This RFC owns the `Orchestrator` abstract base class in `sdk/decision/interfaces.py`. It has
exactly three methods, and their narrowness is deliberate — DI orchestrates, it does not
implement the layers it sequences:

- `interpret(trigger, context_hint) -> TaskIntent` — turns a trigger into intent. `TaskIntent`
  is owned by `sdk.context` (`RFC-0002`); DI produces it, the Context Layer consumes it.
- `decide(plan, context, evaluation) -> DecisionObject` — the heart of the loop. `evaluation`
  is `None` on the first turn (nothing executed to judge yet) and populated thereafter.
- `trace(run_id) -> Sequence[DecisionObject]` — the run's immutable decision trace in order
  (`ADR-0021`, §4.4).

The Planner (`Planner.plan`/`replan`) and confidence combiner (`ConfidencePolicy.fuse`/
`control_for`) are separate SDK contracts DI *calls*; it does not subclass them.

### 4.2 Producing a decision

`decide` performs a fixed, inspectable computation. It gathers per-layer confidences into the
`inputs` map — context coverage from `ContextObject.coverage_confidence` (`ARCH-01`), knowledge
authority, experience applicability, and (when present) the evaluation's `judgment_confidence`
(`ARCH-04`, `ADR-0017`; DI consumes **judgment** confidence, not the raw score — normative in
`RFC-0009`). It calls `ConfidencePolicy.fuse(inputs) -> Confidence` for the single
`fused_confidence`, then `control_for(fused, plan.risk_tier) -> Control` for the risk-adaptive
autonomy decision (both owned by `RFC-0009`; DI treats them as a black box). It intersects the
result with the `PolicyGuard.check(plan, context)` verdict — a disallowed verdict forces
`escalate` (or `abort` where no human path exists), never `proceed` (`ADR-0041`) — and emits
the `DecisionObject` with `choice`, `rationale`, `fused_confidence`, and `inputs`.

### 4.3 The `DecisionObject` / `WorkerDecision` contract

Per `sdk.objects.DecisionObject` and `decision_object.schema.json`, every decision carries
`plan` (the `PLAN-###` it concerns), `choice` (one of the six `Control` strings — the schema
`enum` and the `Control` enum are the same set), `rationale` (non-empty), `fused_confidence`,
and the `inputs` map of per-layer confidences. An optional `policy_verdict` records a guardrail
outcome.

When emitted onto a concrete Worker run's trace it is a **`WorkerDecision`**
(`worker_decision.schema.json`, owned here): it adds `worker` (the Worker type, e.g.
`checkout-feature-worker`) and `trace_seq`, a monotonic position in the run's trace.
`WorkerDecision` mirrors `DecisionObject` field-for-field — the trace is the decisions
themselves, not a lossy summary.

### 4.4 The decision trace (immutable, mandatory)

`ADR-0021` requires that every choice be recorded. The trace is the ordered sequence of
`WorkerDecision`s for a `run_id`, each with a strictly increasing `trace_seq` from 0. It is
**append-only and immutable**: a superseded decision is never edited or deleted; a later turn
appends a new decision referencing the same `plan`. This makes a run replayable (`RFC-0024`)
and auditable, and is the primary input to Reflection (`ARCH-05`, `RFC-0016`). A run with an
execution but no decision explaining it is a defect.

### 4.5 Stop conditions and budgets

DI must terminate. The loop halts on **success** (all `success_criteria` met and the latest
verdict `pass`; DI emits a final `proceed`), on **escalation/abort** (a `Control` of `escalate`
to a human or `abort`), on **iteration-budget exhaustion** (a bounded number of loop turns and
reasoning budget of calls/tokens — on exhaustion DI escalates rather than looping forever, the
direct mitigation for *analysis paralysis*), or on **diminishing returns** (successive
`re-retrieve`/`replan` turns that do not raise `fused_confidence`). The *values* of these
budgets and their cost accounting are deferred to `RFC-0029`; this RFC mandates only that the
budgets exist and that exhaustion escalates.

### 4.6 Delegation boundaries

DI holds agency but not implementation. It **delegates**: planning and validation to
`sdk.planner` (`RFC-0008`); the confidence combiner and thresholds to `sdk.decision.ConfidencePolicy`
(`RFC-0009`); model selection to `sdk.models.ModelRouter` (`RFC-0010`) and provider access to
the Gateway (`RFC-0011`); tool invocation to `sdk.execution.ExecutionRuntime` (`RFC-0012`);
scoring to `sdk.evaluation.Evaluator` (`RFC-0014`); and guardrails to the `PolicyGuard`
(`RFC-0030`). Keeping these behind stable contracts is what keeps DI model- and domain-agnostic:
the same `Orchestrator` drives a Checkout feature Worker and a Recruitment Worker, differing
only in intent, tools, policies, and rubrics (`ARCH-06` Example C).

### 4.8 Example B — confidence-gated control

`ARCH-06` Example B runs on this loop. Mid-task, `Evaluate` returns `partial` on the
contract-test step (a fail against Payments `APP-012`). DI's `decide` fuses the lowered inputs;
`control_for` returns `re-retrieve`. The Context Layer adds the payments idempotency knowledge
(`KN-052`) and re-composes `CTX-0118`; `decide` next returns `replan`, and the Planner emits a
successor plan preserving lineage (`RFC-0008`). Only when re-evaluation lifts `fused_confidence`
back to *high* does `control_for` return `proceed` and DI open the PR. Each of these turns is a
separate `WorkerDecision` on the trace. Critically: had confidence stayed low on this
**PCI-adjacent, Tier 0** change, `control_for` (tighter thresholds for Tier 0/PCI, `RFC-0009`)
would return `escalate`, and DI would hand to a human rather than act — the safety backbone of
`ADR-0014`. **DI never takes a high-stakes action at low fused confidence.**

## 5. Drawbacks

- **Serialization cost.** One inspectable loop with a decision per turn is slower and chattier
  than an opaque single model call; the trace and budgets add overhead (bounded by `RFC-0029`).
- **Concentration risk.** As the sole agent, a loop defect affects every Worker type; mitigated
  by the narrow three-method contract and heavy delegation.
- **Rigidity.** The fixed loop can feel heavy for trivial Tier 3 tasks; `control_for`'s looser
  low-tier thresholds (`RFC-0009`) partly offset this.

## 6. Rationale & alternatives

- **Diffuse agency** (each layer self-directs) — rejected by `ADR-0008`: unauditable,
  unbenchmarkable, and prone to conflicting control decisions.
- **Confidence as advisory, not gating** — rejected by `ADR-0014`: advisory confidence permits
  overconfident autonomy, the top failure mode in `ARCH-06`.
- **Implicit trace (logs only)** — rejected by `ADR-0021`: logs are lossy and mutable; the ECL
  requires typed, immutable decisions for replay (`RFC-0024`) and reflection (`RFC-0016`).
- **DI owning routing/scoring directly** — rejected: it would leak provider and rubric specifics
  into the orchestrator, breaking model- and domain-agnosticism (`ARCH-07`).

## 7. Prior art

Generic, non-proprietary inspirations: the classic **sense–plan–act** control cycle and the
**OODA loop** (observe–orient–decide–act) as framings for iterated decision-making under
uncertainty; and **hierarchical / supervisory control**, where one controller sequences
specialized subsystems behind stable interfaces. The explicit, append-only decision log echoes
event-sourcing practice. No proprietary orchestration framework is referenced or reproduced.

## 8. Unresolved questions

- Should `interpret` emit its own trace entry (an "intent decision"), or is that provenance
  better carried by `RFC-0023`?
- What is the right default iteration budget per risk tier before escalation, and should it be
  learned (`ARCH-05`) rather than fixed? Deferred to `RFC-0029`.
- How should multi-Worker orchestration (`ARCH-06` future) interleave two Workers' traces under
  one `run_id` while preserving per-decision attribution?

## 9. Future possibilities

- **Learned control policies** — the Learning Engine tunes `control_for` thresholds per task
  type from historical control-decision accuracy (`ARCH-06` signals).
- **Playbook fast-paths** — recognizing a recurring situation and invoking a validated
  experience-cluster playbook (`ARCH-03`) instead of planning from scratch, collapsing turns.
- **Speculative routing** — issuing a cheap-model and a high-reasoning attempt in parallel, then
  deciding on evaluated results, as a cost/latency optimization under `RFC-0029`.

---

*RFC-0007 is consistent with `CANON-001`: it concentrates agency in Decision Intelligence
(`ADR-0008`), gates autonomy on fused confidence with risk-adaptive thresholds (`ADR-0014`),
enforces policy before execution including the Tier 0/PCI two-approval rule (`CANON-001` §7,
`ADR-0041`), and records every choice on an immutable decision trace (`ADR-0021`).*
