# ADR-0048: Benchmark Reproducibility Is Mandatory

- Status: Accepted
- Date: 2026-06-23
- Deciders: Architecture Office (TEAM-090)
- Related: ADR-0037, ADR-0018, ADR-0015, ADR-0016, ADR-0032, RFC-0025, RFC-0026

## Context

EnterpriseSim is "The Open Benchmark for Enterprise AI Workers" (CANON-001). A benchmark whose
results cannot be reproduced is not a benchmark — it is an anecdote. The project's entire value
proposition is running the *identical* task suite against different providers and Worker
implementations and comparing them fairly (ARCH-07). That fairness collapses if any input drifts
silently between runs: a changed rubric (the **benchmark drift** failure in ARCH-07), an updated
dataset, a different schema version, or an unrecorded model configuration. Reproducibility is
also what lets the community trust and independently verify published comparisons.

## Decision

We will make **benchmark reproducibility mandatory**, per RFC-0025 and RFC-0026. Every benchmark
run pins and records the full set of inputs required to reproduce it:

- **Task suite version** and dataset version (immutable, content-addressed where possible).
- **Rubric version** — rubrics are versioned (ADR-0018) so a score always states which criteria
  produced it; scores are objective-first (ADR-0015) and never issued without evidence
  (ADR-0016).
- **SDK and schema versions** (SemVer, ADR-0032) so the contract shape is fixed.
- **Model routing configuration** and provider/model identifiers, and the **deterministic replay
  record** (ADR-0037) — captured transcripts, seeds and sampling parameters — so a run can be
  re-executed exactly, not just re-sampled.
- The result record cites all of the above by ID; a result with an unpinned input is invalid.

## Consequences

- Positive: fair, verifiable cross-provider and cross-Worker comparison — the core purpose of
  EnterpriseSim; third parties can independently reproduce published results.
- Positive: regressions and improvements are attributable to a specific changed input (rubric,
  dataset, SDK, or model), because everything else is pinned; the flywheel's improvement trend
  (ADR-0034) is measured on stable footing.
- Negative: pinning overhead — every benchmark artifact must be versioned and retained, and
  replay records consume storage (ADR-0037) and carry classification (ADR-0043).
- Negative: true bit-for-bit reproducibility is bounded by provider nondeterminism; where a
  provider will not honor seeds, reproducibility rests on replayed transcripts, which reproduce
  the observed run rather than a fresh independent sample — this limitation must be stated with
  results.
- Neutral: reproducibility requirements make ad-hoc "quick benchmark" runs heavier, which is an
  intentional trade against the risk of unreproducible claims.
