# ADR-0050: Canon Supremacy — Changes via ADR Only

- Status: Accepted
- Date: 2026-07-07
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §10, ADR-0001, ADR-0033, ADR-0036, ADR-0049

## Context

EnterpriseSim's coherence depends on a single, stable source of enterprise truth: CANON-001. It
defines MCG, the engineering organization, the application landscape and dependency graph, the
naming and ID conventions, and the Enterprise Worker lifecycle. Every artifact in the repository
— architecture docs, schemas, the SDK, Jira issues, PRs, incidents, knowledge and experience —
must remain consistent with it, and CANON-001 already states that when any generated artifact
conflicts with canon, canon wins, and that changes to canon are versioned in its change log.

For that guarantee to hold operationally, there must be exactly one governed path to change an
invariant, and it must be recorded. Otherwise canon erodes through undocumented drift and the
whole benchmark loses its fixed reference frame. This ADR makes the governance explicit and
closes the ADR series (ADR-0001…ADR-0050) on the principle that established it.

## Decision

We will treat **CANON-001 as supreme**, and require that any change to a canonical invariant be
made **only via an Architecture Decision Record**:

- CANON-001 is authoritative; no document (including the ECL architecture, schemas or SDK) may
  contradict it. On conflict, canon wins until an ADR changes canon.
- A change to a canonical invariant — an ID/naming convention, the dependency graph, an
  architecture principle, a lifecycle stage, the license or synthetic-only rule (ADR-0049) —
  requires an accepted ADR, authored by the Architecture Office (TEAM-090), recorded in this
  series and reflected in the CANON-001 change log with a version bump.
- Contract changes (schemas, SDK) go through RFCs (RFC-0021 and others); where a contract change
  *also* alters an invariant, it additionally requires an ADR — consistent with the schema
  migration policy (ADR-0033) and the governed-promotion rule (ADR-0036).
- ADRs are immutable once accepted (ADR-0001); a decision is changed by a new, superseding ADR
  that references the one it replaces, never by editing history.

## Consequences

- Positive: a stable, versioned reference frame for the entire project; every change to truth is
  traceable to a dated, reasoned decision; the benchmark's foundation cannot drift silently.
- Positive: consistency is enforceable — reviewers and Workers can point to canon and the ADR
  series as the authority, and referential integrity (ADR-0023) is protected across change.
- Negative: rigidity and latency — even a good change to an invariant must wait on the ADR
  process; this is a deliberate trade of speed for stability at the canonical layer, while
  trunk-based development (ADR-0031) keeps non-invariant work fast.
- Negative: the Architecture Office is a governance bottleneck by design; its throughput bounds
  how fast canon can evolve.
- Neutral: this closes the foundational ADR set; future ADRs (ADR-0051+) extend it under the
  very rule this ADR establishes.
