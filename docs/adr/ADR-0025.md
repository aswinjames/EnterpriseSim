# ADR-0025: Four Specialization Axes (Knowledge, Tools, Rubrics, Policies)

- Status: Accepted
- Date: 2026-03-30
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §9, ARCH-07, ADR-0024, ADR-0018, ADR-0042

## Context

Given that Workers are domain-agnostic over a shared core (`ADR-0024`), we need a *precise*
definition of what a Worker type is allowed to change. If specialization is open-ended — "a
Worker can override anything" — then domain-specific behavior leaks back into the core, the
reusability guarantee erodes, and Workers drift toward being bespoke systems again. The
extension surface must be small, complete enough to express any real Worker type, and mapped
cleanly onto the layers that consume it.

We must decide *exactly* how a Worker specializes the ECL.

## Decision

We will define **exactly four specialization axes**, and no others, that a `WorkerSpec` binds
to the shared core:

1. **Knowledge domains** — which `KN-###` corpora are in scope (consumed by Knowledge/Context).
2. **Tools** — which enterprise tools the Worker may act through (consumed by the Execution
   Runtime; scoped by least-privilege, `ADR-0042`).
3. **Rubrics** — the task-type scoring criteria (consumed by Evaluation; versioned, `ADR-0018`).
4. **Policies** — the guardrails that gate autonomy (PCI vs. bias/fairness vs. segregation-of-
   duties; consumed by Decision Intelligence's confidence/policy gate, `ADR-0014`).

Everything else — context assembly, experience accumulation, reflection, learning, confidence
fusion, orchestration, model routing — stays identical and is *not* a specialization point. A
new Worker type adds specializations along these four axes only.

## Consequences

- **Positive.** The extension surface is small, explicit and enforceable, so the shared core
  stays domain-free and the "new Worker in a day" promise holds: register knowledge, grant
  tools, define a rubric, set policies — done (the Support Worker example in `ARCH-07`).
- **Positive.** Each axis maps to exactly one consuming concern, so specializations compose
  cleanly and can be reviewed independently (security reviews tools+policies; QE reviews
  rubrics; knowledge owners review domains).
- **Negative.** A Worker whose real need does not fit these four axes cannot be built without an
  architectural change (a new ADR) — deliberately, to prevent scope creep in the extension
  surface. The bet is that four axes are sufficient for enterprise Worker types.
- **Neutral.** The axes are orthogonal: changing a rubric never touches tool grants, changing
  knowledge scope never touches policy — which keeps specialization reasoning tractable.
