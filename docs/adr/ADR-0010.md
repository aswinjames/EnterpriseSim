# ADR-0010: Model-Agnostic by Structural Invariant

- Status: Accepted
- Date: 2026-02-05
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §8 (principle 9), ARCH-07, ADR-0002, ADR-0003, ADR-0009, ADR-0011, ADR-0012

## Context

Model-agnosticism is the core value proposition of EnterpriseSim: the ability to run the
*identical* task suite against different providers and Worker implementations and compare them
fairly. Many systems claim to be model-agnostic but enforce it only by discipline — a code
review norm that "don't couple to a provider" — which erodes the moment a deadline meets a
convenient provider-specific feature. Aspirational agnosticism is not benchmarkable; a leaked
assumption silently biases every comparison thereafter.

We must decide whether model-agnosticism is a *goal we pursue* or an *invariant we structurally
guarantee*.

## Decision

We will make the ECL model-agnostic **by structural invariant**, guaranteed by four mechanisms
acting together, not by discipline:

1. **Single point of contact** — every model call goes through the Model Gateway (`ADR-0009`);
   only it imports provider SDKs.
2. **Stable internal contract** — layers exchange structured context objects and normalized
   results (`ADR-0011`), never provider prompt strings; the Gateway renders and normalizes.
3. **Capability negotiation, not assumption** — DI and Context adapt to per-model capability
   descriptors (`ADR-0012`) rather than hard-coding any provider's behavior.
4. **Learning lives outside the model** (`ADR-0003`) — improvement is data, so the same
   accumulated intelligence works with any model.

No component may depend on a specific provider. This is verifiable: a dependency check that
finds a provider SDK imported outside the Gateway is a build-breaking violation.

## Consequences

- **Positive.** Fair, apples-to-apples benchmarking across providers is possible because the
  *only* thing that changes between runs is the model behind the Gateway. This is the project's
  central purpose (`ARCH-04`, `ARCH-07`).
- **Positive.** Vendor independence is deep: the organization's competence is portable across
  providers and survives provider outages via routing and a local-SLM floor.
- **Negative.** The ECL cannot opportunistically exploit a provider's unique, non-portable
  feature in a layer; such features are usable only if the Gateway can expose them through a
  capability-negotiated, normalized contract, which is more work.
- **Neutral.** The invariant is testable and thus enforceable in CI, turning a design intent
  into a checked property.
