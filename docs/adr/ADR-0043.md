# ADR-0043: Sensitivity Classification Travels With Data

- Status: Accepted
- Date: 2026-05-19
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §4.6, ADR-0041, ADR-0042, ADR-0020, RFC-0030

## Context

The ECL moves data across layers: Knowledge is retrieved into Context, Context is rendered into
model prompts at the Gateway, execution reads enterprise state, and everything is captured for
provenance (ADR-0020) and replay (ADR-0037). Some of that data is sensitive — PCI cardholder
data (isolated to APP-012's boundary, CANON-001 §4.6), PII from the identity service (APP-014),
customer and payment records. If sensitivity is a property checked only at the origin, it is
lost the moment data is copied into a `ContextObject`, a prompt, a signal, or a replay record —
and the policy engine (ADR-0041) has nothing to enforce against downstream.

Classification must be an attribute of the data itself, propagated with it, so that every layer
and every tool can make a correct policy decision wherever the data flows.

## Decision

We will require **sensitivity classification to travel with data** through the ECL, per
RFC-0030:

- Knowledge, Context, Experience, execution, signal and replay objects carry a sensitivity
  classification (e.g. public / internal / confidential / PCI / PII), recorded in-band.
- When data flows into a derived object — knowledge into a `ContextObject`, context into a model
  render, an artifact into a replay record — the classification propagates to (or raises) the
  derived object's classification; a derived object is at least as sensitive as its most
  sensitive input.
- Policy enforcement (ADR-0041) and least-privilege tool access (ADR-0042) key off the traveling
  classification: a tool or provider not authorized for a class cannot receive data of that
  class, and the Gateway will not render restricted data into an egress prompt for an
  unauthorized provider.
- Provenance (ADR-0020) records the classification lineage so audits can prove sensitive data
  never crossed a boundary it should not have.

## Consequences

- Positive: policy can be enforced *wherever* data flows, not only at origin; PCI/PII boundaries
  hold across context assembly, model egress, signals and replay — a precondition for operating
  Workers on real-shaped enterprise data.
- Positive: makes model-provider egress decisions safe — restricted data can be confined to
  approved providers or the local SLM (ADR-0044).
- Negative: labeling burden — every source must classify correctly, and mis-labeling at origin
  propagates a wrong (often too-permissive) label downstream; classification quality is now a
  first-class data-quality concern.
- Negative: conservative propagation (max of inputs) can over-classify derived objects,
  restricting them more than strictly necessary and adding handling friction.
- Neutral: EnterpriseSim's content is synthetic (ADR-0049), so classifications here model the
  discipline rather than protecting real data — but the mechanism is exactly what a real
  deployment requires.
