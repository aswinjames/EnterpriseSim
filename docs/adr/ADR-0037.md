# ADR-0037: Deterministic Replay for Debuggability and Benchmarking

- Status: Accepted
- Date: 2026-04-07
- Deciders: Architecture Office (TEAM-090)
- Related: ADR-0021, ADR-0020, ADR-0048, ADR-0011, RFC-0024

## Context

EnterpriseSim's core purpose is to benchmark Enterprise AI Workers fairly and to make their
behavior auditable. Both require the ability to reconstruct exactly what happened in a task:
which context was assembled, what plan was formed, what the model was asked and answered, which
tools were called, and why each control decision was made. LLM calls are non-deterministic by
default, and enterprise state (repos, telemetry) moves under the Worker's feet — so "run it
again and see" does not reproduce the original run. Decision traces (ADR-0021) and provenance
(ADR-0020) record *what* happened; we additionally need to *re-execute* a recorded run.

## Decision

We will make ECL task runs **deterministically replayable**, per RFC-0024. The runtime captures,
for every task, a replay record sufficient to reconstruct the run:

- the assembled `ContextObject` (structured, not a prompt string — ADR-0011) and its provenance
  including dropped candidates;
- the `PlanningObject`, all execution directives, and the full decision trace (ADR-0021);
- the normalized model inputs and outputs at the Gateway boundary (recorded transcripts), plus
  routing decisions, seeds and sampling parameters where the provider exposes them;
- tool inputs and outputs, and a pinned snapshot/reference of the enterprise state read.

Replay re-drives the loop against these recorded fixtures rather than live providers and live
state, so the same inputs produce the same trajectory. Model nondeterminism is handled by
replaying recorded transcripts (and, where supported, fixed seeds/temperature=0); irreducible
nondeterminism is surfaced explicitly rather than hidden.

## Consequences

- Positive: bugs in Worker behavior are reproducible and debuggable offline; regressions can be
  bisected; the substrate for reproducible benchmarks (ADR-0048) is provided directly.
- Positive: replay works against any provider because the record is at the Gateway's normalized
  contract (ADR-0011, ADR-0010) — a run captured under one model can be inspected regardless of
  provider availability.
- Negative: capturing full model I/O, tool I/O and state snapshots has real storage cost and
  raises sensitivity concerns — replay records carry classification labels (ADR-0043) and
  retention limits.
- Negative: providers that do not honor seeds still vary on live re-execution; replay leans on
  recorded transcripts, which reproduce the *observed* run, not a fresh sample.
- Neutral: replay fidelity is bounded by capture completeness; the same provenance discipline
  that makes reflection possible (ADR-0035) makes replay possible.
