# ADR-0032: Semantic Versioning for SDK and Schemas

- Status: Accepted
- Date: 2026-03-05
- Deciders: Architecture Office (TEAM-090)
- Related: ADR-0027, ADR-0033, ADR-0031, RFC-0021

## Context

The SDK (`sdk.__version__`) and the schema family (`sdk.SCHEMA_VERSION`, surfaced as each
instance's `schema_version`) are contracts that many independent consumers depend on: Worker
implementations, benchmark harnesses, validators, and other-language ports. Those consumers
need to reason about *whether an upgrade will break them* without reading every diff. Without a
disciplined versioning policy, every change is a potential surprise, and reproducible
benchmarks (ADR-0048) lose their footing because "which version" becomes ambiguous.

## Decision

We will version both the SDK and the schemas with **Semantic Versioning** (`MAJOR.MINOR.PATCH`)
and apply consistent break-classification rules:

- **MAJOR** — backward-incompatible change: removing/renaming a field or interface member,
  tightening a type, making an optional field required, or any change that invalidates a
  previously valid instance or caller.
- **MINOR** — backward-compatible additive change: a new optional field, a new interface with a
  default, a new enum value in an open set.
- **PATCH** — clarifications and fixes with no shape or behavior change.

The schema family carries a parallel version surfaced as `2020-12.vN` in `schema_version`
(ADR-0027); additive/optional changes bump the minor, required-field or type changes bump the
major (schemas README). Validators accept the current and previous major during a migration
window (ADR-0033). Every contract change is recorded via RFC-0021; changes that alter an
invariant additionally require an ADR (ADR-0050).

## Consequences

- Positive: consumers upgrade with predictable risk; a MAJOR bump is an explicit signal to
  read the migration notes; benchmarks can pin exact SDK and schema versions (ADR-0048).
- Positive: aligns with CANON-001 §4.1 release tags (`v<semver>`) and §4.8 API versioning.
- Negative: classifying a change as MINOR vs MAJOR requires judgment; ambiguous cases must
  default to the more conservative (MAJOR) rating to protect consumers.
- Negative: strict SemVer can produce frequent MAJORs in early evolution; the expand-contract
  policy (ADR-0033) reduces this by staging breaking changes over minor releases first.
- Neutral: pre-1.0 semantics (0.y.z) apply during the Foundation Phase, where minor bumps may
  carry breaking changes with explicit notice.
