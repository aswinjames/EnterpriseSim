# ADR-0042: Least-Privilege Tool Access for Workers

- Status: Accepted
- Date: 2026-05-12
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §4.6, ADR-0030, ADR-0041, ADR-0043, RFC-0030

## Context

Execution is where a Worker touches the real enterprise: it writes code, opens PRs, runs tests,
comments on Jira, executes runbook steps (CANON-001 §9.4). The set of tools a Worker can invoke
defines its blast radius. CANON-001 §4.6 already mandates least-privilege workload identity and
mutually-authenticated service-to-service calls for MCG; Workers acting inside that estate must
be held to the same standard. A plugin architecture (ADR-0030) makes it easy to register many
tools — but registration must grant *discoverability*, never automatic authority to act.

A Support Worker has no business holding deploy rights to a Tier 0 payments service; a QA Worker
does not need destructive account actions. Broad, ambient tool access is the largest avoidable
risk in an agentic system.

## Decision

We will grant Workers **least-privilege tool access**, per RFC-0030. A Worker's `WorkerSpec`
(ADR-0030) binds exactly the tools it needs; the `ToolRegistry` scopes each Worker to that set
and no more:

- Tools are one of the four specialization edges (ADR-0025); the execution runtime interface is
  identical across Workers, only the granted tool set differs (ARCH-07).
- Grants are explicit and minimal — a Worker cannot invoke a tool it was not bound, even if the
  tool is registered and discoverable in the runtime.
- Tool invocations are mutually authenticated with least-privilege workload identity (CANON-001
  §4.6), pass pre-execution policy (ADR-0041), and are recorded in the decision trace (ADR-0021)
  and Signals Bus (ADR-0038).
- Sensitivity of the data a tool touches travels with that data (ADR-0043); a tool cannot be
  used to move data across a classification boundary it is not authorized for (e.g. PCI).

## Consequences

- Positive: bounded blast radius — a compromised, buggy, or over-eager Worker can only act
  within its explicit grants; aligns Workers with MCG's least-privilege standard (CANON-001
  §4.6).
- Positive: makes third-party plugins (ADR-0030) safe to load — a malicious tool is inert
  without an explicit grant.
- Negative: friction — standing up a Worker requires deliberately enumerating its tool needs; an
  under-grant blocks legitimate work and forces a grant change.
- Negative: capability negotiation (ADR-0012) and grant management add operational overhead.
- Neutral: grants are auditable and revocable; widening a grant for a Worker class is a governed
  change, informed by escalation and guardrail signals (ADR-0038).
