# ADR-0045: Idempotent Execution and Rollback Plans Required

- Status: Accepted
- Date: 2026-06-02
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §4.8, §7.4, ADR-0041, ADR-0033, ADR-0021

## Context

Workers act through real tools and the loop retries: Decision Intelligence may re-route, replan,
and re-issue directives, and a task may run partially, fail, and resume (ARCH-06). If execution
is not idempotent, a retry double-charges a payment, creates duplicate orders, or re-opens a
resolved case. If a change has no rollback, a bad autonomous action cannot be safely undone
under fire. CANON-001 §4.8 already mandates idempotency keys for MCG APIs, and §7.4 requires
every release to ship a documented rollback plan with backward-compatible, expand-contract
migrations so rollback never needs a schema down-migration. The canonical `PLAN-0072` (ARCH-06,
Example A) carries an explicit feature-flag rollback for exactly this reason.

## Decision

We will require Worker execution to be **idempotent** and every plan to carry a **rollback
plan**:

- Every execution directive that mutates enterprise state uses idempotency keys (CANON-001
  §4.8) so a retry is safe and produces the effect at most once.
- Every `PlanningObject` includes a rollback strategy (ARCH-06) — feature flags preferred, so a
  change reverts by flipping a flag with no schema down-migration (CANON-001 §7.4); schema
  changes follow expand-contract (ADR-0033).
- The presence of a valid rollback plan and idempotency guarantees is a **pre-execution policy
  gate** (ADR-0041): an action that cannot be safely retried or undone is blocked before it
  runs, not discovered after.
- Idempotency keys and the rollback strategy are recorded in the decision trace (ADR-0021).

## Consequences

- Positive: safe retries and safe autonomy — the loop can re-issue directives without corrupting
  state, and any autonomous change can be reverted quickly, which is what makes confidence-gated
  autonomy (ADR-0040) tolerable on Tier 0 systems.
- Positive: aligns Workers with MCG's existing API and release standards (CANON-001 §4.8, §7.4);
  automated rollback on SLO breach applies to Worker-authored changes exactly as to human ones.
- Negative: designing idempotent operations and genuine rollback paths is real engineering
  effort and constrains what a Worker may do — some actions are inherently hard to make
  reversible.
- Negative: feature-flag-based rollback accrues flag debt that must be retired (as under
  trunk-based development, ADR-0031).
- Neutral: irreversible actions are not forbidden outright but require human-in-the-loop
  approval (ADR-0040) and explicit acknowledgement that no rollback exists.
