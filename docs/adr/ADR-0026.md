# ADR-0026: Open Standards Over Proprietary Formats

- Status: Accepted
- Date: 2026-02-03
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §8 (principle 9), ADR-0027, ADR-0038, ADR-0049

## Context

EnterpriseSim must be a durable, publicly reusable benchmark for Enterprise AI Workers. It
models Meridian Commerce Group (MCG) and defines the Enterprise Cognitive Layer (ECL), both
of which exchange artifacts — schemas, API contracts, telemetry, provenance, build metadata
— that outlive any single vendor, tool or model provider. CANON-001 §8 already commits MCG to
open standards (OpenAPI, gRPC/protobuf, OpenTelemetry, CloudEvents, SPDX/SBOM) as an
architecture principle rather than a convenience.

Every proprietary format we adopt is a future migration liability and a barrier to the
project's core purpose: running the *identical* task suite against different providers and
Worker implementations and comparing them fairly (ARCH-07). A format that only one vendor's
tooling can read cannot be a neutral benchmark substrate.

## Decision

We will prefer open, publicly specified standards over proprietary formats for every
externally observable contract in EnterpriseSim and the ECL. Specifically:

- Data contracts use JSON Schema (ADR-0027); REST uses OpenAPI 3.x; RPC uses gRPC/protobuf;
  GraphQL uses SDL — consistent with CANON-001 §4.8.
- Observability uses OpenTelemetry semantics; cross-layer events on the Signals Bus (ADR-0038)
  use a CloudEvents-compatible envelope.
- Supply-chain metadata uses SPDX/SBOM and standard provenance attestations.
- Where a capability has no mature open standard, we adopt the closest open format and isolate
  any proprietary dependency behind an abstract interface (ADR-0029) so it can be swapped.

A proprietary format may be used only when no open standard exists for the capability, the
choice is recorded, and it sits behind an adapter that keeps the rest of the system
standards-native.

## Consequences

- Positive: portability across tools, languages and providers; a benchmark any third party can
  read and reproduce; broad off-the-shelf tooling; reduced lock-in; alignment with CANON-001
  §8 principle 9.
- Positive: reinforces model-agnosticism (ADR-0010) — open contracts do not encode any one
  provider's assumptions.
- Negative: open standards evolve by committee and can lag proprietary features; we sometimes
  trade a richer proprietary capability for a portable, "good enough" open one.
- Negative: we must track standard versions and their validator/tooling support (see the
  Draft 2020-12 validator-availability caveat in ADR-0027).
- Neutral: some standards permit extensions; we confine those to sanctioned extension points
  (e.g. `metadata` in the ECL schemas) so the core stays interoperable.
