# ADR-0024: Workers Are Domain-Agnostic

- Status: Accepted
- Date: 2026-03-26
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §9, ARCH-07, ADR-0025, ADR-0008

## Context

EnterpriseSim must support many Enterprise Worker types — QA, Finance, Privacy, Security,
Recruitment, Support, and future kinds not yet imagined. The naive path is to build each Worker
as a bespoke system with its own context handling, memory, evaluation and orchestration. That
path guarantees divergence: six Workers become six architectures, lessons don't transfer,
benchmarking across Workers is apples-to-oranges, and every new Worker re-implements the hard
parts (retrieval, confidence gating, learning). The reusability promise of the ECL — "stand up
a new Worker in a day" (`ARCH-07`) — dies if each Worker is a special case.

We must decide whether the ECL core is domain-specific or domain-agnostic.

## Decision

We will make the ECL core **completely domain-agnostic**, and Workers specializations *over*
that shared core rather than distinct systems. Context assembly, Knowledge and Experience
memory, evaluation machinery, reflection, learning, confidence fusion, orchestration
(`ADR-0008`) and model routing are identical for every Worker type. A Worker is *not* new
architecture; it is a `WorkerSpec` that binds four pluggable specializations to the shared
core (`ADR-0025`). Adding "Future Worker N" requires zero architectural change — only its four
specializations.

## Consequences

- **Positive.** New Worker types are cheap and fast to create, they inherit every safety and
  quality property for free, and lessons and mechanisms transfer across domains (a QA Worker's
  async-test-flake lesson can help a Support Worker). Benchmarking across Worker types is fair
  because the machinery is identical.
- **Positive.** The core gets battle-tested by every Worker, so improvements compound across all
  of them at once.
- **Negative.** The shared core cannot bake in any domain's assumptions; genuinely
  domain-specific behavior must be expressed *only* through the four specialization axes, which
  is a discipline and occasionally a constraint on how a domain would "naturally" model itself.
- **Neutral.** The domain (retail/MCG) remains a realistic backdrop for producing artifacts, not
  something the architecture is coupled to — consistent with `CANON-001`'s design intent.
