# ADR-0030: Plugin Architecture via Entry Points

- Status: Accepted
- Date: 2026-02-24
- Deciders: Architecture Office (TEAM-090)
- Related: ADR-0029, ADR-0042, ADR-0024, ADR-0025, RFC-0027

## Context

The ECL is domain-agnostic: a new Enterprise Worker type is defined not by new architecture but
by four pluggable specializations — knowledge domains, tools, rubrics, policies (ADR-0024,
ADR-0025, ARCH-07). Beyond Workers, every module has extension points (retrievers, stores,
model providers, evaluators). We need a registration mechanism that lets implementations and
Workers be added *without modifying the ECL core*, and that lets third parties contribute
Workers to the open project.

The recurring extension pattern (SDK README) is: implement the module's abstract interface
(ADR-0029), register it, and the runtime wires it in. That registration mechanism must be
standard, discoverable, and packaging-native rather than a bespoke plugin loader.

## Decision

We will use **Python packaging entry points** as the plugin registration mechanism, per
RFC-0027. Implementations declare themselves under well-known ECL entry-point groups (e.g.
knowledge stores, retrievers, tools, model providers, evaluators, worker specs); the ECL
runtime discovers and loads them at startup and composes them behind their abstract interfaces.

A Worker additionally supplies a `WorkerSpec` binding its knowledge domains, tools, rubrics and
policies. Loaded tools are subject to least-privilege scoping (ADR-0042) — registration grants
*discoverability*, not automatic authority to act.

## Consequences

- Positive: extend the ECL without editing its core; add a Worker type in a day (ARCH-07,
  Example C); enables a third-party plugin ecosystem for the open project.
- Positive: packaging-native — no custom loader; standard tooling resolves and installs plugins.
- Negative: dependency and version conflicts between plugins are possible; the runtime must pin
  and resolve carefully, and SemVer (ADR-0032) governs compatibility.
- Negative: loading third-party code is a supply-chain and privilege risk; mitigated by
  least-privilege tool access (ADR-0042), policy enforcement before execution (ADR-0041) and
  synthetic-only content rules (ADR-0049).
- Neutral: discovery failures can be opaque; the runtime logs resolved plugins to the Signals
  Bus (ADR-0038) for auditability.
