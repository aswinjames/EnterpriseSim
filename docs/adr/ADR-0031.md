# ADR-0031: Trunk-Based Development

- Status: Accepted
- Date: 2026-03-03
- Deciders: Architecture Office (TEAM-090)
- Related: CANON-001 §4.1, §4.2, §4.5, ADR-0032, ADR-0033

## Context

EnterpriseSim is itself an engineering project and must model MCG's own SDLC credibly.
CANON-001 §4.1 mandates trunk-based development for MCG: `main` always releasable and
protected, short-lived branches (< 3 days), large work behind feature flags, every change
landing via PR. The EnterpriseSim repository — which defines CANON, the ECL docs, the SDK and
the schemas — should follow the same discipline both for consistency with canon and because the
artifacts here are consumed continuously by Workers and benchmarks.

The alternative, long-lived release branches or GitFlow, produces merge debt, delays
integration feedback, and would contradict CANON-001 §4.1.

## Decision

We will practice **trunk-based development** on the EnterpriseSim repository, mirroring
CANON-001 §4.1–§4.5:

- `main` is always releasable and protected; no direct pushes.
- Work lands via short-lived `feature/`, `bugfix/` or `hotfix/` branches (< 3 days) through PRs
  with the required reviews (CANON-001 §4.2, §7.5).
- Incomplete or risky changes hide behind flags rather than living on a branch.
- Schema and SDK changes are integrated continuously and versioned by SemVer (ADR-0032),
  evolving via expand-contract (ADR-0033) so `main` never carries a breaking half-migration.

## Consequences

- Positive: continuous integration surfaces conflicts early; small, reviewable PRs (CANON-001
  §4.2 targets < 400 lines); `main` is always a coherent, citable source of truth for canon,
  schemas and SDK.
- Positive: consistency between how EnterpriseSim is built and how MCG is documented to build —
  the project practices what it models.
- Negative: requires strong CI gates and reviewer availability; a weak pipeline makes an
  always-releasable trunk unsafe.
- Negative: feature flags accrue debt if not retired; flag hygiene must be tracked.
- Neutral: contract changes still require RFC/ADR governance (ADR-0033, ADR-0050) even under
  fast trunk cadence — speed of merge does not bypass governance of invariants.
