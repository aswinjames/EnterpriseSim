# RB-0019 — Canary Auto-Rollback on SLO Breach

| Field | Value |
|---|---|
| Runbook id | RB-0019 |
| Title | Canary Auto-Rollback on SLO Breach |
| Owner team | TEAM-031 (Developer Experience) |
| Apps | All Tier-0 services |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-014 |
| Related knowledge | KN-418 |

## Purpose

Explain what happens when the automated canary analysis trips an SLO guardrail during a
progressive rollout, how the auto-rollback engages, and how the owning squad confirms it
completed, investigates the canary metrics, decides whether to override or hold, and
re-attempts after a fix. Per CANON §4.3, MCG's standard is progressive delivery
(canary → percentage rollout → full) with **automated rollback on SLO breach** (§7.4).
The rollback engine is owned by TEAM-031 (DevEx); the service SLOs it enforces are owned
by each squad. INC-2026-014 (edge OIDC clock-skew bug) is the reference case: the guardrail
correctly halted the rollout, but the squad still needed this runbook to confirm state and
drive the fix-forward.

## When to use (symptoms / alerts)

- PagerDuty alert `canary-rollback-engaged` fires for your service with a `reason`
  (`error_rate`, `latency_p99`, or `saturation`) and the rollout id `RO-<service>-<n>`.
- Argo Rollouts dashboard **Delivery / Progressive** shows the rollout `Degraded` and the
  canary ReplicaSet scaling back to zero.
- The deploy pipeline stage `deploy(canary)` or `progressive rollout` is marked
  `RolledBack` in GitHub Actions; the release `REL-2026-###` is flagged `auto-reverted`.
- Grafana **Canary Analysis** panel shows the canary metric crossing its guardrail band:
  error rate > 1% (5m), p99 latency > baseline × 1.3, or CPU/memory saturation > 85%.
- Slack `#deploys` posts `AnalysisRun failed: <metric> outside tolerance` from `mcg-deploy`.

## Preconditions

- You are the owning squad's on-call for the service being rolled out (or the follow-the-sun
  holder for a Tier-0 page).
- `kubectl` context set to the affected region: `kubectl config use-context mcg-<region>-prod`.
- `mcg-deploy` and `kubectl argo rollouts` plugins available on the ops jumpbox.
- You know the rollout id (`RO-<service>-<n>`) and the release tag (`v<semver>`) from the
  alert or `mcg-deploy status <service> --region <region>`.
- The prior stable revision is retained (Argo keeps `revisionHistoryLimit: 5`); no manual
  image pull is required to revert.

## Procedure

1. **Read the guardrail verdict first.** Do not touch the rollout until you know which SLO
   tripped and by how much:
   ```
   mcg-deploy analysis show RO-<service>-<n> --region <region>
   ```
   This prints the failing metric, the measured value, the guardrail threshold, and the
   `measurement window`. Note whether it is `error_rate`, `latency_p99`, or `saturation`.
2. **Confirm the auto-rollback is progressing, not stuck.** The engine scales the canary to
   zero and shifts 100% of traffic back to stable:
   ```
   kubectl argo rollouts get rollout <service> -n <namespace> --watch
   ```
   Expect `Status: Degraded → Healthy` with `Stable` weight climbing to 100 and `Canary`
   weight falling to 0. If it hangs at a partial weight (e.g. stuck at 25%) for > 60s, go to
   step 6.
3. **Verify traffic is fully on stable.** Confirm the service mesh / gateway split matches:
   ```
   mcg-deploy traffic RO-<service>-<n> --region <region>
   ```
   `stable=100% canary=0%` is the target. The abort also pins the ingress route back to the
   stable subset at APP-024.
4. **Investigate the canary metrics to find the real cause.** Compare canary vs stable over
   the analysis window so you fix the code, not the symptom:
   ```
   mcg-metrics compare --rollout RO-<service>-<n> \
     --metrics error_rate,latency_p99,cpu,mem --window 15m --region <region>
   ```
   Pull the canary-only error signature from logs (scope to the canary pod hash):
   ```
   kubectl -n <namespace> logs -l app=<service>,rollout-pod-template-hash=<canary-hash> \
     --since=15m | mcg-logql top-errors
   ```
   For INC-2026-014 this surfaced `OIDC token 'nbf' rejected: clock skew` on canary only —
   a config regression, not load.
5. **Decide: hold, override, or fix-forward.**
   - **Hold (default):** leave the rollout aborted, keep stable serving, and fix the code.
     This is correct for a genuine regression.
   - **Override only with IC approval** if analysis was a false positive (e.g. a noisy
     dependency, not your change):
     ```
     mcg-deploy rollout resume RO-<service>-<n> --region <region> --ack-slo-override
     ```
     Overriding a real breach is a Sev-escalating action — never do it to "push through" a
     known-bad build.
6. **Force-complete a stuck rollback.** Only if step 2 shows the rollback wedged:
   ```
   kubectl argo rollouts abort <service> -n <namespace>
   kubectl argo rollouts undo <service> -n <namespace> --to-revision=<stable-rev>
   ```
   Then re-check traffic (step 3).
7. **Re-attempt after a fix.** Land the fix as a normal PR (or hotfix per RB-0020 if the
   incident is Sev1/Sev2), then start a fresh rollout with the guardrails intact:
   ```
   mcg-deploy release <service> --tag v<semver-fixed> --region <region> --strategy canary
   ```
   Do not disable canary analysis to get the release out; tighten or fix, never bypass.

## Verification

- `kubectl argo rollouts get rollout <service>` reports `Status: Healthy` on the stable
  revision; canary ReplicaSet at 0 replicas.
- `mcg-deploy traffic RO-<service>-<n>` shows `stable=100% canary=0%`.
- The tripped SLI is back inside its guardrail band for 10 continuous minutes on the
  **Canary Analysis** board (error rate < 1%, p99 within 1.3× baseline, saturation < 85%).
- `mcg-synthetics run <service>-smoke --region <region>` returns 200 against stable.
- The re-attempted rollout (if run) advances through all analysis gates to 100% with
  `AnalysisRun: Successful`.

## Rollback

- The auto-rollback *is* the rollback; there is normally nothing further to revert once
  traffic is fully on stable.
- If an override (step 5) was issued and the bad build reached full rollout, revert
  immediately: `mcg-deploy rollback <service> --to v<prev-semver> --region <region>`.
- Migrations are expand-contract (§7.4), so reverting the image never requires a schema
  down-migration under fire; leave the expanded schema in place until the fix ships.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** Owning squad's regional on-call is Incident Commander; TEAM-031 owns
  the rollback engine itself if the engine (not the service) misbehaves.
- **T1 (10 min, unresolved):** Page TEAM-031 DevEx (`oncall-devex`) if the rollback is stuck
  or analysis is misconfigured; page TEAM-032 SRE if the SLO definitions are in question.
- **Follow-the-sun handoff** for Tier-0 pages: NA (`oncall-devex-na`) → EU
  (`oncall-devex-eu`) → APAC (`oncall-devex-apac`); rotate IC at the regional boundary and
  keep the incident channel as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
