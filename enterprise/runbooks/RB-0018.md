# RB-0018 — Emergency Feature-Flag Kill Switch

| Field | Value |
|---|---|
| Runbook id | RB-0018 |
| Title | Emergency Feature-Flag Kill Switch |
| Owner team | TEAM-030 (Core Platform) |
| Apps | All — platform feature-flag service |
| Severity scope | Sev1–Sev3 |
| Related incidents | INC-2026-002, INC-2026-019 |
| Related knowledge | KN-417 |

## Purpose

Safely disable a bad code path in production using the platform feature-flag service without
a deploy. MCG mandates that large or risky work ships behind a flag (CANON §4.1), which makes
a flag flip the fastest mitigation for a code-regression incident. This runbook covers
finding the flag, scoping the change (region / percentage / global), toggling it, verifying
propagation, reading the audit trail, and the guardrails — who may break-glass and how
temporary flags expire. It is the mechanism behind several service runbooks: the guest-
loyalty guard in RB-0014 (INC-2026-002) and the async-promo switch in RB-0012 (INC-2026-019).
The flag service is `mcg-flags` (CLI) backed by the `mcg-feature-flags` repo, owned by
TEAM-030 (Core Platform).

## When to use (symptoms / alerts)

- An incident's trigger is a recently-shipped, flag-gated code path and the fastest safe
  mitigation is to turn it off (faster than a rollback deploy).
- A service runbook's Procedure references a `mcg-flags set ...` step (e.g., RB-0012,
  RB-0013, RB-0014, RB-0016).
- A progressive rollout is misbehaving and you need to halt it at the current percentage or
  fully revert it without redeploying.
- A partner/region-specific defect where you want to scope the disable to one region.

## Preconditions

- You are the owning squad's on-call or, for a break-glass global flip, an authorized
  role-holder (see Guardrails below).
- `mcg-flags` CLI authenticated (`mcg-flags whoami` shows your identity and roles).
- You know the **flag key**, the owning service, and the intended **scope** (region /
  percentage / global). If unsure of the key, discover it (step 1).
- The change is announced in the incident channel before a global flip (single source of truth).

## Procedure

1. **Find the flag.** List and search flags for the affected service:
   ```
   mcg-flags list --service <service> --search <keyword>
   mcg-flags describe --service <service> <flag.key>
   ```
   `describe` shows the current value per region/segment, the default, the owner, whether it
   is a **temporary** (kill-switch) or **permanent** (config) flag, and its expiry.
2. **Confirm current state before changing.** Capture the pre-change value so you can revert
   exactly:
   ```
   mcg-flags get <service> <flag.key> --all-scopes
   ```
3. **Scope the change — least blast radius first.** Prefer the narrowest scope that mitigates:
   - **Region:** disable only where impact is observed.
     ```
     mcg-flags set <service> <flag.key>=false --region <NA|EU|APAC|LATAM>
     ```
   - **Percentage:** dial a progressive rollout down (halt or partially revert) rather than
     all-or-nothing.
     ```
     mcg-flags set <service> <flag.key> --rollout 0 --region <region>
     ```
   - **Global (break-glass):** only when impact is global and region scoping is insufficient;
     requires an authorized role and an incident link.
     ```
     mcg-flags set <service> <flag.key>=false --global \
       --break-glass --incident INC-2026-### --reason "<short reason>"
     ```
4. **Verify propagation latency.** Flags propagate via the edge config stream; target is
   < 30s. Confirm pods actually observe the new value rather than assuming:
   ```
   mcg-flags propagation-status <service> <flag.key> --region <region>
   kubectl -n <ns> exec deploy/<service> -- curl -s localhost:<admin-port>/admin/flags | grep <flag.key>
   ```
   If a pod is stuck on the old value past the propagation window, restart just that pod;
   avoid a full rollout restart unless propagation is broadly broken.
5. **Confirm the bad path is actually gated off.** Watch the impact metric the flag is meant
   to control (error rate, latency, bad-account creation, etc.) return to nominal. If the
   symptom persists after full propagation, the flag does not gate the offending path — stop
   relying on it and move to a rollback (see the owning service runbook).
6. **Record the audit trail.** Every set is logged immutably; capture it in the incident:
   ```
   mcg-flags audit <service> <flag.key> --last 10
   ```
   The audit shows who changed what, when, scope, break-glass status and reason. Paste the
   entry into the incident channel.
7. **Set/confirm an expiry for temporary flags.** Kill-switch flags must not live forever;
   attach an expiry and a follow-up ticket so the flag (and the dead code path) is cleaned up:
   ```
   mcg-flags set-expiry <service> <flag.key> --expires <YYYY-MM-DD> --owner @squad --ticket <KEY-####>
   ```

## Verification

- `mcg-flags get <service> <flag.key> --all-scopes` reflects the intended value at the
  intended scope.
- `mcg-flags propagation-status` reports full propagation; sampled pods show the new value.
- The incident's impact metric returns to nominal after the flip (attributable to the flag).
- `mcg-flags audit` shows the change with actor, scope, reason and (if used) break-glass flag.
- Temporary/kill-switch flags have an expiry date and a cleanup ticket assigned.

## Rollback

- A flag flip is inherently reversible — revert to the captured pre-change value:
  ```
  mcg-flags set <service> <flag.key>=<previous-value> --region <region>
  ```
  (or `--global` if that was the scope). Only revert once the underlying fix/rollback is in
  place; reverting into the still-broken state reintroduces the incident.
- If the flip did not mitigate (step 5), do not leave a half-applied global change — revert it
  and escalate to a proper release rollback per the owning service runbook.
- No data is mutated by a flag change, so there is never a schema/data rollback here.

## Guardrails

- **Who can break-glass:** region-scoped and percentage changes are available to the owning
  squad's on-call. A `--global --break-glass` flip requires an authorized role (owning-squad
  lead, TEAM-030 platform on-call, or the SRE IC) and a linked `INC-####`; it pages the flag
  owner automatically.
- **Auditability:** every change is immutable and attributable (CANON §4.5, no unaudited prod
  changes). Break-glass flips are reviewed in the postmortem.
- **Expiry:** temporary flags carry a mandatory expiry; expired-but-still-on flags are flagged
  by a weekly hygiene job and tracked as a Sev3 if left unresolved.
- **Not for config:** do not use kill-switches to carry long-term configuration — permanent
  behavior belongs in versioned config (e.g., pricing rules, RB-0013), not a flag.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** owning squad on-call performs region/percentage flips for their service.
- **T1:** TEAM-030 (Core Platform) on-call for flag-service problems (propagation stalls, the
  flag not gating what it should) and to authorize/execute a global break-glass flip.
- **Follow-the-sun (Tier 0):** rotate on-call/IC NA (`oncall-platform-na`) → EU
  (`oncall-platform-eu`) → APAC (`oncall-platform-apac`); keep the incident channel as the
  single source of truth for any global flip.
- **T2 (Sev1, or global break-glass):** engage SRE (TEAM-032) as Incident Commander and
  follow RB-0011; the IC owns the rollback-vs-fix-forward decision the flag supports.
