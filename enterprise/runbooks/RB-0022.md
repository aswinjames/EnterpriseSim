# RB-0022 — Payments PCI Incident Containment & Secret Rotation

## Purpose

Contain a suspected credential exposure or PCI-boundary concern in Payments (APP-012):
revoke and rotate PSP API keys and service credentials via the platform secret manager,
confirm cardholder data never left the APP-012 boundary, rotate workload identity, coordinate
with Security Engineering (TEAM-040), and audit logs for exposure. Per CANON §4.6, secrets
live only in the platform secret manager (never in code, config or logs), and **PCI
cardholder data is isolated to APP-012's boundary**. Per §2.6, TEAM-040 owns PCI-DSS scope
and cardholder-data boundaries jointly with TEAM-009. APP-012 is Tier-0 PCI and ships on the
`golden-path-jvm-pci` pipeline. INC-2026-009 (primary PSP degraded) is the reference PSP
context; the containment posture here also applies whenever a PSP credential may have been
exposed during such an event.

## When to use (symptoms / alerts)

- Alert `pci-secret-exposure-suspected` or a report that a PSP API key / service credential
  may have leaked (e.g. surfaced in a log, a repo, an error payload, or a third-party notice).
- Secret-scan gate flags a credential-shaped string in a build, log stream, or config.
- Anomalous PSP authorization traffic (`mcg-payments` PSP dashboard shows auth calls from an
  unexpected source or a spike inconsistent with order volume).
- Any concern that data crossing the APP-012 boundary might contain PAN/cardholder data.
- Elevated authorization latency/failover (as in INC-2026-009) coinciding with credential
  churn, raising the question of whether a rotated/compromised key is in play.

## Preconditions

- You are on TEAM-009 (Payments) on-call, or the follow-the-sun holder for a Tier-0 page.
- TEAM-040 (Security Eng) is engaged from minute zero — PCI incidents are co-owned (§2.6).
- `kubectl` context on the affected region; `mcg-secrets` (platform secret manager CLI),
  `mcg-payments` and `mcg-iam` (workload-identity CLI) available on the PCI ops jumpbox.
- You have break-glass approval logged in the incident for secret rotation (rotation is
  audited; approval is recorded, not skipped).
- Know the PSP(s) in play (primary + failover) and the region(s). Cardholder data handling is
  confined to the `payments` namespace / APP-012 boundary; no other service holds PAN.

## Procedure

1. **Contain first: revoke the suspect credential at the PSP.** Cut the blast radius before
   rotating. Disable the exposed key on the PSP side so it cannot be used even if copied:
   ```
   mcg-payments psp key revoke --psp <psp-id> --key-id <exposed-key-id> --region <region>
   ```
   This routes new authorizations through the failover PSP (the same failover path exercised
   in INC-2026-009) while you rotate.
2. **Rotate the PSP API key in the platform secret manager.** Generate a new key at the PSP,
   store it in the secret manager, and roll the version — never paste it into config or a
   ticket:
   ```
   mcg-secrets rotate payments/psp/<psp-id>/api-key --region <region>
   mcg-secrets versions payments/psp/<psp-id>/api-key   # confirm new version is 'current'
   ```
3. **Roll the Payments pods to pick up the new secret.** APP-012 mounts secrets via the
   secret-manager CSI driver; trigger a rolling restart so the new version is loaded:
   ```
   kubectl -n payments rollout restart deploy/payments-service
   kubectl -n payments rollout status deploy/payments-service
   ```
4. **Rotate workload identity.** If the exposure could implicate the service's own identity
   (mTLS cert / OIDC workload credential), rotate it and re-issue:
   ```
   mcg-iam workload rotate --service payments-service --namespace payments --region <region>
   ```
   Confirm service-to-service calls remain mutually authenticated (§4.6) after rotation.
5. **Confirm cardholder data never left the APP-012 boundary.** This is the core PCI check.
   Verify no PAN/cardholder fields appear outside `payments`:
   ```
   mcg-payments pci boundary-check --region <region> --since 2h
   ```
   The check asserts: outbound events to Kafka/OMS carry only tokens (not PAN), logs are
   scrubbed, and no cardholder field crossed to APP-003/APP-009/APP-024. Any hit is a
   confirmed PCI event → escalate to TEAM-040 immediately.
6. **Audit logs for actual exposure.** Search the exposure window for the credential pattern
   and for any PAN-shaped data in logs (logs must never contain either — §4.6):
   ```
   mcg-logql search --service payments-service --since 6h \
     --pattern 'psp_api_key|pan=|card_number' --pci-safe-redact
   ```
   Record findings in the incident. If a real PAN appears in logs, treat as a reportable PCI
   incident and hand the forensic timeline to TEAM-040.
7. **Verify blast radius is closed.** Confirm the old key is dead and only the new version is
   in use:
   ```
   mcg-payments psp key status --psp <psp-id>   # exposed-key-id = revoked
   ```
8. **Record the rotation and boundary attestation** in the incident and notify TEAM-040 for
   the PCI compliance log.

## Verification

- `mcg-secrets versions payments/psp/<psp-id>/api-key` shows the new version as `current` and
  the prior version `disabled`; PSP reports the exposed key `revoked`.
- Authorization success rate and p99 back to baseline on the **Payments / Authorization**
  board; failover PSP drained back to primary if desired.
- `mcg-payments pci boundary-check` returns **no** cardholder data outside APP-012.
- Log audit (step 6) returns zero credential or PAN matches after redaction.
- Workload identity rotation confirmed: `mcg-iam workload status --service payments-service`
  shows the new cert/credential active and mTLS handshakes succeeding.
- `mcg-synthetics run payments-authorize --region <region>` passes against the new key.

## Rollback

- Secret rotation is forward-only and is **not** rolled back — reverting to an exposed
  credential is never acceptable. If the new key is faulty, rotate again to a fresh key.
- If a Payments deploy shipped alongside the rotation and regressed, roll that release back per
  RB-0022's companion deploy runbook / hotfix RB-0020; the secret stays rotated.
- If workload-identity rotation broke service-to-service auth, re-issue the identity (step 4)
  rather than restoring the old credential.
- Expand-contract migrations (§7.4) mean no schema down-migration is needed during containment.

## Escalation (follow-the-sun, Tier 0 PCI)

- **T0 (0–10 min):** TEAM-009 (Payments) regional on-call is Incident Commander; TEAM-040
  (Security Eng) is co-owner from minute zero for any PCI concern (§2.6).
- **T1 (10 min, unresolved):** Engage TEAM-040 IR lead for forensic timeline and
  regulatory/PCI-DSS reporting decision; loop TEAM-030 if the PSP path traverses the gateway
  (APP-024).
- **Follow-the-sun handoff** for Tier-0 pages: NA (`oncall-payments-na`) → EU
  (`oncall-payments-eu`) → APAC (`oncall-payments-apac`); rotate IC at the regional boundary,
  keep the incident channel as the single source of truth.
- **T2 (20 min or Sev1, or any confirmed cardholder-data exposure):** Engage SRE (TEAM-032) as
  Incident Commander and follow RB-0011; confirmed PCI exposure additionally triggers the
  Security Eng disclosure process.
