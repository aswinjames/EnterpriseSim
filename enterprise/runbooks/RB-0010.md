# RB-0010 — Expand-Contract Database Migration

| Field | Value |
|---|---|
| Runbook id | RB-0010 |
| Title | Expand-Contract Database Migration |
| Owner team | TEAM-031 (Developer Experience) |
| Apps | All PostgreSQL-backed services |
| Severity scope | Sev2–Sev3 (preventive) |
| Related incidents | None — preventive |
| Related knowledge | KN-409 |

## Purpose

Define the backward-compatible **expand-contract** migration pattern MCG uses for every
PostgreSQL schema change, so that a code rollback never requires a schema down-migration
under fire (CANON §7.4). A migration proceeds in four phases — **expand** (add nullable
column / new table, dual-write) → **backfill** → **migrate reads** → **contract** (drop the
old shape) — with each phase independently deployable and reversible. At every step the
currently deployed application code is valid against the current schema, which is what makes
the progressive-delivery rollback in RB-0009 safe. This runbook is preventive: it exists to
keep migrations off the incident list.

## When to use (symptoms / alerts)

- You are changing a PostgreSQL schema for any `mcg-*` service (add/rename/drop a column,
  change a type, split/merge a table, add a constraint or index).
- A PR touches a `db/migrations/` directory and CODEOWNERS routed it to DevEx/DBA review.
- You need to change a column type or NOT NULL constraint without a maintenance window.
- Never use this as a shortcut to do a single destructive `ALTER` on a live Tier-0 table —
  that is exactly what expand-contract exists to prevent.

## Preconditions

- Migrations are applied via the platform migration runner (`mcg-migrate`, Flyway/`golang-
  migrate` backed), versioned in the repo, and run in CI before the app deploy.
- `psql` access to the target via the platform proxy (never direct prod creds); read access
  to the **DevEx / DB Migrations** dashboard for replication lag and lock monitoring.
- The change is split into **separate releases per phase** — expand, backfill, migrate-reads,
  and contract ship as distinct `v<semver>` deploys, never bundled.
- For online index/constraint work you will use `CONCURRENTLY` / `NOT VALID` to avoid long
  table locks.

## Procedure

1. **Phase 1 — Expand (additive, backward-compatible).** Add the new shape as nullable / new
   table; old code ignores it. Example adding a replacement column:
   ```
   mcg-migrate new --service <svc> --name add_email_normalized_expand
   # migration body:
   #   ALTER TABLE customers ADD COLUMN email_normalized text NULL;
   mcg-migrate up --service <svc> --region <region> --phase expand
   ```
   New columns must be `NULL` (or have a fast default) so the `ALTER` does not rewrite the
   table or block writes. Verify no long lock:
   ```
   psql -c "SELECT pid, state, wait_event_type, query FROM pg_stat_activity WHERE query ILIKE 'ALTER TABLE%';"
   ```
2. **Enable dual-write.** Deploy app code (via RB-0009) that writes **both** the old and new
   columns while still reading the old one. Gate it behind a flag so it is reversible:
   ```
   mcg-flags set <svc> db.migration.dual_write.email_normalized=true --region <region>
   ```
3. **Phase 2 — Backfill (batched, throttled).** Populate the new shape for existing rows in
   bounded batches so you never hold a long transaction or spike replication lag:
   ```
   mcg-migrate backfill --service <svc> --table customers \
     --set "email_normalized = lower(email)" --batch-size 5000 --sleep 200ms --region <region>
   ```
   Monitor replication lag continuously and pause if it climbs:
   ```
   watch -n 10 'psql -c "SELECT client_addr, replay_lag FROM pg_stat_replication;"'
   ```
   If `replay_lag` exceeds the SLO (e.g. > 30s), `mcg-migrate backfill --pause` and resume
   with a smaller `--batch-size`.
4. **Phase 3 — Migrate reads.** Once backfill is 100% and dual-write has kept new rows
   correct, deploy app code that **reads** the new column (still dual-writing) via RB-0009
   canary. Verify parity before flipping fully:
   ```
   mcg-migrate verify-parity --service <svc> --table customers \
     --old email --new email_normalized --region <region>
   ```
   `verify-parity` must report `mismatches: 0` across a sampled + full scan.
5. **Add constraints online (if required).** Promote the new column to NOT NULL / add indexes
   without blocking:
   ```
   psql -c "CREATE INDEX CONCURRENTLY idx_customers_email_normalized ON customers(email_normalized);"
   psql -c "ALTER TABLE customers ADD CONSTRAINT customers_email_normalized_nn CHECK (email_normalized IS NOT NULL) NOT VALID;"
   psql -c "ALTER TABLE customers VALIDATE CONSTRAINT customers_email_normalized_nn;"
   ```
6. **Phase 4 — Contract (destructive, last and only after soak).** Only after the read-migrated
   code has soaked in production (≥1 release cycle) and no code references the old shape, stop
   dual-write and drop the old column in a final release:
   ```
   mcg-flags set <svc> db.migration.dual_write.email_normalized=false --region <region>
   mcg-migrate new --service <svc> --name drop_email_legacy_contract
   #   ALTER TABLE customers DROP COLUMN email;   -- old, now-unused column
   mcg-migrate up --service <svc> --region <region> --phase contract
   ```
   The contract migration is the point of no return — it ships as its own release with its own
   rollback assessment.

## Verification

- After each phase, `mcg-migrate status --service <svc> --region <region>` shows the expected
  version and `dirty: false`.
- No migration held a lock longer than the threshold: `mcg-migrate lock-report --since <phase_start>`
  shows zero blocking locks over 1s on the target table.
- `pg_stat_replication.replay_lag` stayed within SLO throughout backfill.
- `mcg-migrate verify-parity` reports `mismatches: 0` before reads are migrated.
- Post-contract, application error rate and query latency are nominal on the service SLO
  dashboard for 10 continuous minutes.

## Rollback

- **Expand phase:** roll back the app code (RB-0009); the added nullable column is inert and
  can be left in place or dropped later — no down-migration under fire.
- **Dual-write / backfill:** disable the dual-write flag (`db.migration.dual_write.*=false`)
  and pause the backfill (`mcg-migrate backfill --pause`); the old column remains the source
  of truth, so the system is fully functional.
- **Migrate-reads:** roll back the reads-migrated app version (RB-0009); because dual-write is
  still on, the old column is current and reads revert to it instantly.
- **Contract:** this is the only phase whose migration is destructive. It is not reversible by
  down-migration; recovery from a mistaken contract is a restore-from-backup / PITR event —
  which is exactly why contract ships last, alone, and only after soak. Abort criteria before
  running contract: any nonzero `verify-parity` mismatch or any lingering code reference to
  the old column (`mcg-migrate refs --column <old>` must be empty).

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** The owning squad's regional on-call runs the migration and is Incident
  Commander if a phase misbehaves.
- **T1 (10 min, unresolved):** Page TEAM-031 (DevEx) for the migration runner and TEAM-060
  (Data Platform) / the platform DBA on-call for PostgreSQL replication-lag or lock issues.
- **Follow-the-sun handoff** for Tier-0 pages: NA → EU → APAC on the owning squad's rotation;
  rotate IC at the regional boundary and keep the migration's channel as the single source of
  truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
