# RB-0005 — Edge Rate-Limit Tuning

| Field | Value |
|---|---|
| Runbook id | RB-0005 |
| Title | Edge Rate-Limit Tuning |
| Owner team | TEAM-030 (Core Platform) |
| Apps | APP-024 (API Gateway / Edge) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-013 |
| Related knowledge | KN-308, KN-404 |

## Purpose

Correct an over-aggressive edge rate limit when a token-bucket threshold on APP-024 rejects
legitimate traffic with HTTP 429. The gateway (Envoy/Kong + Go + Lua) enforces per-route,
per-region token buckets; a threshold set too low starves real users while doing nothing for
abuse. This runbook operationalizes INC-2026-013 (a too-aggressive token-bucket threshold
rejected legitimate EU traffic for 14 minutes after REL-2026-007) and its postmortem KN-308.
The change is a config change (CANON §7 config-change class) and is always canaried per
region before full apply.

## When to use (symptoms / alerts)

- PagerDuty alert `edge-429-ratio-high` (`http_429_ratio{app="APP-024"} > 1% (5m)`) or
  `edge-legit-traffic-rejected`.
- Grafana dashboard **Edge / Rate Limits** shows `ratelimit_over_limit_total` spiking on a
  specific `route` and `region` immediately after a gateway config rollout.
- Downstream apps (e.g. APP-001 Storefront, APP-006 Search) report elevated upstream 429s
  they did not generate themselves.
- Customer/CS reports of "too many requests" errors on normal browsing.

## Preconditions

- You are on the TEAM-030 on-call rotation (or the follow-the-sun holder for a Tier-0 edge
  page).
- `kubectl` context on the affected region: `kubectl config use-context mcg-<region>-prod`.
- Gateway runs in namespace `edge`; limiter config is GitOps-managed
  (`mcg-api-gateway/config/ratelimits/<region>.yaml`) and applied via `mcg-edge`.
- The rate-limit service is `edge-ratelimit` backed by `edge-ratelimit-redis-prod`.
- You know the affected **route** and **region** (INC-2026-013 was EU-only — scope the fix,
  do not widen limits globally).

## Procedure

1. **Identify the offending route and current limits.** Confirm which bucket is over-limiting:
   ```
   mcg-edge ratelimit show --route <ROUTE> --region <region>
   ```
   Note `requests_per_unit`, `unit` (second/minute), and `burst` (bucket depth). Cross-check
   the 429 source:
   ```
   kubectl -n edge exec deploy/edge-ratelimit -- \
     redis-cli -h edge-ratelimit-redis-prod --scan --pattern 'rl:<ROUTE>:<region>:*' | head
   ```
2. **Confirm the traffic is legitimate, not abuse.** Before widening, rule out a real attack:
   ```
   mcg-edge traffic profile --route <ROUTE> --region <region> --since 15m
   ```
   Look for many distinct authenticated principals and human-plausible request rates. If the
   429s are shedding a bot/credential-stuffing wave, do NOT widen — go to RB-0008
   (load-shedding) / Security instead.
3. **Compute a safe new bucket.** Set `requests_per_unit` to the observed legitimate p99
   rate plus ~30% headroom, and widen `burst` to absorb bursty page loads. Edit the region
   config:
   ```
   mcg-edge ratelimit set --route <ROUTE> --region <region> \
     --rate 1200/min --burst 400 --dry-run
   ```
   `--dry-run` prints the diff and simulated rejection rate against the last 15m of traffic.
4. **Canary the change in the affected region only.** Apply to a single gateway canary pool
   first (CANON §7.2 progressive delivery):
   ```
   mcg-edge ratelimit apply --route <ROUTE> --region <region> --canary 10
   ```
   This routes 10% of edge pods to the new limit. Watch `http_429_ratio` and upstream health
   for 5 minutes.
5. **Promote to full region.** If the canary is clean:
   ```
   mcg-edge ratelimit apply --route <ROUTE> --region <region> --promote
   ```
   The apply is committed back to `ratelimits/<region>.yaml` via GitOps (no manual prod edit
   per CANON §4.5).
6. **Verify Redis counters reset cleanly.** Confirm the limiter is honoring the new depth:
   ```
   kubectl -n edge exec deploy/edge-ratelimit -- \
     redis-cli -h edge-ratelimit-redis-prod GET rl:<ROUTE>:<region>:cfg
   ```

## Verification

- `http_429_ratio{app="APP-024", route="<ROUTE>", region="<region>"} < 0.1%` for 5
  continuous minutes on the Edge / Rate Limits board.
- `ratelimit_over_limit_total` for the route flattens; no new legitimate rejections in
  `mcg-edge traffic profile --route <ROUTE> --region <region> --since 10m`.
- `mcg-synthetics run edge-route --route <ROUTE> --region <region>` returns `200` under a
  burst of the expected page-load fan-out.
- Downstream apps (APP-001/APP-006) upstream-429 count returns to baseline.
- Confirm the change is in Git: `mcg-edge ratelimit history --route <ROUTE> --region <region>`
  shows the committed revision.

## Rollback

- Config changes are versioned; revert to the prior committed limit:
  ```
  mcg-edge ratelimit rollback --route <ROUTE> --region <region> --to-previous
  ```
- If widening caused upstream saturation (too much traffic now reaching origin), do NOT keep
  widening — roll back and coordinate origin capacity / load-shedding via RB-0008.
- Because the change is region-scoped, rollback affects only `<region>`; other regions are
  untouched.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-030 regional on-call owns the edge/limiter config and is Incident
  Commander.
- **T1 (10 min, unresolved):** Loop in the owning team of the throttled downstream route
  (e.g. TEAM-001 Storefront, TEAM-003 Search) to confirm expected traffic shape, and
  TEAM-040 (Security) if abuse cannot be ruled out.
- **Follow-the-sun handoff** for Tier-0 edge pages: NA (`oncall-edge-na`) → EU
  (`oncall-edge-eu`) → APAC (`oncall-edge-apac`); rotate IC at the regional boundary and keep
  `#inc-edge-ratelimit` as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
