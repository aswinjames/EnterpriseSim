# RB-0014 — Guest-Checkout Orphaned Loyalty Account Recovery

| Field | Value |
|---|---|
| Runbook id | RB-0014 |
| Title | Guest-Checkout Orphaned Loyalty Account Recovery |
| Owner team | TEAM-004 (Cart & Checkout) |
| Apps | APP-003 (Checkout Service), APP-015 (Loyalty) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-002 |
| Related knowledge | KN-301, KN-413 |

## Purpose

Stop the creation of, and clean up, orphaned Loyalty (APP-015) accounts provisioned by a
guest-checkout regression. In INC-2026-002, PR-0207 changed Checkout (APP-003) so that every
guest order provisioned a Loyalty account — including for shoppers who never registered —
creating a large population of orphaned, unclaimable accounts. This runbook disables the
guest-loyalty provisioning path via flag, identifies orphaned accounts by guest-order
correlation, quarantines/soft-deletes them, and reconciles. Root cause is a **code
regression**; the hotfix was PR-0312 on story CHK-1421. Checkout is Java/Spring Boot; Loyalty
is Java/PostgreSQL.

## When to use (symptoms / alerts)

- Alert `loyalty-account-create-spike` — `rate(loyalty_account_created_total)` well above
  baseline, correlated with guest-order volume rather than registrations.
- Loyalty (APP-015) reports accounts with no linked identity (APP-014) profile and a
  `source=guest-checkout` provenance.
- A recent Checkout release (in INC-2026-002, PR-0207) touched the guest order-placement or
  post-order loyalty-enrollment path.
- CS reports of unexpected "welcome to Meridian Rewards" notifications to guest shoppers.

## Preconditions

- TEAM-004 on-call (owns the trigger in Checkout); coordinate with TEAM-011 (Loyalty) who own
  APP-015 and its data.
- `kubectl` context on the affected region(s) — INC-2026-002 impacted NA and EU.
- `mcg-flags` CLI; read access to the loyalty PostgreSQL read replica (`loyalty-db-prod-ro`);
  `mcg-loyalty` admin CLI with quarantine/soft-delete permission (requires TEAM-011 approval).
- Know the Checkout release/PR that introduced the regression and its deploy time.

## Procedure

1. **Stop the bleeding — disable guest-loyalty provisioning via flag.** This halts new
   orphan creation immediately without waiting for a deploy:
   ```
   mcg-flags set checkout-service checkout.loyalty.guest_provisioning=false --region <region>
   ```
   Verify propagation across pods (see RB-0018):
   ```
   kubectl -n checkout exec deploy/checkout-service -- \
     curl -s localhost:8081/admin/flags | grep checkout.loyalty.guest_provisioning
   ```
2. **Confirm the creation rate has stopped.** The provisioning spike should flatten within
   the flag propagation window:
   ```
   mcg-metrics query --region <region> \
     'rate(loyalty_account_created_total{source="guest-checkout"}[5m])'
   ```
3. **Identify orphaned accounts.** Query Loyalty for accounts created by the guest-checkout
   path since the regression deploy that have no claimed identity link. Use the read replica:
   ```
   mcg-loyalty query --region <region> --sql "
     SELECT la.account_id, la.created_at, la.guest_order_id
     FROM loyalty_account la
     LEFT JOIN loyalty_identity_link lil ON lil.account_id = la.account_id
     WHERE la.source = 'guest-checkout'
       AND la.created_at >= '<regression_deploy_ts>'
       AND lil.identity_id IS NULL
     ORDER BY la.created_at;"
   ```
   Correlate `guest_order_id` back to Checkout to confirm these came from guest orders, not
   real registrations. Export the `account_id` list to a work file for the batch.
4. **Snapshot before mutating.** Preserve the set so the action is reversible/auditable:
   ```
   mcg-loyalty export --region <region> --account-ids @orphans.txt --out orphans-snapshot.json
   ```
5. **Quarantine (soft-delete) the orphaned accounts.** Do not hard-delete — soft-delete so a
   guest who later registers can still be reconciled, and so the action is reversible:
   ```
   mcg-loyalty account quarantine --region <region> --account-ids @orphans.txt \
     --reason "INC-2026-002 guest-checkout orphan" --soft-delete
   ```
   This sets `status=quarantined`, suppresses points accrual/notifications, and excludes them
   from active-member counts. Batch in chunks (e.g., 500) to avoid long-running transactions.
6. **Suppress downstream side effects.** Cancel any queued "welcome" notifications (APP-023)
   and back out erroneous points for the quarantined set:
   ```
   mcg-loyalty points reverse --region <region> --account-ids @orphans.txt --reason "INC-2026-002"
   ```
7. **Reconcile.** Confirm counts line up — number quarantined equals number identified, and
   active-member metrics return to the expected trendline:
   ```
   mcg-loyalty audit --region <region> --since <regression_deploy_ts> --status quarantined
   ```
8. **Land the code hotfix.** The flag is the mitigation; the durable fix is the hotfix that
   removes the unconditional guest provisioning. It was PR-0312 on story CHK-1421, cut as
   `hotfix/INC-2026-002-guest-loyalty` from the release tag with ≥2 approvals (Tier 0), then
   forward-merged to `main` (CANON §7.3).

## Verification

- `loyalty_account_created_total{source="guest-checkout"}` rate is at/near zero after the flag.
- The orphan query in step 3 returns zero new rows since the flag flip.
- Active-member and account-creation dashboards return to the pre-regression baseline.
- No "welcome to Rewards" notifications sent to guests post-mitigation (`mcg-notify audit --template rewards-welcome --since <ts>`).
- Hotfix PR-0312 merged, forward-merged to `main`, and the flag default aligned with the fix.
- `mcg-synthetics run guest-checkout --region <region>` completes an order without creating a
  loyalty account.

## Rollback

- The mitigation flag is safely reversible: re-enable only after the code fix ships and only
  if intended: `mcg-flags set checkout-service checkout.loyalty.guest_provisioning=true`.
- Account quarantine is soft-delete by design — restore from the snapshot if a batch was
  mis-scoped:
  ```
  mcg-loyalty account restore --region <region> --account-ids @orphans.txt \
    --from orphans-snapshot.json
  ```
- Never hard-delete under fire; soft-delete + reconcile preserves the ability to recover a
  guest who legitimately registers later. No schema down-migration (expand-contract, §7.4).

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-004 regional on-call owns the Checkout trigger and the flag flip.
- **T1 (10 min):** Engage TEAM-011 (Loyalty) — they own APP-015 data and must approve the
  quarantine/soft-delete of accounts; and TEAM-014 (Identity) if link data is in question.
- **Follow-the-sun (Tier 0):** rotate on-call/IC NA (`oncall-checkout-na`) → EU
  (`oncall-checkout-eu`) → APAC (`oncall-checkout-apac`); INC-2026-002 impacted NA and EU.
  Keep `#inc-guest-loyalty` as the single source of truth.
- **T2 (Sev2 or > 20 min):** engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
