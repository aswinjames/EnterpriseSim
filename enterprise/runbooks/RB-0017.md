# RB-0017 — Kafka Consumer Lag Recovery

| Field | Value |
|---|---|

## Purpose

Generic runbook for recovering a Kafka consumer group that has fallen behind, for any MCG
service that consumes events. MCG is event-driven (CANON §8.2): services communicate
asynchronously via versioned, backward-compatible Kafka events, so a lagging consumer
degrades freshness rather than availability. This runbook measures lag, isolates a slow or
stuck partition, scales consumers, handles poison messages via the DLQ, and — only when
authorized — performs a bounded offset reset. It generalizes the pattern behind
INC-2026-003 (search reindex lag) and INC-2026-021 (catalog ingest stall). Core Platform
(TEAM-030) owns the Kafka platform; the consuming squad co-drives.

## When to use (symptoms / alerts)

- Alert `kafka-consumer-lag-high` — `kafka_consumergroup_lag` over threshold for a group, or
  a service's freshness SLO (e.g., search index age, order-event processing age) breached.
- One partition's `LAG` grows while others drain — signature of a slow/stuck partition or a
  poison message.
- Rebalance storms: consumers repeatedly joining/leaving the group.
- Downstream staleness reported by a consumer's service runbook (e.g., RB-0015 catalog).

## Preconditions

- TEAM-030 on-call, co-driving with the consuming squad (TEAM-005 for APP-005, TEAM-003 for
  APP-006, TEAM-006 for APP-009, etc.).
- `kafka-consumer-groups`, `kafka-console-consumer`, `kcat` on the ops jumpbox; broker
  bootstrap `kafka-prod:9092`; `kubectl` context on the affected region.
- Know the **consumer group** and **topic**. An offset reset requires the owning squad's
  explicit authorization and is never done blind.

## Procedure

1. **Measure the lag and locate it.** Describe the group to see per-partition lag:
   ```
   kafka-consumer-groups --bootstrap-server kafka-prod:9092 \
     --describe --group <consumer-group>
   ```
   Read `CURRENT-OFFSET`, `LOG-END-OFFSET`, `LAG`, and `CONSUMER-ID` per partition. Even lag
   across all partitions → under-provisioned/slow consumers (go to step 4). Lag concentrated
   on one partition with others healthy → slow or stuck partition (step 2).
2. **Inspect the stuck partition.** Peek at the next message the group would process without
   committing:
   ```
   kcat -b kafka-prod:9092 -t <topic> -p <partition> \
     -o <current-offset> -c 3 -f 'offset=%o key=%k\n%s\n'
   ```
   A message that repeatedly fails processing (visible as the consumer re-reading the same
   offset, or errors in the consumer logs referencing that key) is a **poison message** →
   step 5. Otherwise it is genuinely slow processing → step 4.
3. **Check consumer health and rebalancing.** Rule out crash-looping or rebalance storms:
   ```
   kubectl -n <ns> get pods -l app=<consumer> -o wide
   kubectl -n <ns> logs deploy/<consumer> --since=10m | grep -Ei 'rebalance|revoked|assigned|error'
   ```
4. **Scale consumers to drain the backlog.** Add consumer instances up to (not beyond) the
   partition count — extra consumers past partition count sit idle:
   ```
   kubectl -n <ns> scale deploy/<consumer> --replicas=<= partition_count>
   kafka-consumer-groups --bootstrap-server kafka-prod:9092 --describe --group <consumer-group>
   ```
   Watch `LAG` trend down. If processing is CPU/IO-bound downstream (e.g., DB writes), scaling
   consumers alone will not help — coordinate with the owning squad on the bottleneck.
5. **Handle a poison message via DLQ.** Route the bad message aside so the partition can
   advance; MCG consumers use a standard retry → DLQ pattern:
   ```
   mcg-kafka dlq route --group <consumer-group> --topic <topic> \
     --partition <p> --offset <o> --reason "poison msg, INC-2026-###"
   ```
   This publishes the offending record to `<topic>.dlq` and advances the consumer past it.
   Never hand-commit past a message without capturing it to the DLQ first — that is silent
   data loss. Triage the DLQ afterward with the owning squad.
6. **Bounded offset reset (authorized only).** If offsets are corrupt or a replay is required
   and the owning squad has authorized it, reset to a timestamp (never blindly to earliest).
   Consumers must be stopped for the reset:
   ```
   kubectl -n <ns> scale deploy/<consumer> --replicas=0
   kafka-consumer-groups --bootstrap-server kafka-prod:9092 --group <consumer-group> \
     --topic <topic> --reset-offsets --to-datetime <ISO8601-ts> --execute
   kubectl -n <ns> scale deploy/<consumer> --replicas=<normal>
   ```
   Prefer `--to-datetime` bounded to the incident window over `--to-earliest`; rely on
   consumer idempotency (upsert/keyed) to make replay safe.
7. **Confirm the group stabilizes.** Watch lag drain and membership settle:
   ```
   watch -n 5 "kafka-consumer-groups --bootstrap-server kafka-prod:9092 \
     --describe --group <consumer-group>"
   ```

## Verification

- `kafka_consumergroup_lag` for the group is at/near zero across all partitions and stable.
- No partition is stuck; `CURRENT-OFFSET` advances on every partition.
- The consuming service's freshness SLO recovers (e.g., search index age, order-event age).
- DLQ count is bounded and triaged; no silent gaps in processed keys.
- `mcg-synthetics` for the affected consumer's journey passes (e.g., catalog offer lookup,
  search freshness, order-event processing).

## Rollback

- Scaling consumers back down to the steady-state replica count is safe once lag is drained:
  `kubectl -n <ns> scale deploy/<consumer> --replicas=<normal>`.
- An offset reset cannot be "undone" — that is why it requires authorization and a bounded
  window; if a reset over-replayed, rely on idempotent processing to converge, and confirm no
  duplicates in the consuming store.
- If a consumer image change was the trigger, roll it back:
  `kubectl -n <ns> rollout undo deploy/<consumer>`.

- **T0 (0–10 min):** TEAM-030 (Core Platform) on-call owns the Kafka platform and this

- **T1 (10 min):** Escalate to the broker/platform SME within TEAM-030 for broker-side issues
  (under-replicated partitions, ISR shrinkage) beyond consumer scaling.
- **Follow-the-sun (Tier 0):** rotate on-call/IC NA (`oncall-platform-na`) → EU

  source of truth.
- **T2 (Sev2 or > 20 min):** engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
