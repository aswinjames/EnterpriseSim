# RB-0009 — Tier-0 Progressive Deploy & Rollback

## Purpose

Define the golden-path progressive delivery procedure for any Tier-0 service: canary →
percentage rollout → full, with automated rollback on SLO breach (CANON §7.2–§7.5). This is
the deploy runbook every Tier-0 squad follows and the one other runbooks reference for
"roll back that release." It also carries the **mandatory promo-cache pre-release check**
that came out of INC-2026-018 (the third promo-cache staleness incident, which drove a
systemic write-through fix and this standing gate) and the deploy-safety lessons from
INC-2026-014 (an edge OIDC regression that reached production). The pipeline is the
golden-path: `lint → build → unit → SAST/SCA → package → deploy(staging) →
integration/contract → DAST → deploy(canary) → progressive rollout`.

## When to use (symptoms / alerts)

- You are shipping a Tier-0 service change (any `APP-` at Tier 0) via `v<semver>` under a
  `REL-YYYY-###` train, or cutting a `hotfix/<INC-ID>-<slug>` from a release tag.
- The deploy dashboard **DevEx / Progressive Delivery** shows a rollout paused, stuck, or
  SLO-gated.
- Alert `deploy-slo-gate-tripped` fired during a canary/rollout and you need to confirm or
  force rollback.
- A dependent runbook (RB-0003/0004/0005/0006/0007/0008) instructed "roll back that release."

## Preconditions

- You are the deploying squad's on-call/release owner; Tier-0 changes require **≥2 approvals**
  (incl. CODEOWNERS; +Security Eng for PCI/auth) per CANON §7.5, and the PR carries a
  rollback plan.
- `kubectl` context on the target region; `mcg-deploy` CLI (Argo Rollouts backed) available.
- The service defines canary SLOs in its `rollout.yaml` analysis template (success rate,
  latency p99, error budget burn).
- For any service that touches pricing/promotions/checkout, the **promo-cache pre-release
  check** (below) is a required gate before canary.

## Procedure

1. **Run the mandatory promo-cache pre-release check (INC-2026-018 gate).** For any change to
   or dependency on APP-007/APP-008/APP-003, confirm promo cache write-through is enabled and
   invalidation is wired before you ship:
   ```
   mcg-deploy precheck promo-cache --service <svc> --release <REL-YYYY-###>
   ```
   It verifies `promo.cache.write_through=true`, that active offers have invalidation hooks,
   and that no stale-cache regression is present. A `FAIL` blocks the deploy — do not
   override; remediate via RB-0002 first.
2. **Confirm the pipeline is green through DAST.** The canary stage only unlocks after all
   prior golden-path gates pass:
   ```
   mcg-deploy status --service <svc> --release <REL-YYYY-###>
   ```
   Expect `staging: deployed`, `integration/contract: pass`, `DAST: pass`. Any red gate stops
   here.
3. **Deploy the canary.** Route a small slice (typically 5%) to the new `v<semver>`:
   ```
   mcg-deploy canary --service <svc> --version v<semver> --region <region> --weight 5
   ```
   Argo Rollouts pins the canary ReplicaSet; the analysis run starts automatically.
4. **Verify canary SLOs before promotion.** Watch the automated analysis; do not promote on a
   hunch:
   ```
   mcg-deploy analysis --service <svc> --region <region>
   kubectl argo rollouts get rollout <svc> -n <ns> --watch
   ```
   Gate on: success rate ≥ SLO, p99 latency within budget, error-budget burn rate < 2x, and
   zero new Sev-worthy alerts for the bake window (≥10 min for Tier 0).
5. **Progress the rollout in steps.** Promote through defined weights, baking at each:
   ```
   mcg-deploy promote --service <svc> --region <region> --to-weight 25
   # bake, re-check analysis, then:
   mcg-deploy promote --service <svc> --region <region> --to-weight 50
   mcg-deploy promote --service <svc> --region <region> --to-weight 100
   ```
   Each `promote` re-evaluates the analysis template; a breach auto-halts and (if configured)
   auto-rolls-back.
6. **Automated rollback on SLO breach.** If the analysis fails, the rollout aborts and shifts
   traffic back to the stable ReplicaSet automatically. Confirm it happened:
   ```
   mcg-deploy status --service <svc> --region <region>   # expect: Degraded → RolledBack
   ```
7. **Manual rollback (when you must pull it yourself).** To abort and revert immediately:
   ```
   mcg-deploy rollback --service <svc> --region <region> --to-previous
   # or, at the platform layer:
   kubectl argo rollouts abort <svc> -n <ns>
   kubectl argo rollouts undo <svc> -n <ns>
   ```
   Confirm the previous `v<semver>` is serving 100%. Because migrations are expand-contract
   (RB-0010), no schema down-migration is needed under fire.
8. **Full promotion.** Once 100% weight bakes clean, mark the release complete:
   ```
   mcg-deploy finalize --service <svc> --release <REL-YYYY-###>
   ```

## Verification

- `mcg-deploy status --service <svc> --region <region>` shows `Healthy` at 100% on
  `v<semver>` (or `RolledBack` to the prior tag if aborted).
- Canary analysis history shows all gates green for the full bake window.
- Service SLO dashboard (success rate, p99, error budget) is nominal for 10 continuous
  minutes post-promotion.
- `mcg-synthetics run <svc>-critical-journey --region <region>` passes.
- The promo-cache precheck record is attached to the release: `mcg-deploy precheck status
  --release <REL-YYYY-###>` shows `PASS`.

## Rollback

- The rollback path **is** steps 6–7; automated on SLO breach, manual via
  `mcg-deploy rollback --to-previous` or `kubectl argo rollouts undo`.
- Rollback reverts the image/version only. Config/flag changes shipped alongside must be
  reverted explicitly (`mcg-flags set ... --region <region>`).
- Never resolve a bad Tier-0 deploy by rolling *forward* under fire unless a hotfix is already
  reviewed (≥2 approvals) — prefer rollback, then fix on a `hotfix/<INC-ID>-<slug>` branch.
- If the DB schema was changed, it was expand-contract (RB-0010); the old code path is still
  valid against the new schema, so version rollback is safe with no down-migration.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** The deploying squad's regional on-call is Incident Commander for the
  rollout.
- **T1 (10 min, unresolved):** Page TEAM-031 (DevEx) for pipeline/Argo Rollouts issues and
  TEAM-030 (Core Platform) for traffic-shifting/edge concerns.
- **Follow-the-sun handoff** for Tier-0 pages: NA → EU → APAC on the owning squad's rotation;
  rotate IC at the regional boundary and keep the release's incident channel as the single
  source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
