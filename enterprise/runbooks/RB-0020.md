# RB-0020 — Hotfix Cut-and-Deploy

| Field | Value |
|---|---|
| Runbook id | RB-0020 |
| Title | Hotfix Cut-and-Deploy |
| Owner team | TEAM-031 (Developer Experience) |
| Apps | All services |
| Severity scope | Sev1–Sev2 |
| Related incidents | INC-2026-002, INC-2026-007 |
| Related knowledge | KN-419 |

## Purpose

Execute the CANON §7.3 hotfix procedure: when a Sev1/Sev2 incident or a critical security
finding requires an out-of-band fix, cut a `hotfix/<INC-ID>-<slug>` branch from the affected
**release tag** (not `main`), make a minimal targeted change, pass expedited-but-mandatory
smoke and security gates, obtain **≥1 approval (≥2 for Tier 0/PCI)**, deploy via the
fast-tracked pipeline, and forward-merge to `main`. This runbook exists so the hotfix path is
disciplined under pressure — no direct pushes, no skipped security gates, no drift between
the deployed hotfix and `main`. The worked example throughout is INC-2026-002 (guest checkout
provisioned orphaned Loyalty accounts), fixed by hotfix PR-0312 under story CHK-1421.

## When to use (symptoms / alerts)

- An active **Sev1 or Sev2** incident where waiting for the normal release train is not
  acceptable and a small, targeted change resolves it.
- A **critical/high security finding** (SAST/DAST/SCA/secret-scan or an external report)
  that must ship before the next scheduled release.
- The fix is **small and surgical** — if it needs broad refactoring, it is not a hotfix; fix
  forward on `main` and roll the normal pipeline instead.
- Example: INC-2026-002 — PR-0207 (in REL-2026-001, tag `v2.3.0` of `mcg-checkout-service`)
  created a Loyalty account for every guest order; a one-line guard was needed immediately.

## Preconditions

- The incident exists in the incident tool with an `INC-YYYY-###` id and an IC assigned.
- You are on the owning squad's on-call (checkout is TEAM-004; the hotfix *machinery* /
  fast-track pipeline is owned by TEAM-031 DevEx).
- You know the **affected release tag** (`mcg-deploy status <service>` shows the currently
  deployed `v<semver>`), the target region(s), and the repo.
- Git access to the `mcg-*` repo; `mcg-deploy` with hotfix privileges; secret manager access
  is **not** needed for code (secrets never live in code — §4.6).
- A Jira hotfix story exists or will be created (CHK-1421 for the worked example).

## Procedure

1. **Confirm the deployed tag you must branch from.** Never branch a hotfix from `main` —
   `main` may contain unreleased changes:
   ```
   mcg-deploy status mcg-checkout-service --region NA
   # deployed: v2.3.0  (REL-2026-001)
   ```
2. **Cut the hotfix branch from that release tag.** Branch name is `hotfix/<INC-ID>-<slug>`
   (CANON §4.1):
   ```
   git fetch --tags origin
   git checkout -b hotfix/INC-2026-002-guest-loyalty v2.3.0
   ```
3. **Make the minimal, targeted change.** Change only what the incident requires. For
   INC-2026-002, guard Loyalty provisioning so it is skipped for guest orders:
   ```
   # in OrderPlacementService: only enroll when the order has an authenticated customerId
   if (order.isGuest()) { skipLoyaltyEnrollment(order); }
   ```
   Add/adjust the regression test that would have caught it (`TC-#####` in TestRail) and
   bump the patch version to `v2.3.1`.
4. **Open the hotfix PR linked to the incident and story.** Push and open the PR with the
   `hotfix` label so the fast-track pipeline is selected:
   ```
   git push -u origin hotfix/INC-2026-002-guest-loyalty
   gh pr create --base main --head hotfix/INC-2026-002-guest-loyalty \
     --title "hotfix(INC-2026-002): skip loyalty enrollment for guest orders (CHK-1421)" \
     --label hotfix --body "Incident INC-2026-002. Story CHK-1421. Rollback: revert to v2.3.0."
   ```
   The PR is PR-0312 in the worked example. The PR template still requires summary, linked
   issue, testing evidence, rollback plan, and risk tier.
5. **Run the fast-tracked pipeline with mandatory gates.** The hotfix pipeline compresses the
   golden path but **never drops** smoke or security gates
   (`lint → build → unit → SAST/SCA → package → smoke → DAST → deploy(canary)`):
   ```
   mcg-deploy hotfix run --pr PR-0312 --incident INC-2026-002 --region NA
   ```
   High/critical security findings still block (§4.6). Integration/contract tests run in the
   expedited smoke subset scoped to the touched boundary (checkout↔loyalty here).
6. **Obtain expedited review approvals.** Still mandatory: **≥1 approval**, **≥2 for Tier 0
   or PCI**. Checkout (APP-003) is Tier 0, so two approvals incl. CODEOWNERS are required:
   ```
   gh pr checks PR-0312     # all required checks green
   gh pr review PR-0312 --approve   # by two CODEOWNERS reviewers
   ```
7. **Deploy via canary, then progressive rollout.** The fast-track still uses progressive
   delivery with auto-rollback (RB-0019); it just skips the fortnightly train coordination:
   ```
   mcg-deploy release mcg-checkout-service --tag v2.3.1 --region NA --strategy canary
   ```
8. **Forward-merge to `main`.** The hotfix MUST land on `main` so it is not lost in the next
   release. Squash-merge the PR; if `main` diverged, cherry-pick/forward-merge and resolve:
   ```
   gh pr merge PR-0312 --squash
   # if main advanced past v2.3.0:
   git checkout main && git merge --no-ff hotfix/INC-2026-002-guest-loyalty
   ```

## Verification

- `mcg-deploy status mcg-checkout-service --region NA` shows `v2.3.1` healthy at 100%.
- The incident's failing signal clears: no new orphaned Loyalty accounts created for guest
  orders (`mcg-loyalty audit --guest --since 30m` returns zero new enrollments).
- `mcg-synthetics run guest-checkout --region NA` passes end to end.
- `git branch --merged main | grep hotfix/INC-2026-002` confirms the forward-merge landed.
- The regression test `TC-#####` is green in the CI run and recorded as a TestRail run `TR-####`.

## Rollback

- If the hotfix itself regresses, roll back the deployment to the prior tag:
  `mcg-deploy rollback mcg-checkout-service --to v2.3.0 --region NA`.
- Because branches are cut from a tag and migrations are expand-contract (§7.4), reverting the
  image is safe and needs no schema down-migration.
- If auto-rollback already engaged during the hotfix canary, follow RB-0019 to confirm state,
  then re-cut a corrected hotfix (`v2.3.2`) rather than overriding the guardrail.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** Owning squad's regional on-call drives the fix; the incident IC owns
  severity and comms.
- **T1 (10 min):** Page TEAM-031 DevEx (`oncall-devex`) if the fast-track pipeline stalls;
  page TEAM-040 Security Eng if a security gate blocks or the trigger is a security finding
  (≥2 reviews incl. Security Eng for PCI/auth code — §7.5).
- **Follow-the-sun handoff** for Tier-0 pages: NA → EU → APAC on-call; rotate IC at the
  regional boundary and keep the incident channel as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
