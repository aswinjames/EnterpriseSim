# RB-0004 — ATP Oversell Reconciliation

| Field | Value |
|---|---|
| Runbook id | RB-0004 |
| Title | ATP Oversell Reconciliation |
| Owner team | TEAM-012 (Inventory) |
| Apps | APP-010 (Inventory Service), APP-009 (Order Management) |
| Severity scope | Sev1–Sev2 |
| Related incidents | INC-2026-012 |
| Related knowledge | KN-307, KN-403 |

## Purpose

Detect and reconcile available-to-promise (ATP) oversell when a reservation race across
multiple warehouses lets APP-010 promise more units of a high-demand SKU than physically
exist, then cancel or backorder the excess and notify Order Management (APP-009). APP-010 is
a Tier-0 Go + PostgreSQL + Redis service; the authoritative on-hand count lives in the WMS
(APP-011) while fast reservations are served from Redis, and drift between them is the
oversell surface. This runbook operationalizes INC-2026-012 (a cross-warehouse reservation
race briefly oversold high-demand SKUs in NA) and its postmortem KN-307.

## When to use (symptoms / alerts)

- PagerDuty alert `inventory-oversell-detected` (`atp_reserved > atp_on_hand` for any
  `sku × warehouse`) or `inventory-ledger-drift` (`redis_reserved != pg_reserved`).
- Grafana dashboard **Inventory / ATP** shows negative `atp_available` on one or more SKUs.
- OMS (APP-009) reports orders accepted that WMS (APP-011) cannot allocate; fulfillment
  exceptions climb on the OMS board.
- CS or merchandising reports "sold out item still orderable" for a flash/high-demand SKU.

## Preconditions

- You are on the TEAM-012 on-call rotation (or the follow-the-sun holder for a Tier-0 page).
- `kubectl` context on the affected region: `kubectl config use-context mcg-<region>-prod`.
- Inventory Service runs in namespace `inventory`; reservation cache is `inventory-redis-prod`;
  the ledger is PostgreSQL `inventory-pg-prod` (table `atp_ledger`).
- `mcg-inv` CLI available; break-glass read access to WMS (APP-011) allocation API.
- You know the affected **SKU(s)** and **warehouse code(s)** — never freeze the whole
  catalog when a handful of SKUs are oversold.

## Procedure

1. **Enumerate oversold SKUs.** Get the authoritative drift list per warehouse:
   ```
   mcg-inv oversell list --region <region> --threshold 0
   ```
   Records show `sku`, `warehouse`, `atp_on_hand`, `atp_reserved`, `oversell_qty`. Copy the
   list into `#inc-inventory-oversell`.
2. **Freeze reservations on affected SKUs only.** Stop the bleeding without taking the whole
   catalog offline:
   ```
   mcg-inv reservation freeze --sku <SKU> --warehouse <WH> --region <region>
   ```
   This flips the SKU to `reserve_disabled` so new checkouts fall back to other warehouses or
   backorder, while existing reservations are preserved for reconciliation.
3. **Snapshot the ledger vs. WMS truth.** Compare the Redis reservation counter, the
   PostgreSQL `atp_ledger`, and WMS on-hand:
   ```
   redis-cli -h inventory-redis-prod GET atp:reserved:<SKU>:<WH>
   psql -h inventory-pg-prod -c "SELECT reserved, on_hand FROM atp_ledger WHERE sku='<SKU>' AND wh='<WH>';"
   mcg-inv wms onhand --sku <SKU> --warehouse <WH>
   ```
   WMS on-hand is the tiebreaker source of truth.
4. **Reconcile the ledger to WMS.** Re-derive `atp_reserved` from the durable order
   reservations and rewrite the ledger + cache atomically:
   ```
   mcg-inv reconcile --sku <SKU> --warehouse <WH> --source wms --region <region>
   ```
   The command recomputes `atp_available = on_hand - valid_reservations`, corrects
   `atp_ledger`, and refreshes the Redis counter under the per-SKU lock introduced after
   INC-2026-012.
5. **Resolve the excess reservations.** For orders that can no longer be honored, cancel or
   backorder the surplus, oldest-reservation-wins by reservation timestamp:
   ```
   mcg-inv oversell resolve --sku <SKU> --warehouse <WH> --strategy backorder-then-cancel --region <region>
   ```
   Use `--strategy cancel` only when backorder is disallowed for the SKU.
6. **Notify OMS.** Emit the reconciliation events so APP-009 updates order state and triggers
   customer comms (via APP-023):
   ```
   mcg-inv oms notify --batch <RECON_BATCH_ID>
   ```
   Confirm OMS consumed them: `mcg-oms events tail --topic inventory.reservation.reconciled`.
7. **Unfreeze once corrected.** After the ledger matches WMS, re-enable reservations:
   ```
   mcg-inv reservation unfreeze --sku <SKU> --warehouse <WH> --region <region>
   ```

## Verification

- `mcg-inv oversell list --region <region> --threshold 0` returns empty for 10 continuous
  minutes.
- For each reconciled SKU, `redis-cli GET atp:reserved:<SKU>:<WH>` equals the `reserved`
  column in `atp_ledger` (no cache/ledger drift).
- `atp_available >= 0` for all affected SKUs on the Inventory / ATP board.
- OMS shows every surplus order moved to `backordered` or `cancelled`; no orders remain in
  `awaiting_allocation` for the affected SKUs.
- `mcg-synthetics run reserve-atp --sku <SKU> --region <region>` respects the corrected count.

## Rollback

- Reconciliation corrects derived state to match WMS truth and is not itself rolled back.
- If `mcg-inv reconcile` picked the wrong source and over-corrected, replay from the
  reservation event log: `mcg-inv reconcile --sku <SKU> --warehouse <WH> --source event-log
  --replay-from <ts>`.
- If the trigger was a bad Inventory release (the INC-2026-012 race was introduced by
  REL-2026-006), roll that service back per RB-0009 rather than repeatedly reconciling.
- Do not restore PostgreSQL from a snapshot for drift; the ledger is reconstructable from
  WMS on-hand plus the durable reservation log.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-012 regional on-call is Incident Commander for Inventory.
- **T1 (10 min, unresolved):** Loop in TEAM-006 (Order Management) since order state is
  customer-visible, and TEAM-013 (Warehouse & Fulfillment) for WMS on-hand disputes — all
  co-owned INC-2026-012.
- **Follow-the-sun handoff** for Tier-0 pages: NA (`oncall-inventory-na`) → EU
  (`oncall-inventory-eu`) → APAC (`oncall-inventory-apac`); rotate IC at the regional
  boundary and keep `#inc-inventory-oversell` as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
