# RB-0024 — Inventory Reservation Reconciliation Job

| Field | Value |
|---|---|
| Runbook id | RB-0024 |
| Title | Inventory Reservation Reconciliation Job |
| Owner team | TEAM-012 (Inventory) |
| Apps | APP-010 (Inventory Service) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-012 |
| Related knowledge | KN-423 |

## Purpose

Run and interpret the reservation reconciliation job that repairs drift between the three
sources of inventory truth: the **reservation ledger** in Redis (fast available-to-promise
holds), the **source-of-truth PostgreSQL** inventory (durable on-hand and committed counts),
and **WMS** (APP-011) physical counts. Drift causes either phantom unavailability (stale holds
never released) or, worse, **oversell** — the failure class in INC-2026-012, where a
reservation race across warehouses briefly allowed oversell on high-demand SKUs. This runbook
covers running the job manually, dry-run vs apply, reading the drift report, releasing stale
reservations, and preventing oversell. APP-010 is Go + PostgreSQL + Redis. It complements
RB-0004 (which addresses the live oversell-guard / ATP path); this runbook is the batch
repair.

## When to use (symptoms / alerts)

- Alert `inventory-drift-detected` — scheduled reconciliation flagged
  `redis_reserved != pg_reserved` beyond tolerance for one or more SKUs.
- Alert `atp-oversell-suspected` or OMS (APP-009) reports orders accepted for SKUs whose true
  ATP was zero (the INC-2026-012 signature).
- Grafana **Inventory / Reservations** shows `stale_reservation_count` climbing (holds past
  their expiry not released) or `atp_negative_skus > 0`.
- WMS reconciliation feed shows physical counts diverging from APP-010's on-hand.
- After a deploy or a Redis incident (see RB-0001/RB-0023) where the ledger may have drifted.

## Preconditions

- You are on TEAM-012 (Inventory) on-call (or the follow-the-sun holder for a Tier-0 page).
- `kubectl` context on the affected region; `mcg-inventory` CLI, `psql`, and `redis-cli` on
  the ops jumpbox. DB/Redis credentials from the platform secret manager
  (`mcg-secrets get inventory/pg/prod`, `.../redis/prod`) — never from logs.
- APP-010 runs in namespace `inventory`; ledger in `inv-redis-prod`
  (keys `inv:resv:{<sku>}:<warehouseId>`), truth in `pg-inventory-prod` (tables
  `inventory_onhand`, `inventory_reservation`), WMS counts via APP-011's reconciliation topic.
- Coordinate with TEAM-006 (OMS) and TEAM-013 (WMS) if drift spans order or warehouse state.
- **Always dry-run before apply.** Applying reconciliation mutates durable inventory.

## Procedure

1. **Scope the drift.** Get a fast read of which SKUs/warehouses are drifting before running
   the full job:
   ```
   mcg-inventory recon scan --region <region> --tolerance 0
   ```
   This compares Redis ledger vs PG truth vs the latest WMS counts and prints the count of
   drifting `(sku, warehouse)` pairs by drift type.
2. **Run the reconciliation job in DRY-RUN.** Never apply blind. Dry-run computes the repair
   plan without mutating anything:
   ```
   mcg-inventory recon run --mode dry-run --region <region> \
     --sources redis,pg,wms --report /tmp/recon-<date>.json
   ```
   For a targeted repair, add `--sku <SKU>` and/or `--warehouse <WH_ID>`.
3. **Read the drift report.** Interpret the three drift classes it emits:
   - `stale_reservation` — a Redis hold past its expiry still counted against ATP (release it).
   - `orphan_reservation` — a Redis hold with no matching PG reservation row (release it).
   - `phantom_commit` — a PG committed count with no WMS physical basis (needs WMS
     reconciliation, coordinate with TEAM-013).
   - `oversell_risk` — `sum(reservations) > on_hand` for a SKU/warehouse (the INC-2026-012
     case — highest priority).
   ```
   mcg-inventory recon report /tmp/recon-<date>.json --summary
   ```
4. **Release stale/orphan reservations (targeted).** Apply only the safe release classes
   first; this frees ATP without risking oversell:
   ```
   mcg-inventory recon apply --report /tmp/recon-<date>.json \
     --only stale_reservation,orphan_reservation --region <region>
   ```
   Under the hood this deletes the expired ledger keys and marks the PG reservation rows
   `released`, then republishes an ATP update event on Kafka.
5. **Resolve oversell risk conservatively.** For `oversell_risk`, prefer to **reduce ATP to
   the true on-hand** (fail closed) rather than accept more orders. Apply the oversell-guard
   correction:
   ```
   mcg-inventory recon apply --report /tmp/recon-<date>.json \
     --only oversell_risk --clamp-atp-to-onhand --region <region>
   ```
   Escalate affected in-flight orders to TEAM-006 (OMS) for allocation review — do not silently
   cancel orders from this job.
6. **Reconcile WMS phantom commits.** For `phantom_commit`, trigger a WMS count sync and
   re-run recon after it lands (physical truth wins for on-hand):
   ```
   mcg-inventory wms-sync trigger --warehouse <WH_ID> --region <region>
   ```
7. **Verify no new oversell path remains.** Confirm the live ATP guard is intact (this is
   RB-0004's domain) so the drift does not immediately recur:
   ```
   mcg-flags get inventory-service inventory.atp.oversell_guard --region <region>   # expect true
   ```

## Verification

- `mcg-inventory recon scan --tolerance 0` returns **zero** drifting pairs (or only known,
  WMS-pending `phantom_commit` entries being tracked separately).
- `atp_negative_skus = 0` and `stale_reservation_count` back to baseline on the
  **Inventory / Reservations** board.
- For any `oversell_risk` SKU, `sum(active reservations) ≤ on_hand` in PG:
  ```
  psql -h pg-inventory-prod -U mcg_admin -c "
    SELECT sku, warehouse_id, on_hand,
           (SELECT count(*) FROM inventory_reservation r
            WHERE r.sku=o.sku AND r.warehouse_id=o.warehouse_id AND r.status='active') AS resv
    FROM inventory_onhand o WHERE sku = '<SKU>';"
  ```
- OMS (APP-009) confirms no further orders accepted beyond true ATP for the affected SKUs.
- `mcg-synthetics run inventory-atp --sku <SKU> --region <region>` returns the corrected ATP.

## Rollback

- The job is **idempotent** and audited; every apply writes a reversible batch id. To undo the
  last apply (e.g. a release that shouldn't have happened):
  ```
  mcg-inventory recon undo --batch <batch-id> --region <region>
  ```
- Releasing stale/orphan reservations is safe and normally not rolled back (those holds were
  invalid). `clamp-atp-to-onhand` is conservative (fails closed) and safe to keep.
- Expand-contract migrations (§7.4) mean PG schema changes never require a down-migration
  during reconciliation.
- If a bad Inventory release caused the drift, roll that release back (RB-0020) before
  re-running, or the drift will recur.
