# RB-0015 — Catalog Ingestion Stall Recovery

| Field | Value |
|---|---|
| Runbook id | RB-0015 |
| Title | Catalog Ingestion Stall Recovery |
| Owner team | TEAM-005 (Catalog) |
| Apps | APP-005 (Product Catalog) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-021 |
| Related knowledge | KN-314, KN-414 |

## Purpose

Detect and recover a stalled catalog offer-ingestion pipeline after an upstream dependency
outage, then resume/replay from the last committed offset and confirm clean catch-up with no
duplicate offers. In INC-2026-021 a brief Enterprise Data Platform (APP-020) outage stalled
catalog offer ingestion across NA/EU/APAC; ingestion caught up once the platform recovered.
Root cause is a **dependency failure**, not a Catalog code or config bug — so the fix is to
confirm upstream recovery and resume consumption idempotently, not to roll anything back.
APP-005 is Java/PostgreSQL/OpenSearch and consumes offer feeds over Kafka.

## When to use (symptoms / alerts)

- Alert `catalog-ingestion-stalled` — `catalog_ingest_last_commit_age_seconds` exceeding
  threshold, or consumer lag on the offer-ingest topic climbing (see RB-0017).
- Grafana **Catalog / Ingestion** shows `catalog_offers_ingested_total` flat while upstream
  offer events are being produced.
- An APP-020 (Data Platform) incident or maintenance overlaps the stall window.
- Search (APP-006) / storefront show stale offer data because Catalog stopped updating.

## Preconditions

- TEAM-005 on-call; `kubectl` context on the affected region(s) — INC-2026-021 hit NA, EU
  and APAC.
- `kafka-consumer-groups` tooling on the ops jumpbox; `mcg-catalog` admin CLI; read access to
  the catalog PostgreSQL (`catalog-db-prod-ro`) and OpenSearch (`catalog-search-prod`).
- Catalog Service runs in namespace `catalog` as deploy/catalog-service; the ingest consumer
  group is `catalog-offer-ingest`; source topic `offers.ingest.v1`.
- Confirm whether APP-020 is the trigger via the incident channel / StatusPage.

## Procedure

1. **Confirm the stall and its shape.** Check ingest freshness and consumer lag:
   ```
   mcg-catalog ingest status --region <region>
   kafka-consumer-groups --bootstrap-server kafka-prod:9092 \
     --describe --group catalog-offer-ingest
   ```
   Note `CURRENT-OFFSET`, `LOG-END-OFFSET` and `LAG` per partition, and the last committed
   offset — this is the resume point. A uniformly frozen `CURRENT-OFFSET` across partitions
   with growing lag is the signature of an upstream stall, not a poison message.
2. **Confirm upstream (APP-020) recovery before resuming.** Resuming into a still-down
   platform just re-stalls:
   ```
   mcg-dep check --app APP-020 --region <region>
   mcg-catalog ingest source-health --region <region>
   ```
   Wait for APP-020 to report healthy (or confirm in its incident record) before continuing.
3. **Resume the consumer from the last committed offset (primary action).** The consumer is
   idempotent (offers keyed by `offer_id` + `version`, upsert semantics), so resuming from the
   committed offset will not duplicate:
   ```
   mcg-catalog ingest resume --region <region> --group catalog-offer-ingest
   ```
   If the consumer pods are wedged, restart to force a clean rejoin/rebalance:
   ```
   kubectl -n catalog rollout restart deploy/catalog-ingest-worker
   kubectl -n catalog rollout status deploy/catalog-ingest-worker
   ```
4. **Replay a gap only if offsets were lost.** If the committed offset was lost (rare — only
   if the group's `__consumer_offsets` were affected), replay explicitly from the last
   good watermark rather than resetting to earliest:
   ```
   mcg-catalog ingest replay --region <region> --from-timestamp <upstream_last_healthy_ts>
   ```
   Do **not** `--reset-offsets --to-earliest` — that would reprocess the full backlog; rely on
   idempotent upsert but bound the replay window to the outage.
5. **Watch catch-up drain the lag.** Ingest throughput should spike as it processes the
   backlog:
   ```
   watch -n 5 "kafka-consumer-groups --bootstrap-server kafka-prod:9092 \
     --describe --group catalog-offer-ingest"
   ```
   Lag should trend to zero. See RB-0017 if a single partition stays stuck (poison message).
6. **Reindex any offers that missed the search projection.** Ensure OpenSearch reflects the
   caught-up state:
   ```
   mcg-catalog reindex --region <region> --since <upstream_last_healthy_ts> --incremental
   ```
7. **Check for duplicates introduced by the replay.** Confirm the upsert held and no offer
   was double-written:
   ```
   mcg-catalog query --region <region> --sql "
     SELECT offer_id, COUNT(*) FROM catalog_offer
     WHERE updated_at >= '<upstream_last_healthy_ts>'
     GROUP BY offer_id HAVING COUNT(*) > 1;"
   ```
   Zero rows = no duplicates.

## Verification

- Consumer lag on `catalog-offer-ingest` is at/near zero across all partitions.
- `catalog_ingest_last_commit_age_seconds` back within threshold; `catalog-ingestion-stalled`
  alert clears.
- `catalog_offers_ingested_total` resumes climbing at the normal rate.
- Duplicate query in step 7 returns zero rows.
- OpenSearch offer count/freshness matches PostgreSQL; `mcg-synthetics run catalog-offer-lookup --region <region>` returns current offer data.
- Downstream Search (APP-006) reflects fresh offers.

## Rollback

- There is nothing to roll back — the trigger was an upstream outage, and recovery is resume/
  replay of idempotent ingestion, not a change to Catalog.
- If a manual `replay` was scoped too wide and caused churn, it is self-healing via upsert;
  no data down-migration is needed (expand-contract, CANON §7.4).
- If a consumer restart picked up a bad image, roll back the worker deployment:
  `kubectl -n catalog rollout undo deploy/catalog-ingest-worker` and confirm the prior
  `v<semver>` tag.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-005 regional on-call owns Catalog ingestion; acts as Ops lead.
- **T1 (10 min):** Engage TEAM-060 (Data Platform) — they own APP-020, the upstream root
  cause — and TEAM-030 (Core Platform) if the stall is a Kafka/consumer-group problem (RB-0017).
- **Follow-the-sun (Tier 0):** rotate on-call/IC NA (`oncall-catalog-na`) → EU
  (`oncall-catalog-eu`) → APAC (`oncall-catalog-apac`); INC-2026-021 impacted all three
  regions. Keep `#inc-catalog-ingest` as the single source of truth.
- **T2 (Sev2 or > 20 min):** engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
