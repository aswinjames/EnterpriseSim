# RB-0023 — Cart Redis Cache Flush & Warm

| Field | Value |
|---|---|
| Runbook id | RB-0023 |
| Title | Cart Redis Cache Flush & Warm |
| Owner team | TEAM-004 (Cart & Checkout) |
| Apps | APP-004 (Cart Service) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-001 |
| Related knowledge | KN-300, KN-422 |

## Purpose

Remove corrupted or poisoned cart entries from the Redis backing APP-004 — bad serialization,
a schema mismatch after a deploy, or a poison key that crashes readers — as distinct from a
Redis **failover** (that is RB-0001). Cart state is ephemeral (TTL 24h) and reconstructable by
the client on the next request, which makes targeted deletion and even a guarded full flush
acceptable when the cache holds bad data. The goal is to delete only what is poisoned, prefer
the narrowest scope (key pattern → single shard → full flush), and warm the cache so checkout
(APP-003) does not hit a cold start. APP-004 is Go + Redis. INC-2026-001's postmortem (KN-300)
motivated clearer separation between failover recovery and cache-hygiene actions.

## When to use (symptoms / alerts)

- Alert `cart-deserialize-error-ratio > 1% (5m)` or `cart-read-panic` — Cart Service logs
  show `gob: decode` / `json: cannot unmarshal` / `unknown schema version` on cart reads.
- A Cart Service deploy in the last 30 min changed the cart value schema and older cached
  entries no longer deserialize (schema mismatch), but Redis itself is healthy
  (`redis_master_link_status = up`, no failover event).
- Grafana **Cart / Redis** shows normal cluster health but elevated application-level read
  errors and customers seeing "We couldn't load your cart".
- A specific SKU/offer or a bad producer wrote a poison value that repeatedly crashes readers.

## Preconditions

- You are on TEAM-004 on-call (or the follow-the-sun holder for a Tier-0 page).
- **First rule out failover** — if a primary is down or promoting, this is RB-0001, not this
  runbook. Confirm cluster health before flushing anything.
- `kubectl` context on the affected region; `redis-cli` via the ops jumpbox; Redis auth token
  from the platform secret manager (`mcg-secrets get cart/redis/prod`) — never from logs.
- Cart Service runs in namespace `cart`; Redis is `cart-redis-prod` (3 shards, 1 replica each).
- Cart keys follow `cart:{<cartId>}` (hash-tagged for shard locality); session index at
  `cart:idx:session:<sessionId>`.

## Procedure

1. **Confirm this is corruption, not failover.** Check cluster health so you don't flush
   during a promotion:
   ```
   redis-cli -h cart-redis-prod --cluster check cart-redis-prod:6379
   ```
   All slots covered + a healthy master per shard means this is a data problem → continue. A
   down/promoting master means stop and use RB-0001.
2. **Identify the poison scope.** Reproduce the deserialize failure and capture the offending
   key(s) from the error logs:
   ```
   kubectl -n cart logs deploy/cart-service --since=15m | \
     grep -E 'decode|unmarshal|unknown schema' | mcg-logql top-keys
   ```
   Determine whether it is a few keys, one shard, or a schema-wide mismatch.
3. **Freeze the bad writer if a producer is poisoning keys.** If a deploy is actively writing
   bad values, stop the bleeding first — roll it back (RB-0020 / owning deploy runbook) or flag
   off the offending write path:
   ```
   mcg-flags set cart-service cart.write.<feature>=false --region <region>
   ```
4. **Targeted key deletion (preferred).** Delete only the poisoned keys by pattern; scan (do
   not `KEYS`) and batch-delete on the owning shard:
   ```
   redis-cli -h cart-redis-prod --scan --pattern 'cart:{*}:schema:v3' | \
     xargs -n 500 redis-cli -h cart-redis-prod DEL
   ```
   Cart state is client-reconstructable, so deleting a stale-schema key simply forces a clean
   rebuild on next request.
5. **Selective single-shard flush.** If corruption is confined to one shard, flush just that
   shard's keyspace (never the whole cluster):
   ```
   redis-cli -h cart-redis-prod -p 6379 -c CLUSTER NODES   # find the shard master
   redis-cli -h <shard-master-host> -p <shard-port> FLUSHDB
   ```
6. **Guarded full flush (last resort, authorized).** Only with IC approval and only because
   cart state is ephemeral + reconstructable. Confirm no failover in flight (step 1), then:
   ```
   redis-cli -h cart-redis-prod --scan --pattern 'cart:*' | \
     xargs -n 500 redis-cli -h cart-redis-prod DEL
   ```
   Do **not** `FLUSHALL` the cluster during a peak/flash sale without explicit authorization —
   it cold-starts every active cart at once.
7. **Warm the cache.** Pre-warm hot carts so checkout does not stampede a cold cache; the
   warmer replays recent active sessions from the write-ahead source:
   ```
   mcg-cart cache warm --region <region> --active-sessions --since 1h
   ```
8. **Re-enable any writer you froze** once schema alignment is confirmed:
   `mcg-flags set cart-service cart.write.<feature>=true --region <region>`.

## Verification

- `cart-deserialize-error-ratio` back under 0.2% for 5 continuous minutes on the
  **Cart / Redis** board; no read panics in `cart-service` logs.
- A test cart round-trips cleanly: `mcg-synthetics run cart-add-item --region <region>` → 200,
  then `cart-fetch` returns the expected items.
- Spot-check a previously-poisoned key is gone and rebuilds:
  `redis-cli -h cart-redis-prod GET 'cart:{<cartId>}'` → `(nil)` then repopulates on next read.
- Cache hit ratio recovers after warm-up (`cart_cache_hit_ratio` back to baseline).
- Cluster still healthy: `--cluster check` reports "All 16384 slots covered".

## Rollback

- Cache deletion/flush is not reversible and needs no rollback — cart is derived, ephemeral
  (TTL 24h), and client-reconstructable.
- If the trigger was a bad Cart Service release (schema change), roll that release back per
  RB-0020 rather than repeatedly flushing; then re-warm.
- Do **not** restore Redis from a snapshot for a cache-hygiene problem; a stale snapshot would
  reintroduce the poisoned entries.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-004 regional on-call owns cart cache correctness and is Incident
  Commander.
- **T1 (10 min, unresolved):** Loop TEAM-030 (Core Platform) if Redis cluster behavior is
  implicated (as opposed to pure data corruption); loop the producing squad if an upstream
  service wrote the poison values.
- **Follow-the-sun handoff** for Tier-0 pages: NA (`oncall-cart-na`) → EU (`oncall-cart-eu`) →
  APAC (`oncall-cart-apac`); rotate IC at the regional boundary, keep the incident channel
  `#inc-cart-redis` as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
