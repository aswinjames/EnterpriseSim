# RB-0001 — Cart Redis Primary Failover Recovery

| Field | Value |
|---|---|
| Runbook id | RB-0001 |
| Title | Cart Redis Primary Failover Recovery |
| Owner team | TEAM-004 (Cart & Checkout) |
| Apps | APP-004 (Cart Service) |
| Severity scope | Sev1–Sev2 |
| Related incidents | INC-2026-001 |
| Related knowledge | KN-300, KN-400 |

## Purpose

Restore cart write availability when the Redis primary backing APP-004 fails over to a
replica. Cart state (line items, pricing preview) is held in a Redis cluster; a primary
loss forces a replica promotion during which writes fail closed. This runbook shortens the
error window observed in INC-2026-001 (9 minutes of elevated cart-write errors before
promotion completed) and confirms clean recovery.

## When to use (symptoms / alerts)

- PagerDuty alert `cart-redis-primary-down` or `CartWriteErrorRatio > 2% (5m)`.
- Grafana dashboard **Cart / Redis** shows `redis_connected_clients` dropping to zero on one
  shard and `redis_master_link_status = down` on its replicas.
- Storefront (APP-001) surfaces "We couldn't update your cart" toasts; checkout (APP-003)
  `cart.fetch` spans error out with `REDIS_LOADING` / `READONLY` responses.
- Sentinel/cluster event `+failover-state-select-slave` in Redis logs.

## Preconditions

- You are on the TEAM-004 on-call rotation (or the follow-the-sun holder for a Tier-0 page).
- `kubectl` context set to the affected region cluster: `kubectl config use-context mcg-<region>-prod`.
- `redis-cli` available via the ops jumpbox; Redis auth token pulled from the platform
  secret manager (`mcg-secrets get cart/redis/prod`).
- Cart Service runs in namespace `cart`; Redis runs as a managed cluster (`cart-redis-prod`)
  with 3 shards, 1 replica each, fronted by Sentinel.

## Procedure

1. **Declare and size the blast radius.** Confirm which shard failed:
   ```
   kubectl -n cart exec deploy/cart-service -- \
     redis-cli -h cart-redis-prod --cluster check cart-redis-prod:6379
   ```
   Note the shard whose master is unreachable and the slot range it owns.
2. **Check Sentinel is already promoting.** Sentinel should auto-promote within ~10s:
   ```
   redis-cli -h sentinel-cart-prod -p 26379 sentinel masters
   ```
   Look for `flags=master` on the promoted replica. If a replica is `flags=s_down,slave`
   and no promotion is in flight, Sentinel quorum may be lost — go to step 5.
3. **Fail cart writes soft, not hard.** Enable the cart degraded-mode flag so writes are
   retried against the newly promoted primary instead of erroring to the customer:
   ```
   mcg-flags set cart-service cart.redis.degraded_mode=true --region <region>
   ```
   This routes writes through the retry/queue path (backed by the local write-behind buffer)
   for up to 60s.
4. **Force promotion if Sentinel stalled.** Only if step 2 shows no promotion after 30s:
   ```
   redis-cli -h sentinel-cart-prod -p 26379 sentinel failover cart-mymaster-<shard>
   ```
5. **Restore quorum if Sentinel is down.** If fewer than 2 Sentinels are healthy, scale the
   Sentinel StatefulSet back to 3 and wait for quorum:
   ```
   kubectl -n cart scale statefulset cart-redis-sentinel --replicas=3
   kubectl -n cart rollout status statefulset cart-redis-sentinel
   ```
6. **Reconnect the service.** Cart Service uses lazy reconnection; force a pool refresh so it
   picks up the new primary without a full restart:
   ```
   kubectl -n cart exec deploy/cart-service -- curl -s -XPOST localhost:8081/admin/redis/reconnect
   ```
   If reconnect endpoint is unresponsive, do a rolling restart: `kubectl -n cart rollout restart deploy/cart-service`.
7. **Rehydrate the replica.** Confirm the old primary (once healthy) rejoins as a replica:
   ```
   redis-cli -h <old-primary> replicaof <new-primary> 6379
   ```

## Verification

- `CartWriteErrorRatio` back under 0.5% for 5 continuous minutes on the Cart / Redis board.
- `redis_master_link_status = up` on all replicas; `--cluster check` reports "All 16384 slots covered".
- Synthetic canary passes: `mcg-synthetics run cart-add-item --region <region>` returns 200.
- Drain the write-behind buffer to zero: dashboard panel `cart_writebehind_queue_depth = 0`.
- Disable degraded mode once error ratio is nominal: `mcg-flags set cart-service cart.redis.degraded_mode=false --region <region>`.

## Rollback

- Nothing to roll back if this was an organic failover; the "change" here is degraded-mode
  and forced-failover, both of which are reverted in Verification.
- If a rolling restart introduced a bad image, roll back the Cart Service deployment:
  `kubectl -n cart rollout undo deploy/cart-service` and confirm the previous `v<semver>` tag.
- Do **not** restore Redis from a snapshot for a transient failover; cart state is
  ephemeral (TTL 24h) and reconstructable from the client on next request.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-004 regional on-call is Incident Commander for the shard.
- **T1 (10 min, unresolved):** Page TEAM-030 (Core Platform) for Redis/cluster support and
  hand the primary/Sentinel steps to them.
- **Follow-the-sun handoff** for Tier-0 pages: NA (`oncall-cart-na`) → EU (`oncall-cart-eu`)
  → APAC (`oncall-cart-apac`); rotate IC at the regional boundary, keep the incident channel
  `#inc-cart-redis` as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) Incident Commander and follow RB-0011.
