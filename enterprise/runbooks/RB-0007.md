# RB-0007 — Search Reindex Lag Recovery

| Field | Value |
|---|---|
| Runbook id | RB-0007 |
| Title | Search Reindex Lag Recovery |
| Owner team | TEAM-003 (Search & Discovery) |
| Apps | APP-006 (Search & Browse) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-003 |
| Related knowledge | KN-302, KN-406 |

## Purpose

Recover catalog-to-index freshness when propagation lag on the catalog→search Kafka stream
causes APP-006 to surface stale data (most visibly stale prices) in search results. APP-006
(Python + OpenSearch + Kafka) consumes catalog/price change events from APP-005 and projects
them into the OpenSearch index; when the consumer falls behind, results reflect an old
snapshot. This runbook operationalizes INC-2026-003 (catalog-to-index propagation lag briefly
showed stale prices in NA search results after REL-2026-002) and its postmortem KN-302.
Respect the dependency direction: Search reads from Catalog, never the reverse.

## When to use (symptoms / alerts)

- PagerDuty/warning alert `search-index-lag-high` (`kafka_consumer_lag{group="search-indexer"}
  > 50k (5m)`) or `search-freshness-slo-breach`.
- Grafana dashboard **Search / Indexing** shows `index_propagation_seconds` p99 exceeding the
  60s freshness SLO, and `catalog_events_consumed_rate` sagging below produced rate.
- Search results show prices/attributes that disagree with Catalog (APP-005) /
  Pricing (APP-007) truth for a set of SKUs.
- CS or merchandising reports "search shows the wrong price" shortly after a catalog/price
  update.

## Preconditions

- You are on the TEAM-003 on-call rotation (or the follow-the-sun holder for a Tier-0 page).
- `kubectl` context on the affected region: `kubectl config use-context mcg-<region>-prod`.
- Search Service runs in namespace `search`; the indexer consumes topic
  `catalog.offer.changed`; the OpenSearch cluster is `search-os-prod`.
- `mcg-search` CLI and Kafka admin (`mcg-kafka`) available; read access to Catalog truth via
  `mcg-catalog`.

## Procedure

1. **Measure the lag precisely.** Confirm which partitions are behind:
   ```
   mcg-kafka lag --group search-indexer --topic catalog.offer.changed --region <region>
   ```
   Note partitions with high `lag` and whether lag is growing (producer outpacing consumer)
   or draining. Cross-check the consumer health:
   ```
   kubectl -n search get deploy search-indexer -o wide
   ```
2. **Confirm the indexer is healthy, then scale consumption.** If pods are healthy but lag is
   high, add consumer parallelism up to the partition count:
   ```
   kubectl -n search scale deploy search-indexer --replicas=<= num_partitions>
   kubectl -n search rollout status deploy search-indexer
   ```
   If pods are crash-looping (poison message), capture the offset before scaling:
   `kubectl -n search logs deploy/search-indexer --tail=200 | grep -i 'deserialize\|poison'`.
3. **Drain the backlog.** Let the scaled consumers catch up; watch lag trend toward zero:
   ```
   watch -n 15 'mcg-kafka lag --group search-indexer --topic catalog.offer.changed --region <region>'
   ```
   If a single poison event blocks a partition, skip it deliberately (and file a bug):
   ```
   mcg-search indexer skip-offset --partition <P> --offset <O> --region <region>
   ```
4. **Identify the affected SKUs.** Determine which documents are stale rather than reindexing
   everything:
   ```
   mcg-search freshness diff --since <incident_start_ts> --region <region>
   ```
   This lists SKUs whose indexed value differs from Catalog/Pricing truth.
5. **Targeted partial reindex.** Reproject only the affected SKUs from Catalog truth (cheaper
   and faster than a full reindex, which cold-starts relevance):
   ```
   mcg-search reindex --skus @affected-skus.txt --source catalog --region <region>
   ```
   For a bounded campaign/category, `mcg-search reindex --category <CAT> --source catalog`.
6. **Verify freshness restored.** Re-run the diff and confirm zero drift:
   ```
   mcg-search freshness diff --since <incident_start_ts> --region <region>
   ```

## Verification

- `kafka_consumer_lag{group="search-indexer"}` back under 1k and flat for 10 continuous
  minutes on the Search / Indexing board.
- `index_propagation_seconds` p99 back within the 60s freshness SLO.
- `mcg-search freshness diff` returns empty for the affected window.
- `mcg-synthetics run search-price-check --sku <SKU> --region <region>` shows the search
  result price matching Pricing (APP-007) truth.
- Spot-check the live index: `curl -s search-os-prod:9200/products/_doc/<SKU> | jq '.\_source.price'`
  equals Catalog truth.

## Rollback

- Reindexing corrects derived state and is not itself rolled back.
- If you scaled the indexer up, scale back to steady-state replicas once lag is nominal:
  `kubectl -n search scale deploy search-indexer --replicas=<baseline>`.
- If a full reindex was triggered and relevance/latency regressed while warming, prefer
  serving from the prior index alias until warm:
  `mcg-search alias switch products --to products-prev` then switch back once warm.
- If the lag was caused by a bad indexer release (INC-2026-003 followed REL-2026-002), roll
  that service back per RB-0009 rather than repeatedly draining.

- **T0 (0–10 min):** TEAM-003 regional on-call owns index freshness and is Incident Commander.
- **T1 (10 min, unresolved):** Loop in TEAM-005 (Catalog) if the producer side is emitting
  incorrectly or lagging, and TEAM-030 (Core Platform) for Kafka/OpenSearch cluster health.
- **Follow-the-sun handoff** for Tier-0 pages: NA (`oncall-search-na`) → EU
  (`oncall-search-eu`) → APAC (`oncall-search-apac`); rotate IC at the regional boundary and
  keep `#inc-search-index` as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
