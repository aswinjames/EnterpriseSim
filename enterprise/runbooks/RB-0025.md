# RB-0025 — Storefront Origin Saturation & Edge Cache Recovery

| Field | Value |
|---|---|
| Runbook id | RB-0025 |
| Title | Storefront Origin Saturation & Edge Cache Recovery |
| Owner team | TEAM-001 (Storefront Experience) |
| Apps | APP-001 (Storefront Web), APP-024 (API Gateway / Edge) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-016 |
| Related knowledge | KN-311, KN-424 |

## Purpose

Recover meridian.com storefront availability and latency when the Next.js/Node BFF origin
(APP-001) saturates under peak load: scale the BFF, raise the CDN/edge cache hit ratio (extend
TTLs for cacheable pages, enable stale-while-revalidate), shed non-critical requests, and
coordinate edge load-shedding with TEAM-030 at the gateway (APP-024). This is a **capacity**
runbook, not a bug fix. INC-2026-016 is the reference case: a pre-peak load test revealed
origin saturation and drove edge load-shedding tuning (postmortem KN-311). APP-001 is
Next.js/React + Node BFF; the edge/CDN and API Gateway are owned by TEAM-030 (APP-024), so
recovery is co-driven. It complements RB-0008 (edge load-shedding at the gateway).

## When to use (symptoms / alerts)

- Alert `storefront-origin-saturation` or `StorefrontLatencyP99 > 1.5s (5m)`; PagerDuty page
  during a traffic peak, flash sale, or load test.
- Grafana **Storefront / Origin** shows BFF pods at CPU/event-loop saturation
  (`nodejs_eventloop_lag_p99` climbing, `bff_cpu > 85%`), and rising 5xx / 503 from origin.
- CDN dashboard shows `edge_cache_hit_ratio` dropping (more requests falling through to
  origin) while request volume spikes.
- API Gateway (APP-024) shows origin connection pool exhaustion / upstream timeouts to APP-001.
- The pattern from INC-2026-016: origin cannot absorb peak because too much cacheable content
  is going to origin.

## Preconditions

- You are on TEAM-001 (Storefront) on-call (or the follow-the-sun holder for a Tier-0 page);
  TEAM-030 (Core Platform) on-call is engaged for edge/gateway actions (APP-024).
- `kubectl` context on the affected region; `mcg-cdn`, `mcg-flags`, and `mcg-edge` CLIs on the
  ops jumpbox.
- APP-001 BFF runs in namespace `storefront` (HPA enabled); the edge/CDN config is owned by
  TEAM-030 and changed via `mcg-cdn` (GitOps-backed, auditable — §4.5).
- Know which pages are cacheable (home, category/browse, PDP for logged-out users) vs
  personalized (cart, account, checkout) — only cacheable pages get TTL/SWR changes.

## Procedure

1. **Confirm origin saturation vs a downstream fault.** Make sure the origin is the
   bottleneck, not a slow dependency (catalog APP-005, pricing APP-007):
   ```
   mcg-metrics compare --service storefront-bff \
     --metrics eventloop_lag,cpu,upstream_latency --window 15m --region <region>
   ```
   High event-loop lag + CPU with healthy upstreams → origin saturation → continue. High
   `upstream_latency` → chase the dependency instead.
2. **Scale the BFF.** Bump the HPA ceiling and add replicas immediately (don't wait for the
   HPA to catch up under a spike):
   ```
   kubectl -n storefront scale deploy/storefront-bff --replicas=<n>
   kubectl -n storefront patch hpa storefront-bff \
     -p '{"spec":{"maxReplicas":<higher-max>}}'
   kubectl -n storefront rollout status deploy/storefront-bff
   ```
3. **Raise the edge cache hit ratio — extend TTLs for cacheable pages.** With TEAM-030, push
   more cacheable traffic to the edge so it never reaches origin:
   ```
   mcg-cdn ttl set --path '/' --ttl 120s --region <region>
   mcg-cdn ttl set --path '/c/*' --ttl 300s --region <region>     # category/browse
   mcg-cdn ttl set --path '/p/*' --ttl 180s --region <region>     # PDP (logged-out)
   ```
   Never cache personalized routes (`/cart`, `/account`, `/checkout`) — they are marked
   `no-store` and must stay origin-served.
4. **Enable stale-while-revalidate.** Let the edge serve slightly-stale cached pages while it
   revalidates in the background, absorbing origin latency spikes:
   ```
   mcg-cdn swr enable --path '/c/*,/p/*' --stale 600s --region <region>
   ```
5. **Shed non-critical requests.** Turn off cost-heavy, non-essential origin work first
   (personalized recommendation rails, non-critical A/B experiments) via flags:
   ```
   mcg-flags set storefront-web storefront.reco_rail.enabled=false --region <region>
   mcg-flags set storefront-web storefront.experiments.heavy=false --region <region>
   ```
6. **Coordinate edge load-shedding at the gateway (APP-024).** With TEAM-030, shed the lowest
   priority traffic classes at the edge before origin collapses (see RB-0008). Tune the
   priority-based shed threshold rather than a blunt global rate limit (the INC-2026-016 fix):
   ```
   mcg-edge shed set --service storefront --priority-below 3 \
     --when origin_cpu>85 --region <region>
   ```
   This drops bots/low-priority prefetch first, protecting real shopper sessions.
7. **Confirm origin recovers headroom.** Watch BFF saturation fall as hit ratio climbs and
   shedding engages; hold the changes through the peak.

## Verification

- `StorefrontLatencyP99` back under 800ms for 10 continuous minutes; origin 5xx/503 near zero.
- `edge_cache_hit_ratio` up materially (e.g. > 0.85 for cacheable routes) on the CDN board.
- BFF `nodejs_eventloop_lag_p99` and CPU back under saturation thresholds; HPA stable, not
  pinned at max.
- Personalized routes (`/cart`, `/account`, `/checkout`) confirmed **not** cached:
  `mcg-cdn inspect --path /cart --region <region>` shows `no-store`.
- `mcg-synthetics run storefront-home,storefront-pdp --region <region>` passes with cache HITs
  on cacheable pages.

## Rollback

- These are capacity/config changes; back them out once the peak passes to avoid over-serving
  stale content:
  ```
  mcg-cdn ttl reset --path '/,/c/*,/p/*' --region <region>
  mcg-cdn swr disable --path '/c/*,/p/*' --region <region>
  mcg-flags set storefront-web storefront.reco_rail.enabled=true --region <region>
  mcg-edge shed clear --service storefront --region <region>
  ```
- Scale the BFF back down gradually (let the HPA settle) rather than dropping replicas
  abruptly mid-traffic.
- No data or schema is changed here, so there is no migration rollback concern (§7.4).
- If a bad APP-001 release caused the regression (not organic load), roll it back per RB-0020
  instead of masking it with cache/shed changes.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-001 (Storefront) regional on-call is Incident Commander for the
  origin; TEAM-030 (Core Platform) on-call co-drives edge/CDN and gateway (APP-024) actions.
- **T1 (10 min, unresolved):** Page TEAM-030 for edge load-shedding and CDN changes (RB-0008);
  loop dependency owners (TEAM-005 Catalog, TEAM-007 Pricing) if step 1 shows a slow upstream.
- **Follow-the-sun handoff** for Tier-0 pages: NA (`oncall-storefront-na`) → EU
  (`oncall-storefront-eu`) → APAC (`oncall-storefront-apac`); rotate IC at the regional
  boundary, keep the incident channel as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
