# RB-0006 — Edge OIDC Clock-Skew Token Rejection

| Field | Value |
|---|---|
| Runbook id | RB-0006 |
| Title | Edge OIDC Clock-Skew Token Rejection |
| Owner team | TEAM-030 (Core Platform) |
| Apps | APP-024 (API Gateway / Edge), APP-014 (Identity & Customer Profile) |
| Severity scope | Sev1–Sev2 |
| Related incidents | INC-2026-014 |
| Related knowledge | KN-309, KN-405 |

## Purpose

Restore authentication when edge OIDC verification on APP-024 rejects valid JWTs with HTTP
401 because of clock skew between edge pods and the token issuer (APP-014 Identity). The
gateway validates `exp`/`nbf`/`iat` on inbound bearer tokens; if an edge pod's clock drifts
or the skew-tolerance (leeway) is too tight, freshly issued valid tokens fail verification
for a subset of users. This runbook operationalizes INC-2026-014 (a clock-skew tolerance bug
in edge OIDC verification rejected valid tokens for 58 minutes across NA and EU after
REL-2026-007) and its postmortem KN-309. Root cause was a `deployment`-category regression,
so a rollback path is first-class here.

## When to use (symptoms / alerts)

- PagerDuty alert `edge-oidc-401-spike` (`http_401_ratio{app="APP-024"} > 1% (5m)`) or
  `edge-jwt-verify-fail`.
- Grafana dashboard **Edge / Auth** shows `jwt_verify_fail_total{reason="token_not_yet_valid"}`
  or `{reason="token_expired"}` spiking while Identity (APP-014) issuance is healthy.
- The 401s correlate with a recent edge deploy and hit only a subset of users (those routed
  to skewed pods).
- CS reports "kept getting logged out" / "please sign in again" loops on valid sessions.

## Preconditions

- You are on the TEAM-030 on-call rotation (or the follow-the-sun holder for a Tier-0 edge
  page).
- `kubectl` context on the affected region: `kubectl config use-context mcg-<region>-prod`.
- Gateway runs in namespace `edge`; OIDC verification config is GitOps-managed
  (`mcg-api-gateway/config/oidc/<region>.yaml`) and applied via `mcg-edge`.
- Identity (APP-014) JWKS endpoint and issuer clock are owned by TEAM-014 — coordinate any
  issuer-side finding with them.

## Procedure

1. **Confirm the failure reason is skew, not a real bad token.** Break down verification
   failures:
   ```
   mcg-edge oidc verify-stats --region <region> --since 15m
   ```
   A skew problem shows `token_not_yet_valid` (nbf/iat in the future) or narrowly
   `token_expired` clustered on specific pods, while signature (`bad_signature`) and issuer
   (`bad_issuer`) counts stay at zero.
2. **Check NTP / time sync on edge pods.** Find drifted pods:
   ```
   kubectl -n edge get pods -o name | while read p; do
     echo "$p"; kubectl -n edge exec "$p" -- chronyc tracking 2>/dev/null | grep -E 'System time|Leap';
   done
   ```
   Any pod with `System time` offset > 2s from the reference is a suspect. Restart drifted
   pods so they re-sync via the node chrony/NTP source:
   ```
   kubectl -n edge delete pod <drifted-pod>
   ```
3. **Widen the OIDC clock-skew leeway.** As immediate mitigation, increase the allowed skew
   so borderline-valid tokens verify (the INC-2026-014 fix raised leeway from 30s to 120s):
   ```
   mcg-edge oidc set --region <region> --clock-skew-leeway 120s --dry-run
   mcg-edge oidc apply --region <region> --canary 10
   ```
   `--dry-run` shows the simulated pass-rate change; canary applies to 10% of edge pods
   first (CANON §7.2).
4. **Verify JWKS freshness.** A stale key cache can masquerade as skew after a key rotation;
   confirm the edge has Identity's current keys:
   ```
   mcg-edge oidc jwks status --region <region>
   ```
   If `jwks_age_seconds` exceeds the refresh interval, force a refetch:
   ```
   mcg-edge oidc jwks refresh --region <region>
   ```
   and confirm the `kid` set matches Identity: `mcg-identity jwks list` (coordinate with
   TEAM-014).
5. **Promote the leeway change region-wide.** If the canary clears:
   ```
   mcg-edge oidc apply --region <region> --promote
   ```
   Committed back to `oidc/<region>.yaml` via GitOps (no manual prod edit).
6. **Decide rollback vs. forward-fix.** Since the root cause was a deployment regression, if
   the skew bug is in the newly shipped edge verification code (not pod clocks), prefer
   rolling back the bad release — see Rollback.

## Verification

- `http_401_ratio{app="APP-024", region="<region>"} < 0.1%` for 5 continuous minutes on the
  Edge / Auth board.
- `jwt_verify_fail_total{reason="token_not_yet_valid"}` and `{reason="token_expired"}`
  return to baseline.
- All edge pods report `chronyc tracking` offset < 1s.
- `mcg-synthetics run edge-authenticated --region <region>` (obtains a fresh token from
  APP-014 and calls a protected route) returns `200`.
- `mcg-edge oidc jwks status --region <region>` shows `jwks_age_seconds` within the refresh
  interval and the `kid` set matching Identity.

## Rollback

- **Preferred if code-level:** roll back the offending edge release (INC-2026-014 traced to
  REL-2026-007) per RB-0009:
  ```
  kubectl -n edge rollout undo deploy/api-gateway
  ```
  Confirm the prior `v<semver>` tag and that `jwt_verify_fail` clears.
- The `--clock-skew-leeway` config change is versioned; revert with
  `mcg-edge oidc rollback --region <region> --to-previous`. Keep leeway at the corrected
  value (≥120s) as the standing default per KN-309 unless Security requires tighter.
- Do not leave leeway arbitrarily wide (e.g. minutes) as a permanent fix — that weakens
  token freshness guarantees; fix pod time sync as the durable remedy.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-030 regional on-call owns edge OIDC verification and is Incident
  Commander.
- **T1 (10 min, unresolved):** Engage TEAM-014 (Identity & Customer Profile) for any
  issuer-side clock, JWKS or key-rotation finding (co-owned APP-014 in INC-2026-014), and
  TEAM-040 (Security) if a tokening/replay concern arises.
- **Follow-the-sun handoff** for Tier-0 edge pages: NA (`oncall-edge-na`) → EU
  (`oncall-edge-eu`) → APAC (`oncall-edge-apac`); rotate IC at the regional boundary and keep
  `#inc-edge-oidc` as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
