## Purpose

Restore database write availability when a managed PostgreSQL primary is lost, or when the
connection path saturates (too many connections, PgBouncer at capacity, idle-in-transaction
sessions holding slots). MCG runs Patroni-managed HA Postgres clusters fronted by PgBouncer
for the Tier-0 transactional services Pricing (APP-007), OMS (APP-009) and Payments
(APP-012). This runbook covers detecting primary loss vs pool exhaustion (they present
similarly — writes failing — but the fix differs), promoting a replica, repointing services,
killing stuck sessions, tuning pool sizes, and confirming replication has caught up. It is
preventive/general and owned by TEAM-030 (Core Platform), who own the shared platform DB
tier; the owning product squad joins as the domain expert.

## When to use (symptoms / alerts)

- PagerDuty alert `pg-primary-down-<cluster>` or `pg-pool-saturation-<cluster>`.
- Grafana **Platform / Postgres** shows `pg_up{role="primary"} = 0`, or
  `pgbouncer_pools_cl_waiting` climbing while `pgbouncer_pools_sv_active` is pinned at the
  pool max.
- Application logs show `FATAL: remaining connection slots are reserved` / `sorry, too many
  clients already`, or `could not connect to server` from a service DAO.
- `pg_stat_activity` shows a growing count of `idle in transaction` sessions.
- Patroni event `demoted self because ... / promoting replica` in the cluster logs.

## Preconditions

- You are on TEAM-030 on-call (or the follow-the-sun holder for a Tier-0 page); the owning
  squad (TEAM-007/006/009) is looped in as domain owner.
- `kubectl` context on the affected region: `kubectl config use-context mcg-<region>-prod`.

  (`mcg-secrets get platform/pg/<cluster>/admin`) — never from code or logs.
- Clusters: `pg-pricing-prod`, `pg-oms-prod`, `pg-payments-prod` (each 1 primary + 2 sync/async

## Procedure

1. **Classify: primary loss vs pool exhaustion.** Check the cluster topology first:
   ```
   patronictl -c /etc/patroni/<cluster>.yml list
   ```
   If no member has `Role: Leader` (or the leader is `stopped`), it is a **primary loss** →
   step 2. If a healthy leader exists but apps still can't connect, it is **pool exhaustion**
   → step 5.
2. **Confirm/await automatic failover.** Patroni auto-promotes the healthiest sync replica
   within its `ttl` (~30s):
   ```
   patronictl -c /etc/patroni/<cluster>.yml list --watch
   ```
   Look for a replica transitioning to `Leader`. If it stalls (no leader after 60s, DCS
   split-brain), force it in step 3; otherwise skip to step 4.
3. **Manual promotion (only if auto-failover stalled).** Promote the most-caught-up replica
   (lowest replication lag):
   ```
   patronictl -c /etc/patroni/<cluster>.yml switchover \
     --candidate <replica-node> --force
   ```
   If etcd/DCS lost quorum, restore DCS quorum before promoting (do not manually `pg_ctl
   promote` behind Patroni's back — that risks split-brain).
4. **Repoint services to the new primary.** Services connect through PgBouncer to the
   `<cluster>-primary` service, which follows the Patroni leader label; force the endpoint to
   re-resolve and reload the pooler:
   ```
   kubectl -n platform annotate svc <cluster>-primary patroni.role=leader --overwrite
   kubectl -n platform exec deploy/pgbouncer-<cluster> -- \
     psql -p 6432 pgbouncer -c "RELOAD;"
   ```
   Then refresh app pools without a full restart:
   `kubectl -n <app-ns> rollout restart deploy/<service>` only if pools don't self-heal.
5. **Diagnose pool exhaustion.** Find who is holding connections:
   ```
   psql -h <cluster>-primary -U mcg_admin -d <db> -c "
     SELECT state, count(*), max(now()-state_change) AS max_age
     FROM pg_stat_activity GROUP BY state ORDER BY 2 DESC;"
   ```
   A large `idle in transaction` bucket with old `max_age` is the usual culprit (a service
   leaked a transaction).
6. **Kill idle-in-transaction sessions (targeted).** Terminate only sessions idle in
   transaction longer than 5 minutes — never blanket-kill active queries:
   ```
   psql -h <cluster>-primary -U mcg_admin -d <db> -c "
     SELECT pg_terminate_backend(pid) FROM pg_stat_activity
     WHERE state='idle in transaction'
       AND (now()-state_change) > interval '5 minutes';"
   ```
7. **Relieve the pooler and tune pool sizes.** Inspect PgBouncer, then raise
   `default_pool_size` / `max_client_conn` within the DB's `max_connections` budget:
   ```
   psql -p 6432 -h pgbouncer-<cluster> pgbouncer -c "SHOW POOLS;"
   mcg-flags set pgbouncer-<cluster> pgbouncer.default_pool_size=40 --region <region>
   psql -p 6432 -h pgbouncer-<cluster> pgbouncer -c "RELOAD;"
   ```
   Keep `default_pool_size × app_replicas ≤ max_connections − reserved`. Prefer fixing the
   leaking service over unbounded pool growth.
8. **Verify replication caught up before declaring healthy.** Confirm the new topology has a
   synchronous standby and low lag:
   ```
   psql -h <cluster>-primary -U mcg_admin -c "
     SELECT client_addr, state, sync_state,
            pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
     FROM pg_stat_replication;"
   ```

## Verification

- `patronictl list` shows one `Leader` (running) and replicas `streaming` with a
  `sync_state=sync` standby present.
- Application write-error rate back under 0.5% for 5 continuous minutes on the owning
  service's SLO board; no `too many clients` in logs.
- `pgbouncer SHOW POOLS` shows `cl_waiting = 0` and `sv_active` below pool max.
- `pg_stat_replication` lag_bytes trending to ~0 on the sync standby.
- Synthetic write passes: `mcg-synthetics run <service>-db-write --region <region>` → 200.

## Rollback

- An organic failover has nothing to roll back; the promoted replica becomes the durable
  primary. Do **not** demote back to the old node under fire — let it rejoin as a replica.
- If a pool-size change caused DB connection saturation, revert it:
  `mcg-flags set pgbouncer-<cluster> pgbouncer.default_pool_size=<prev> --region <region>`
  then `RELOAD`.
- Never restore Postgres from a snapshot for a transient failover; expand-contract migrations
  (§7.4) mean the schema is forward/backward compatible and no down-migration is needed.
- If a bad application release caused the connection leak, roll that release back per the
  owning squad's deploy runbook rather than repeatedly killing sessions.
