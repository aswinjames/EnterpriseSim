# RB-0008 — Edge Load-Shedding at Peak

| Field | Value |
|---|---|
| Runbook id | RB-0008 |
| Title | Edge Load-Shedding at Peak |
| Owner team | TEAM-030 (Core Platform) |
| Apps | APP-024 (API Gateway / Edge), APP-001 (Storefront Web) |
| Severity scope | Sev1–Sev2 |
| Related incidents | INC-2026-016 |
| Related knowledge | KN-311, KN-407 |

## Purpose

Protect origin services from collapse under peak or load-test traffic by enabling prioritized
load-shedding at the edge (APP-024): shed low-priority and bot traffic first, protect the
checkout path, and apply adaptive concurrency limits while Storefront (APP-001) autoscaling
catches up. The gateway (Envoy/Kong + Go + Lua) can classify and shed traffic by priority
before it reaches saturated origins. This runbook operationalizes INC-2026-016 (a pre-peak
load test revealed origin saturation; edge load-shedding was tuned in response, NA) and its
postmortem KN-311. Root cause was `capacity`.

## When to use (symptoms / alerts)

- PagerDuty alert `origin-saturation` (`upstream_concurrency_saturation{app="APP-001"} > 90%
  (3m)`) or `edge-shed-recommended`.
- Grafana dashboard **Edge / Load** shows rising `upstream_rq_pending`, growing
  `upstream_rq_time` p99, and origin CPU/connection pools near limit.
- Storefront (APP-001) p99 latency climbing and 5xx beginning to appear while autoscaling is
  still ramping (HPA `desiredReplicas > currentReplicas`).
- A scheduled load test or a real peak event (sale, marketing push) is in progress.

## Preconditions

- You are on the TEAM-030 on-call rotation (or the follow-the-sun holder for a Tier-0 edge
  page).
- `kubectl` context on the affected region: `kubectl config use-context mcg-<region>-prod`.
- Gateway runs in namespace `edge`; load-shed and priority config is GitOps-managed
  (`mcg-api-gateway/config/loadshed/<region>.yaml`) and applied via `mcg-edge`.
- Traffic-priority classes are defined: `checkout`/`payments` = P0 (never shed),
  authenticated browse = P1, anonymous browse = P2, bots/crawlers = P3 (shed first).
- Coordinate with TEAM-001 (Storefront) so autoscaling and shedding move together.

## Procedure

1. **Confirm origin saturation, not an edge fault.** Verify the bottleneck is downstream:
   ```
   mcg-edge origin health --app APP-001 --region <region>
   kubectl -n storefront get hpa storefront-web
   ```
   Saturation shows high `upstream_rq_pending` with origin near connection/CPU limits and HPA
   still scaling up. If the edge itself is the bottleneck, scale the gateway instead.
2. **Enable prioritized load-shedding.** Turn on shedding lowest-priority first, protecting
   the checkout path:
   ```
   mcg-flags set api-gateway edge.loadshed.enabled=true --region <region>
   mcg-edge loadshed set --region <region> --shed-below P2 --protect checkout,payments --dry-run
   ```
   `--dry-run` reports the share of traffic that would be shed by class. `--shed-below P2`
   sheds P3 (bots) first; escalate to `--shed-below P1` only if origin stays saturated.
3. **Apply adaptive concurrency limits.** Cap in-flight requests per upstream so the origin
   is never driven past its safe concurrency (gradient-based limiter):
   ```
   mcg-edge concurrency set --app APP-001 --region <region> --mode adaptive --min-limit 200
   mcg-edge loadshed apply --region <region>
   ```
   Adaptive mode auto-discovers the limit from observed latency; `--min-limit` floors it so
   we never shed to zero.
4. **Signal Storefront to scale.** Ensure origin capacity is growing underneath the shed:
   ```
   kubectl -n storefront scale deploy storefront-web --replicas=<burst_target>
   ```
   or bump the HPA ceiling: `kubectl -n storefront patch hpa storefront-web --type merge -p
   '{"spec":{"maxReplicas":<n>}}'`. Confirm with TEAM-001 first.
5. **Watch and de-escalate.** As origin recovers and `upstream_rq_pending` drains, raise the
   shed threshold back toward P3-only:
   ```
   mcg-edge loadshed set --region <region> --shed-below P3 --protect checkout,payments
   mcg-edge loadshed apply --region <region>
   ```
6. **Confirm checkout was never shed.** Prove the protected path stayed whole:
   ```
   mcg-edge loadshed stats --region <region> --since 20m
   ```
   `shed_total{priority="P0"}` must be `0`.

## Verification

- `upstream_concurrency_saturation{app="APP-001"} < 70%` and Storefront p99 back within SLO
  for 5 continuous minutes on the Edge / Load board.
- `mcg-edge loadshed stats --region <region>` shows `shed_total{priority="P0"} = 0` (checkout
  never shed) and shedding tapering as origin recovers.
- Storefront 5xx returns to baseline; HPA `currentReplicas == desiredReplicas` (autoscaling
  caught up).
- `mcg-synthetics run guest-checkout --region <region>` passes throughout the event.
- Once traffic normalizes, disable shedding: `mcg-flags set api-gateway
  edge.loadshed.enabled=false --region <region>`.

## Rollback

- Load-shed and concurrency settings are versioned config; revert with
  `mcg-edge loadshed rollback --region <region> --to-previous` and disable the flag.
- If adaptive concurrency limited too aggressively and shed legitimate P1 traffic
  unnecessarily, raise `--min-limit` or switch to `--mode fixed --limit <n>` at a measured
  origin-safe value rather than turning shedding off entirely under load.
- Do not disable shedding while origin is still saturated — that re-triggers the collapse.
  De-escalate priority thresholds first (step 5), then disable.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-030 regional on-call owns edge load-shedding and is Incident
  Commander.
- **T1 (10 min, unresolved):** Engage TEAM-001 (Storefront) for origin autoscaling/capacity
  (co-owned APP-001 in INC-2026-016); loop in the owning team of any other saturated origin.
- **Follow-the-sun handoff** for Tier-0 edge pages: NA (`oncall-edge-na`) → EU
  (`oncall-edge-eu`) → APAC (`oncall-edge-apac`); rotate IC at the regional boundary and keep
  `#inc-edge-loadshed` as the single source of truth.
- **T2 (20 min or Sev1):** Engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
