# RB-0012 — Checkout p99 Latency Regression

| Field | Value |
|---|---|
| Runbook id | RB-0012 |
| Title | Checkout p99 Latency Regression |
| Owner team | TEAM-004 (Cart & Checkout) |
| Apps | APP-003 (Checkout Service) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-019 |
| Related knowledge | KN-313, KN-411 |

## Purpose

Restore checkout p99 latency when a synchronous downstream call on the order-placement path
regresses tail latency. In INC-2026-019 a promotions (APP-008) call was placed inline on the
checkout hot path; when the Promotions Engine slowed, checkout p99 climbed until the call was
made asynchronous. This runbook identifies the hot span in a trace, moves the promo call to
an async/timeout-with-fallback path via feature flag, and confirms p99 recovers — without a
redeploy. APP-003 is a Java/Spring Boot Tier-0 service; a latency regression here is
revenue-impacting.

## When to use (symptoms / alerts)

- Alert `checkout-p99-slo-breach` — `checkout_place_order_p99 > 800ms (5m)` (SLO is 600ms).
- Grafana **Checkout / Latency** shows p99 (and p999) rising while p50 is roughly flat — the
  signature of a slow synchronous dependency, not broad saturation.
- Distributed-trace view (Tempo/Jaeger) shows a large `promotions.apply` (or `promo.resolve`)
  child span dominating `POST /v1/checkout/{id}/place`.
- Correlates with a recent APP-003 or APP-008 release, or a Promotions Engine slowdown
  (`promo_apply_p99` up on the Promotions dashboard).

## Preconditions

- TEAM-004 on-call; `kubectl` context on the affected region cluster
  (`kubectl config use-context mcg-<region>-prod`); `mcg-flags` CLI available.
- Checkout Service runs in namespace `checkout` as deploy/checkout-service, admin port 8081.
- You can read traces: `mcg-trace` CLI or the Tempo datasource in Grafana.
- Know the current APP-003 release tag and whether a deploy landed in the last 30 min
  (`mcg-release show --app APP-003 --region <region>`).

## Procedure

1. **Confirm the tail-latency signature.** Rule out broad saturation before chasing a span:
   ```
   mcg-metrics query --region <region> \
     'histogram_quantile(0.99, checkout_place_order_duration_seconds_bucket)'
   ```
   If p99 is up but p50/CPU/pool utilization are flat, it is a slow dependency — continue.
2. **Find the hot span in traces.** Pull the slowest recent place-order traces:
   ```
   mcg-trace search --service checkout-service --region <region> \
     --operation "POST /v1/checkout/{id}/place" --min-duration 800ms --last 10m
   ```
   Open a representative trace; identify the dominant child span. For INC-2026-019 this is a
   synchronous `promotions.apply` call to APP-008 sitting on the critical path.
3. **Confirm the dependency is the cause.** Check the downstream's own latency:
   ```
   mcg-metrics query --region <region> \
     'histogram_quantile(0.99, promo_apply_duration_seconds_bucket)'
   ```
   A promo p99 in the hundreds of ms feeding an inline checkout call explains the regression.
4. **Switch the promo call to async with fallback (primary mitigation).** The safe order
   path can place the order and apply eligible promos asynchronously; toggle it via flag so
   no redeploy is needed:
   ```
   mcg-flags set checkout-service checkout.promo.async_apply=true --region <region>
   ```
   This makes `promotions.apply` fire off the hot path; the order commits on the last-known
   promo state and reconciles on the async result.
5. **Bound the synchronous fallback with a tight timeout.** In case async is not appropriate
   for a given cart type, cap the inline call and fall back to no additional promo rather
   than blocking placement:
   ```
   mcg-flags set checkout-service checkout.promo.sync_timeout_ms=150 --region <region>
   mcg-flags set checkout-service checkout.promo.fail_open=true --region <region>
   ```
   `fail_open=true` means a promo timeout does not fail the order — the customer is not
   blocked; any missed discount is reconciled post-order.
6. **Verify flag propagation.** Confirm every checkout pod picked up the flags:
   ```
   kubectl -n checkout exec deploy/checkout-service -- \
     curl -s localhost:8081/admin/flags | grep checkout.promo
   ```
   Propagation is typically < 30s (see RB-0018); do not restart pods to force it unless a pod
   is stuck showing the old value.
7. **If the trigger was a bad release, prepare a rollback in parallel.** If a checkout deploy
   in the last 30 min introduced the inline call, roll it back rather than relying on the flag
   long-term (see Rollback). Never roll checkout ahead of its upstreams — APP-012/APP-010.

## Verification

- `checkout_place_order_p99` back under the 600ms SLO for 5 continuous minutes; `checkout-p99-slo-breach` clears.
- The `promotions.apply` span no longer appears on the critical path in fresh place-order
  traces (it is async, or capped at ≤150ms with fail-open).
- `mcg-synthetics run checkout-place-order --region <region>` passes end to end.
- Order-placement success rate unchanged (async promo did not drop orders):
  `mcg-metrics query --region <region> 'rate(checkout_place_order_success_total[5m])'`.
- Async promo reconciliation backlog drains: dashboard `checkout_promo_async_queue_depth = 0`.

## Rollback

- The primary mitigation is flags; to revert set them back:
  `mcg-flags set checkout-service checkout.promo.async_apply=false --region <region>` (only
  once the underlying slowness is gone — reverting during the slowdown reintroduces the p99
  regression).
- If a checkout release introduced the synchronous path, roll it back:
  ```
  kubectl -n checkout rollout undo deploy/checkout-service
  mcg-release rollback --app APP-003 --to <previous v-semver> --region <region>
  ```
  Confirm the previous `v<semver>` tag is serving. Because migrations are expand-contract
  (CANON §7.4), rollback requires no schema down-migration.
- Fix-forward is preferred here: the durable fix is to keep `async_apply` on and ship the
  code change that makes the async path the default, retiring the flag.

## Escalation (follow-the-sun, Tier 0)

- **T0 (0–10 min):** TEAM-004 regional on-call owns the checkout latency; acts as Ops lead.
- **T1 (10 min):** Loop in TEAM-008 (Promotions & Offers) if APP-008 is the slow dependency —
  they own the underlying promo latency and RB-0002.
- **Follow-the-sun (Tier 0):** rotate on-call/IC NA (`oncall-checkout-na`) → EU
  (`oncall-checkout-eu`) → APAC (`oncall-checkout-apac`) at the shift boundary; keep
  `#inc-checkout-latency` as the single source of truth.
- **T2 (Sev2 or > 20 min):** engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
