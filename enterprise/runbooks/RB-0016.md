# RB-0016 — Self-Service Returns Eligibility Regression

| Field | Value |
|---|---|
| Runbook id | RB-0016 |
| Title | Self-Service Returns Eligibility Regression |
| Owner team | TEAM-001 (Storefront Experience) |
| Apps | APP-021 (Customer Portal / My Meridian) |
| Severity scope | Sev2–Sev3 |
| Related incidents | INC-2026-015 |
| Related knowledge | KN-310, KN-415 |

## Purpose

Restore correct self-service returns eligibility in My Meridian (APP-021) when a rule
regression wrongly marks delivered orders as ineligible for return. In INC-2026-015 a
returns-eligibility rule regression showed some delivered orders as ineligible in the
customer portal. The fix is to identify the bad rule/BFF version, roll back the change, clear
the eligibility cache, and re-check eligibility against the authoritative order state in OMS
(APP-009). Root cause is a **code regression** in the portal's Node BFF eligibility logic;
APP-021 is React + Node BFF, Tier 1. Order truth lives in OMS (APP-009).

## When to use (symptoms / alerts)

- Alert `returns-eligibility-anomaly` — spike in `returns_eligibility_denied_total` for
  orders in a delivered state.
- CS reports customers seeing "This order isn't eligible for return" on orders that are
  clearly within the return window and delivered.
- Grafana **My Meridian / Returns** shows denial rate diverging from the OMS-derived expected
  eligibility rate; correlated with a recent APP-021 release (in INC-2026-015, REL-2026-008).
- The eligibility check returns ineligible while OMS (APP-009) order state is `DELIVERED`
  within the return window.

## Preconditions

- TEAM-001 on-call; `kubectl` context on the affected region (INC-2026-015 impacted NA).
- `mcg-flags` CLI; access to the portal BFF deploy and the eligibility cache (Redis
  `portal-returns-cache-prod`); read access to OMS order-state API.
- Portal BFF runs in namespace `portal` as deploy/customer-portal-bff (Node), admin port 8080.
- Know the current APP-021 release tag and whether an eligibility rule/BFF change landed
  recently (`mcg-release show --app APP-021 --region <region>`).

## Procedure

1. **Confirm the regression against OMS truth.** Pick an affected order and compare the BFF
   verdict to OMS state:
   ```
   mcg-portal returns eligibility --order <ORDER_ID> --explain
   mcg-oms order state --order <ORDER_ID>
   ```
   If OMS shows `DELIVERED` within the return window but the BFF `--explain` denies (e.g., a
   flipped comparison or wrong window boundary in the rule), the regression is confirmed.
2. **Identify the bad rule/BFF version.** Find what changed and when:
   ```
   mcg-release show --app APP-021 --region <region> --last 5
   mcg-portal rules version --domain returns-eligibility
   ```
   Note the suspect release tag / rule version and its deploy time (the last-known-good prior
   version is your rollback target).
3. **Roll back the BFF / rule change (primary mitigation).** Prefer a versioned rollback of
   the release that introduced the regression:
   ```
   mcg-release rollback --app APP-021 --to <previous v-semver> --region <region>
   kubectl -n portal rollout status deploy/customer-portal-bff
   ```
   If only the eligibility ruleset changed (not code), revert the ruleset version instead:
   ```
   mcg-portal rules rollback --domain returns-eligibility --to <good_version> --region <region>
   ```
   If a redeploy is too slow and the bad path is flag-gated, disable it via flag as an
   interim (see RB-0018): `mcg-flags set customer-portal returns.eligibility.v2=false --region <region>`.
4. **Clear the eligibility cache.** Cached denials from the bad rule must be evicted so
   re-checks use the restored logic:
   ```
   mcg-portal cache invalidate --domain returns-eligibility --region <region>
   ```
   Verify the keys are gone:
   ```
   redis-cli -h portal-returns-cache-prod --scan --pattern 'returns:elig:*:<region>' | head
   ```
   (targeted by region; avoid flushing unrelated portal caches).
5. **Re-check eligibility against OMS.** Recompute eligibility for orders touched during the
   window so customers see correct status immediately, sourced from OMS (APP-009) state:
   ```
   mcg-portal returns recheck --region <region> --since <regression_deploy_ts> \
     --source oms
   ```
6. **Confirm propagation.** Ensure all BFF pods serve the restored version/rules:
   ```
   kubectl -n portal exec deploy/customer-portal-bff -- \
     curl -s localhost:8080/admin/rules | grep returns-eligibility
   ```

## Verification

- `returns_eligibility_denied_total` returns to the OMS-derived expected baseline;
  `returns-eligibility-anomaly` alert clears.
- For a sample of previously-denied delivered orders, `mcg-portal returns eligibility --order <ORDER_ID> --explain` now returns eligible, matching OMS state.
- `mcg-synthetics run returns-eligibility --region <region>` passes for a delivered in-window order.
- Cache holds no stale denials: re-checked orders show correct eligibility from OMS.
- CS confirms the customer-reported cases are resolved.

## Rollback

- The mitigation is a rollback; if the restored version is also wrong, roll to the next
  earlier known-good release/ruleset and re-check again.
- An interim flag disable is reversible: re-enable only after the corrected rule ships.
- No schema change is involved (BFF logic + cache only), so no DB down-migration; expand-
  contract discipline (CANON §7.4) keeps OMS state untouched.
- The durable fix is a corrected eligibility rule with a contract test against OMS order
  states (delivered / within-window matrix) added to the portal pipeline (KN-415).

- **T0 (0–10 min):** TEAM-001 regional on-call owns the portal BFF and the returns rule;
  acts as Ops lead.
- **T1 (10 min):** Loop in TEAM-006 (Order Management) if OMS (APP-009) order-state data
  itself is in question rather than the portal rule.
- **Follow-the-sun (Tier 0 process):** rotate on-call/IC NA (`oncall-portal-na`) → EU
  (`oncall-portal-eu`) → APAC (`oncall-portal-apac`); INC-2026-015 impacted NA. Keep
  `#inc-returns-eligibility` as the single source of truth.
- **T2 (Sev2 or escalating):** engage SRE (TEAM-032) as Incident Commander and follow RB-0011.
