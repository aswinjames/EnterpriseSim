## Summary

REL-2026-007 shipped an updated token-bucket rate-limit configuration to the API Gateway
(APP-024). The new threshold was set too aggressively for EU traffic patterns, so for ~14
minutes the gateway rejected a portion of **legitimate** requests with HTTP 429 (Too Many
Requests). Affected clients — primarily EU web and mobile sessions — saw intermittent request
failures and retries until the threshold was rolled back to a value appropriate for observed
EU traffic. No data was lost or corrupted; the impact was availability/UX for a subset of EU
requests during the window.

## Impact

- **Users:** A subset of EU shoppers experienced intermittent 429 rejections and slow/failed
  page or API calls for ~14 minutes.
- **Regions:** EU only.
- **Revenue-proxy:** Small — estimated ~$9K exposure from EU sessions degraded during the
  window; most requests succeeded on client retry.
- **Data integrity:** None affected; rejected requests were simply not served and were
  retried.

## Root cause

**Category: config_change.** The rate-limit threshold in REL-2026-007 was calibrated without
accounting for EU regional traffic patterns and burst behavior, setting the token-bucket
capacity too low. Legitimate bursty traffic exceeded the new limit and was rejected with 429.
This is a configuration defect: the gateway enforced exactly the limit it was told to, but
the limit was wrong for the region. There was no pre-release validation of the new thresholds
against observed regional traffic baselines.

## Detection

Automated. The edge 429-rate SLO alert (scoped per region) fired within minutes for EU.
Detection was healthy; the missing control was pre-release validation of thresholds against
real traffic.

## Resolution

The rate-limit configuration was rolled back to the prior known-good value via the GitOps
pipeline (no manual production change), immediately relieving the false rejections. A durable
fix — deriving thresholds from observed per-region traffic baselines with headroom — was
scoped as follow-up.

## What went well

- Region-scoped 429 SLO alerting isolated the problem to EU quickly.
- GitOps made rollback fast and auditable.
- The gateway correctly distinguished from an attack scenario once responders inspected
  traffic, avoiding an over-reaction.

## What went wrong

- New rate-limit thresholds were not validated against observed regional traffic baselines
  before release.
- Thresholds were set globally without accounting for EU burst patterns.

## Lessons learned

- Rate limits are region-sensitive; a single global threshold will be wrong somewhere.
  Calibrate against observed per-region traffic, not intuition.
- Protective controls (rate limiting) can themselves cause outages when miscalibrated; treat
  their configuration changes with canary discipline.
- Region-scoped SLO alerting is essential to localize a regional misconfiguration fast.
