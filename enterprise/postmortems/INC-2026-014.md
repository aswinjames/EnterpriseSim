## Summary

A change in REL-2026-007 to the API Gateway's edge OIDC token verification (APP-024,
validating tokens issued by Identity, APP-014) shipped with a **clock-skew tolerance bug**.
The verifier applied too tight a tolerance for allowable difference between token timestamps
(`iat`/`nbf`/`exp`) and edge node clocks, so valid tokens on nodes whose clock differed
slightly from the issuer were rejected as not-yet-valid or expired. For ~58 minutes, a subset
of NA and EU users were intermittently signed out or received authorization failures
depending on which edge node served their request. It was resolved by rolling back the edge
verification change and restoring the previous skew tolerance.

## Impact

- **Users:** A subset of authenticated NA and EU users hit intermittent auth failures /
  forced sign-outs for up to ~58 minutes; impact varied by edge node clock offset, so the
  experience was inconsistent and confusing.
- **Regions:** NA and EU.
- **Revenue-proxy:** Estimated ~$70K exposure from authenticated sessions unable to complete
  actions (including some checkout sessions) during the window; many users recovered by
  retrying or re-authenticating.
- **Data integrity / security:** No data exposed and no security weakening — the bug was
  over-strict (false rejections of valid tokens), the safe-failure direction. No invalid
  token was accepted.

## Root cause

**Category: deployment.** The edge OIDC verification change in REL-2026-007 tightened the
clock-skew tolerance below the real-world clock variance across edge nodes. Because edge node
clocks are not perfectly synchronized with the token issuer (APP-014), valid tokens fell
outside the too-narrow `nbf`/`exp` window on affected nodes and were rejected. The defect was
deployment/rollout-shaped: it manifested non-uniformly across the fleet depending on each
node's clock offset, which is why the user experience was intermittent and node-dependent.
Tests in a clock-synchronized environment did not reproduce the real-world skew.

## Detection

Automated plus user reports. The edge auth-rejection SLO alert fired at onset, corroborated by
a rise in sign-out reports. Detection was healthy. The intermittent, node-dependent nature of
the failure lengthened diagnosis, which drove most of the 58-minute duration.

## Resolution

The edge OIDC verification change was rolled back to the previous version, restoring the prior
(adequate) clock-skew tolerance. Auth success recovered across the fleet. A durable fix — a
correctly sized, configurable skew tolerance plus tightening edge-node clock synchronization —
was scoped as follow-up. Because this touches auth code, the eventual fix requires 2 reviews
including Security Engineering per release policy.

## What went well

- The failure was in the safe direction: valid tokens were rejected, no invalid token was
  accepted — no security exposure.
- Identity and Platform collaborated quickly to localize the fault to the edge verifier
  versus issuance.
- Rollback via GitOps restored service without a risky forward fix under pressure.

## What went wrong

- The skew tolerance was tightened without accounting for real-world edge-node clock variance.
- Pre-release testing ran in a clock-synchronized environment that could not reproduce the
  skew, giving false confidence.
- The intermittent, node-dependent symptom lengthened diagnosis.

## Lessons learned

- Distributed clocks are never perfectly synced; any time-window verification must tolerate
  realistic skew, and that skew must be represented in tests.
- Node-dependent, intermittent failures are the hardest to diagnose; per-node telemetry pays
  for itself on exactly these incidents.
- Failing safe (rejecting valid tokens rather than accepting invalid ones) turned a potential
  security incident into an availability incident — a property worth designing for.
