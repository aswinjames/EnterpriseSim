## Summary

REL-2026-003 shipped a configuration change to the Pricing Service (APP-007) that introduced
a misconfigured regional rounding rule for the APAC region (AU). For a ~22 minute window,
resolved prices in APAC exhibited an off-by-one error in the least significant currency unit
(a rounding-direction misconfiguration) on a subset of price computations. The error was
small per item but systematic. It was detected by a pricing-consistency monitor comparing
resolved prices against expected rounding invariants, and remediated by rolling the regional
rounding configuration back to its previous known-good value. No schema or code change was
needed; the fix was a configuration rollback.

## Impact

- **Users:** APAC (AU) shoppers saw prices off by one minor currency unit on affected items
  for ~22 minutes. A minority of transactions in the window used the incorrect rounding.
- **Regions:** APAC only.
- **Revenue-proxy:** Small and bounded — estimated ~$6K net exposure across affected APAC
  transactions during the window, with individual discrepancies of a single minor unit.
  Affected orders were identified for reconciliation.
- **Data integrity:** Order records are correct as placed; the discrepancy was in the
  price-resolution step. Affected orders were flagged for finance reconciliation.

## Root cause

**Category: config_change.** A regional pricing configuration change in REL-2026-003 set the
rounding-direction parameter for the APAC region to an incorrect value, producing systematic
off-by-one rounding in the minor currency unit. The configuration passed release because
there was no automated assertion that resolved prices satisfy per-region rounding invariants
for the specific parameter that changed. This is a configuration defect, not a code defect —
the pricing engine behaved exactly as its (wrong) configuration instructed.

## Detection

Automated. The pricing-consistency monitor, which checks resolved prices against expected
rounding invariants per region, fired within minutes of the rollout. Detection was healthy;
the gap was in pre-release validation, not in runtime monitoring.

## Resolution

The APAC regional rounding configuration was rolled back to its previous known-good value
through the GitOps configuration pipeline (no manual production change). New price
resolutions immediately satisfied the rounding invariants. Affected orders from the ~22
minute window were enumerated and handed to finance for reconciliation. No code or schema
change was required.

## What went well

- The pricing-consistency monitor caught a subtle, low-magnitude systematic error quickly.
- Rollback was clean and fast because pricing configuration is GitOps-managed and versioned.
- Impacted orders were precisely enumerable for reconciliation.

## What went wrong

- A regional configuration change reached production without an automated rounding-invariant
  check for the changed parameter.
- Regional pricing config changes were not treated with the same rigor (staged validation,
  invariant assertions) as code changes.

## Lessons learned

- Configuration is code: regional pricing config changes must pass the same invariant checks
  and staged validation as source changes.
- Low-magnitude systematic errors (off-by-one in a minor unit) are financially and legally
  material at scale even when individually tiny; monitor for invariants, not just outages.
- Region-scoped changes need region-shaped validation — a global smoke test would not have
  caught an APAC-only rounding misconfiguration.
