## Summary

A guest-checkout feature shipped in **PR-0207** introduced a side effect in the Checkout
Service (APP-003): on every guest order placement, Checkout called the Loyalty service
(APP-015) to provision a Meridian Rewards account — even though guests, by definition, have
no registered identity to attach points to. This produced a stream of **orphaned loyalty
accounts**: rewards accounts with no owning customer profile, created for one-off guest
orders. The defect violated a core Checkout domain invariant (see KN-045): *a guest checkout
MUST NOT create a Loyalty account.* It was detected the morning after release via a Loyalty
data-quality alert on anomalous account-creation volume. It was remediated by hotfix
**PR-0312** (story **CHK-1421**), which removed the guest→loyalty provisioning call, and by
a cleanup job to quarantine the orphaned accounts.

## Impact

- **Users:** No direct customer-facing failure — guest checkouts completed successfully and
  orders were placed. The harm was internal data pollution in the Loyalty domain.
- **Regions:** NA and EU (all regions where the guest-checkout path was enabled).
- **Revenue-proxy:** No direct revenue loss; orders succeeded. Revenue-proxy exposure is
  effectively $0. Cost was borne as engineering remediation effort and Loyalty data
  hygiene (~2 engineer-days plus a cleanup job).
- **Data integrity:** Several thousand orphaned APP-015 accounts created over the ~overnight
  window between PR-0207's release and detection; all were identifiable by the absence of a
  linked identity (APP-014) record and were quarantined, not deleted, pending audit.

## Root cause

**Category: code_regression.** PR-0207 added guest checkout but wired the order-placement
flow to always call Loyalty account provisioning, without branching on whether the checkout
was authenticated or guest. The Checkout domain rule (KN-045) explicitly states a guest
checkout must not create a Loyalty account, but that invariant was not encoded as a test or
a guard in the new code path.

The deeper learning-engine analysis (REF-0019) found two systemic gaps:
- **Missing experience:** no prior experience object warned about the APP-003 → APP-015 side
  effect, so it was not surfaced during context assembly for the guest-checkout task.
- **Test gap:** the plan did not include a negative-side-effect assertion, so passing tests
  gave false confidence. The loyalty domain rules were dropped from context (CTX-0091) for
  budget reasons.

This incident became the canonical example driving **EXP-090** ("guest carts must not create
loyalty accounts") and two policy updates: for APP-003 feature changes always retrieve
APP-015 domain rules, and feature-change plans must include negative-side-effect assertions.

## Detection

Detected by a Loyalty (APP-015) data-quality alert on anomalous account-creation volume,
not by Checkout monitoring. This is a detection gap: the defect originated in APP-003 but was
only visible downstream in APP-015. Detection lagged the release by roughly the length of an
overnight low-traffic period.

## Resolution

Hotfix **PR-0312** (story **CHK-1421**) removed the unconditional loyalty-provisioning call
and gated loyalty account creation on an authenticated identity, and added the negative
assertion test that had been missing. It received two approvals (Tier 0 / touches
cross-domain flow) and shipped through the fast-tracked hotfix pipeline with smoke and
security gates. A separate cleanup job quarantined the orphaned accounts created during the
window for audit before removal. PR-0312 forward-merged to `main`.

## What went well

- Loyalty's data-quality monitoring caught an anomaly that Checkout's own monitoring did not.
- Once correlated, root cause and remediation were fast (~50 minutes end to end).
- The hotfix added the missing negative test, closing the specific gap rather than only
  reverting behavior.
- Orphaned accounts were quarantined (reversible) rather than hard-deleted, preserving audit.

## What went wrong

- A well-known domain invariant (KN-045) was not encoded as a test or guard in new code.
- Tests passed because none asserted the negative case — green CI gave false confidence.
- Relevant Loyalty domain rules were dropped from the task context for budget, so the side
  effect was never considered during design.
- Detection depended on a downstream team's monitoring; Checkout had no signal for this class
  of defect.

## Lessons learned

- Domain invariants that live only in documentation are not enforced; encode them as tests
  and guards. KN-045 said it; the code did not.
- Green tests prove only what they assert — cross-domain side effects require explicit
  negative assertions.
- Dropping domain rules from context to save budget is a false economy when the dropped rule
  is exactly the one that governs the change. This incident directly motivated the policy to
  always retrieve APP-015 rules for APP-003 changes, and is the seed of the ECL learning-loop
  example (ARCH-05, Example A/B): the same model later succeeded on CHK-1421 because EXP-090
  had been learned.
